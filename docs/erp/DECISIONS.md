## 2026-10-30 - Greenfield codebase (part 00.01)
`ERP_SAP CLS` is a new codebase. The owner chose not to audit `ERP_Construction` or `ERP_SAHAA INFRA`. The discovery baseline is therefore empty.

## 2026-10-30 - Technology stack (part 00.02)
Owner chose Node + SQLite over PostgreSQL because PostgreSQL and Docker are not installed on the development machine.

- Server: Node 24 (ESM), Express 5, `node:sqlite`, Zod for input validation.
- Client: React 19, Vite.
- Tests: `node:test` for unit and API tests; Playwright (installed Chrome, no browser download) for E2E.
- Consequence: the pack's `NUMERIC(18,2/4/3)` and `EXPLAIN` on 100k rows do not map onto SQLite. Money and quantities must be stored as integer minor units or as text decimals, never REAL. A move to PostgreSQL later needs a migration plan; the migration files are plain SQL kept simple for that reason.
- Consequence: `timestamptz` is stored as ISO-8601 UTC text.

## 2026-10-30 - Schema baseline locked at the end of part 00.02
00.01 found no database, so its baseline is empty and could not protect anything. `schema/baseline.json` was locked from migrations `20261030000001` to `20261030000003`. From now on schema-diff fails if any of those objects is altered or dropped. New tables, new indexes and new nullable (or defaulted) columns are allowed. To re-lock after an approved change run `node scripts/schema_diff.mjs --lock` and record the reason here.

## 2026-10-30 - Feature-flag data model
One table, `core_feature_flags`. A row's scope comes from its columns: environment default (`environment` set), company override (`company_id`), project override (`company_id` and `project_id`), flag default (all NULL; `default_enabled`). Overrides apply in every environment. Flags are defined by reference-seed migrations, never created through the API.

## 2026-10-30 - Golden outputs
`golden/registry.mjs` holds deterministic runners; `golden/outputs/*.json` holds the captured results, compared byte-for-byte. The first registered output is the flag-evaluation matrix, because no business calculations exist yet.

## 2026-10-30 - CI/CD and release engineering (part 00.03)
- One quality-gate command, `npm run erp:regression`, is both the local check and the CI `verify` job, so the two cannot drift.
- Staging and production hosting are not chosen. Deploy, rollback, backup and smoke-test tooling is written against a directory-based environment and rehearsed there; moving it to a real host means replacing the start/stop and copy steps in `scripts/lib/deploy.mjs`.
- Database rollback prefers the down-migrations of the build being removed (keeps new data) and falls back to the pre-deploy restore point (loses data written since). Restore points are SQLite `VACUUM INTO` copies.
- Coverage gate: line coverage of changed JavaScript files under `src/server` and `scripts/lib`, minimum 60 %, to be raised to 80 %. The server entry point is excluded because it is exercised as a separate process. Client code is covered by the E2E suite, not by line coverage.
- Build ID is `<timestamp>-<commit>` locally and `<run number>-<commit>` in CI. Versions are bumped by hand with `npm run release -- patch|minor|major`; the changelog comes from the `P<part>:` commit subjects and business-language notes from `Release-note:` lines.
- The About page and `GET /api/v1/core/about` are limited to `core.about.view` (SYSADM, ITADM). The build ID appears nowhere else in the UI.
- Security scans: `npm audit` (high and critical block), a built-in secret scanner (`scripts/lib/secrets.mjs`) and CodeQL in the workflow. No third-party secret scanner is installed.

## 2026-10-30 - Application architecture and API conventions (part 01.01)
Architecture decision records. The reference text is `docs/erp/ARCHITECTURE.md`; each record here gives the reason.

- **ADR-01 Layers.** route -> controller -> service -> repository, one file each per resource. Business rules, the permission guard and the data-scope check live in the service so jobs, imports and other modules that call it are protected like HTTP requests. Tests fail if a controller, route or validator contains SQL.
- **ADR-02 Module ownership and registry.** `src/server/modules/<code>/` owns its tables; `modules/registry.js` lists modules and mounts them under `/api/v1/<code>`. The existing flags, about and session code was moved into module `core`, which is the reference implementation. Nothing outside this repository's own code needed an adapter.
- **ADR-03 Platform libraries.** Cross-cutting code (`config`, `db`, `http`, `auth`, `validation`, `pagination`, `money`, `health`, `audit`, `events`) lives in `src/server/platform/` and never imports from `modules/`. Old file paths were not kept as re-export shims: all imports were updated, so each thing has one location.
- **ADR-04 One error envelope and one error-code registry.** `platform/http/errors.js` holds the codes; the handler, the guide page and the tests read the same list. Malformed JSON used to fall through to a 500; it is now a 400 `BAD_JSON`, and an oversized body a 413. That is a bug fix: the old response was an unhandled-error 500, not a designed shape. Unexpected errors return a generic 500 and the stack stays in the server log under the correlation ID.
- **ADR-05 Request logging.** One JSON line per request with correlation ID, method, path, status, duration and user. Query strings and bodies are never logged, so a search term or an amount cannot leak into logs.
- **ADR-06 Lists.** `parseListQuery` implements `page`, `pageSize` (max 200), `sort`, `q`, `filter[column]`, `from`, `to`. `sort` and `filter` accept only columns the endpoint allow-lists (otherwise 400) and `ORDER BY` is built from a column map. Express 5 does not nest `filter[x]`, so the keys are matched by pattern.
- **ADR-07 Decimals.** No floats for business numbers. `src/shared/decimal.js` is a BigInt-based exact decimal, rounding half-up (ties away from zero) by default, used by the server and the browser. Money 2, rate 4, quantity 3, percent 4 places; rounding happens once at the end; `allocate` splits an amount without losing paise. A number with a fraction must be passed as a string.
- **ADR-08 Health.** `/health/live` is public. `/health/ready` is for ITADM/SYSADM or a monitoring token (`HEALTH_TOKEN`, 16 characters or more, compared in constant time) because it names failing dependencies. Database, queue (outbox) and storage are checked; a failing dependency returns 503, a backed-up outbox is `degraded` (200). `/api/health` stays unchanged.
- **ADR-09 Events.** `publishEvent` writes the standard envelope (`eventId`, `occurredAt`, `companyId`, `projectId`, `siteId`, `entity`, `entityId`, `version`, `actorId`, `data`) to the outbox in the caller's transaction. Rows written by part 00.02 have the older flat payload; the dispatcher in 01.04 must accept both (D-016).
- **ADR-10 Frontend.** One API client (retries idempotent GETs only, one correlation ID per call, errors normalised to `ApiError`), TanStack Query for server state with a key factory, and a module route registry. Navigation hides entries the user has no permission for and entries whose feature flag is OFF; the page itself still shows a no-permission or not-enabled state when reached by URL. The guide is rendered by a small parser that builds React elements, so no HTML is ever injected.
- **ADR-11 Contract snapshot.** `tests/contract.test.js` records 25 requests to the pre-existing routes and replays them against the data that existed then (migrations up to `20261030000004`), so later reference seeds do not look like contract changes. Permission lists may grow, never shrink. Re-record only on purpose and say why here.
- **ADR-12 Gated coverage.** The coverage gate now also covers `src/shared` and the plain-JavaScript client platform files (API client, registry, markdown, formatting, query keys). React components stay covered by the E2E suite.
- **ADR-13 Feature flag.** The guide ships behind `ff.core.p0101`: default OFF, ON in development and test. The API answers 404 "not enabled" and the navigation entry is hidden while it is OFF for the user's company.

## 2026-10-30 - Database foundation, migration framework and data integrity (part 01.02)
- **ADR-14 Money and numbers are whole integers.** The pack asks for NUMERIC(18,2) and similar; SQLite has no exact decimal type, and REAL is a float. Business numbers are therefore stored as INTEGER minor units: money in paise, rates x10000, quantities x1000, percentages x10000, converted with `toUnits` and `fromUnits` (exact, half-up). SQL can add, compare and index them exactly, so "header total equals the sum of its lines" is an exact `<>` test. The schema lint rejects REAL, TEXT or untyped money-like columns. When the database moves to PostgreSQL the columns become `NUMERIC(18,2)` (money), `NUMERIC(18,4)` (rates), `NUMERIC(18,3)` (quantities), `NUMERIC(9,4)` (percentages) in one migration that divides by the scale, and indexes are then created `CONCURRENTLY` outside the transaction. SQLite integers are 64-bit; `toUnits` refuses values above 2^53 paise (about 90 trillion rupees).
- **ADR-15 Migration zero.** Part 00.01 found no database, so there is nothing to baseline from outside. Migration `20261030000001` is migration zero and `docs/erp/DB_BASELINE.md` (generated, checked in CI) is the schema at the end of this part. `schema/baseline.json` was re-locked from migrations up to `20261030000007`; objects in it can never be altered or dropped, only added to.
- **ADR-16 Idempotency.** Keys are scoped to the user and the endpoint. First request: the handler runs and a 2xx response is stored for 24 hours. Same key and same body: the stored response is returned with `Idempotency-Replayed: true`. Same key, different body: 422 `IDEMPOTENCY_KEY_REUSED` (BR-02). Same key while the first is still running: 409 `REQUEST_IN_PROGRESS`. Non-2xx responses are not stored, so a client that fixes a validation error can reuse its key. The body is hashed after sorting object keys, so key order does not matter. The key is required on submit, post, payment, stock and approval endpoints (`required: true`) and optional on the flag change and the integrity run, where it is honoured when sent. Stored responses hold whatever the endpoint returned, so they are business data with a 24-hour life (D-019).
- **ADR-17 Integrity checks.** Seven checks, each with a severity; a failed Critical check blocks CI (BR-03) and `--fail-on` raises or lowers the bar. Business tables are found by convention (column names) and modules add what the schema cannot say through `integrityRegistry.register`. A check with nothing to look at reports `not_applicable`, never a pass, so an empty database cannot look healthy. Results are stored one row per check per run. Samples hold identifiers only (table, id, company, key) so ITADM, who has no business-data access by default, never sees amounts, rates or personal data. A check that throws is reported as a failure with the reason instead of hiding the other checks.
- **ADR-18 Company scope.** `companyScope`, `findScoped` and `listScoped` are the way business queries read a company's data. An actor without a company is refused (deny by default), a row of another company is "not found", and a scoped list must have a limit of 1 to 200.
- **ADR-19 Back-fills.** A back-fill is a function that does one batch and returns its cursor. The batch and its ledger update commit in one transaction, so there is no state where data changed but the ledger did not. Failed batches roll back and the ledger records the error; the next run resumes. No real back-fill exists yet: the registry (`backfills/`) is empty and the framework is tested with fixtures.
- **ADR-20 Backups.** A backup is a `VACUUM INTO` copy plus a manifest (file hash, SQLite integrity result, row count and hash of each table, schema hash). Restore verifies the manifest first, never touches the target if verification fails, and re-checks the restored file against the manifest. The helpers moved from the deploy tool into `scripts/lib/backup.mjs`; the deploy tool uses them.
- **ADR-21 Test data.** The generator creates its own `perf_*` tables in a scratch database, not in the application's migrations, so performance data can never leak into a real schema. It is deterministic for a seed (fixed timestamps included) and its tables follow every standard, so the integrity suite and the schema rules run against something realistic.
- **ADR-22 Data Health.** `/admin/data-health`, API `POST /api/v1/core/integrity/run` (ITADM, `core.integrity.run`), `GET .../integrity/summary` and `.../integrity/runs` (ITADM and SYSADM, `core.integrity.view`), behind `ff.core.p0102`. The run is synchronous: the suite takes about half a second on 100,000 documents; long runs belong to the job scheduler of part 01.04 (D-018).
- **ADR-23 Numbering counters.** One counter row per series and period key, advanced by a single `INSERT ... ON CONFLICT ... RETURNING` statement, so concurrent requests and processes cannot receive the same number. A gap-free series issues only inside the caller's transaction (a rollback gives the number back); a non-gap-free series may be issued on its own. Cancelled numbers stay in `core_number_issues` as CANCELLED and are never reused.
- **ADR-24 Series scope.** The most specific series wins: project, then branch, then company. A reset rule needs matching tokens in the format (a financial-year reset needs `{FY}`, `{FYS}` or `{YYYY}`), so numbers cannot repeat. Statutory numbers are at most 16 characters of letters, digits, `/` and `-` (GST rule 46).
- **ADR-25 Period control.** Statuses are per module and per month. Soft-closed accepts only actors with `core.period.post_soft_closed`. Closing is by the Accounts Manager; reopening needs an approved request (ACCMGR then CFO) and is applied in the transaction of the final approval.
- **ADR-26 Parameters.** Typed (string, integer, decimal, boolean, date, json), with limits, allowed values and scopes declared in code. Rows are never edited: a new value closes the old one the day before it starts. Past dates are refused. System scope needs `core.param.configure_system` (IT Administrator); company scope needs `core.param.configure`.
- **ADR-27 Interim approvals.** `platform/approvals` supports role chains, segregation of duties (the requester cannot approve), comments and a handler that applies the change in the same transaction as the last approval. Delegation, SLA and configurable chains belong to the workflow engine (04.01, D-022).
- **ADR-28 Excel import.** Holiday import reads `.xlsx` in the browser (`read-excel-file`) and sends rows as JSON, so the server needs no spreadsheet parser. The import is all or nothing: every bad row is reported and nothing is saved.
- **ADR-29 Outbox stays as it is.** `core_outbox` (part 00.02) is the event log and is not altered: its `published_at` means "the relay has fanned this event out". Per-consumer state lives in the new `core_inbox`, so no pre-existing object changes. The outbox is never purged, because it is the replay history.
- **ADR-30 Delivery model.** At-least-once delivery with de-duplication: one inbox row per (consumer, eventId), a handler and its processed mark in one transaction, retries with exponential back-off (30 s doubling to 1 h), dead letter after `maxAttempts`. Handlers are synchronous. Exactly-once effect depends on the handler writing only inside its transaction; effects outside the database (mail, SMS) must check `ctx.replay` and be idempotent on their own.
- **ADR-31 Request types are not a CHECK constraint.** `core_change_requests.type` listed its values in a CHECK, so each new approval-controlled change needed a table rebuild. Migration `20261030000013` rebuilds the two change-request tables once without it (rows, ids and indexes kept; its down migration restores the constraint and removes `schedule_change` requests). The approval engine already refuses a type with no registered handler.
- **ADR-32 Single database, no external queue.** The bus and the job runner use SQLite tables and polling workers; several instances sharing the file are safe because every claim is a single statement or a `BEGIN IMMEDIATE` transaction. A message broker or Socket.IO relay is not built (D-026); the interface (`publishEvent`, `subscribe`, `enqueue`) does not change when one is added.
- **ADR-33 Schedules.** Cron in IST with five fields; a missed slot runs once; a schedule is defined in code (seeded once) and changed only through a maker-checker request (ITADM asks, SYSADM approves). Schedule rows are system-wide; the request is filed under the requester's company.
- **ADR-34 Console scope.** Events, dead letters and jobs are shown for the actor's company plus system-wide ones (no company). Payloads are masked (identifiers, bank, salary, rate and cost fields) in the console, the dead-letter viewer and CSV exports.
- **ADR-35 Access follows the record.** The file service has no permissions of its own for reading, attaching or removing: it asks the module that owns the linked record (`fileEntities`). A module that registers a record type therefore decides who can see its files, and a cross-company or unknown record is "not found". Only administration (overview, settings, rescan) uses `core.files.*` permissions.
- **ADR-36 Type checking.** An extension must be in the company's allow-list and the leading bytes must match what a real file of that type starts with; Windows, Linux and macOS programs and scripts are refused under any name. Archives (zip), HTML and SVG are not on the list: they can hide or carry active content, and the system cannot check what is inside.
- **ADR-37 Scan before use.** A stored file is PENDING until the scan job gives a verdict; nothing but CLEAN is ever served, not even to an administrator. The built-in scanner finds only the EICAR string and an ERP test string (so the quarantine path works everywhere); real protection is ClamAV through clamd, which the system checks and uses when `CLAMAV_HOST` is set. A scan that errors is retried, never treated as clean.
- **ADR-38 Resumable uploads.** Offset-based chunks into a temporary file, a session per upload, the server as the source of truth for how many bytes it has (a half-received chunk is discarded). Completing re-runs every check, so the two upload paths cannot differ in what they accept.
- **ADR-39 Signed links.** A link is a short-lived bearer: HMAC over file, expiry, variant and disposition. Permission is checked when the link is issued, not when it is used, so a link keeps working until it expires even if the record's permissions change. The life is short (default 120 seconds) and a company setting. `FILE_URL_SECRET` is required in staging and production so every instance signs and verifies alike.
- **ADR-40 Metadata and privacy.** Capture time and GPS position are read from a JPEG's EXIF into the record. "Strip" on upload removes every metadata block from the stored JPEG or PNG (camera, serial, owner, thumbnails) except the orientation, so the picture still shows the right way up; time and position stay in the record only. The checksum is of what is stored.
- **ADR-41 Files are never destroyed by the application.** Delete is a soft delete and a superseded version stays; quarantined files are moved, not deleted. Retention classes are recorded per file from the category setting, but no job purges by retention yet (D-036).
- **ADR-42 The calculation language.** Formulas are programs in a small language parsed and evaluated by our own code: decimals, text, yes/no, arithmetic, comparison, `if`, and the functions round, min, max, abs, floor, ceil, percent and sum. It is deliberately not JavaScript: nothing can loop, read the environment or run for long. A division keeps 12 decimal places and the output is rounded once; 3,000 random cases of each built-in formula matched the original code to the paisa (D-038 names the theoretical limit). Rounding policies are named (`half_up`, `bankers`, `down`, `up`) and apply to every `round()` and to the outputs of a formula unless a call names a mode.
- **ADR-43 Versions are immutable and approved.** A version is a draft until it is activated; after that its calculation cannot change (a database trigger refuses it), and a change is a new version. Activation is a request to the approval chain of the owning module (project controls manager for BOQ, accounts manager for tax, billing and stores, IT administrator for core), plus the CFO for financial formulas. The built-in version 1 of each existing calculation is seeded as active by the system, because it is the code that already ran; starting the application fails if the stored definition and the code differ. Two versions may not start on the same day or out of order, so history is never rewritten.
- **ADR-44 A document keeps its formula versions.** The sample bill stores the versions it was calculated with. A draft is recalculated with the versions in force today; a submitted bill only with its stored versions, and the result must equal what is stored (BR-01). The same rule applies to every module that adopts the engine.
- **ADR-45 Traces.** The engine can store, for a record, the inputs, every step with its formula and value, the roundings, the outputs and the formula version (`core_calc_traces`). Showing a trace needs view permission on the record, decided by the module that owns it (the same registry the file service uses). Traces are for audited values; the test bench keeps nothing.
- **ADR-46 Shadow mode.** A version in SHADOW is evaluated next to the active one whenever the active one is used for a record or the bench with recording on; it never decides a result and cannot calculate a record by itself. Results go to `core_calc_shadow_results`. The activation request shows how many real calculations were compared and how many differed.
- **ADR-47 Units of measure.** Until the UOM master of part 06.02 exists, units and factors live in `core_uoms` and `core_uom_conversions`. A factor is a decimal text; a chain of factors is multiplied as an exact fraction and rounded once. An item row beats a generic row for the same pair, and rows are shared by every company (D-042).
- **ADR-48 Golden outputs for calculations.** Golden files for the built-in formulas were captured from the code the engine replaced (`tests/helpers/legacy_calcs.js`, which uses no formula language) on fixed cases that include rounding boundaries. They are compared with the engine's output by `npm run erp:golden` and by the full regression.
- **ADR-49 Redaction by key and by pattern.** Every log entry is redacted before it is written or buffered: by the name of the field (secret keys fully, identifiers keep four characters, document content omitted) and by pattern in free text (PAN, GSTIN, Aadhaar, IFSC, e-mail, bearer tokens, JWTs, long digit runs). Redaction is the logger's job, not each caller's, so a new log line cannot forget it (BR-01).
- **ADR-50 Pseudonymised user in logs.** Logs carry `u_` plus ten hex characters of an HMAC of the user name, never the name. An administrator who needs the person looks up the pseudonym through the audit trail, which does record the user.
- **ADR-51 Own tracer instead of the OpenTelemetry SDK.** The SDK is not installed and nothing is added without need. A small tracer keeps W3C `traceparent` and exports OTLP/JSON, so an OpenTelemetry collector can take the traces later without changes to the code that creates spans (D-046).
- **ADR-52 Metrics by route pattern.** Metrics are keyed by the matched route pattern, not the URL, so identifiers never create new series; a URL that matches nothing is counted as "unmatched". Latency is a fixed-edge histogram per minute, which makes percentiles cheap and objectives computable over days from hourly roll-ups.
- **ADR-53 Objectives and alert rules change by request.** A change to an objective or an alert threshold can hide a real problem, so it follows maker-checker like other configuration (ITADM asks, SYSADM approves) and is audited.
- **ADR-54 The event log shows the latest 20,000 events.** At 100,000 events the unfiltered log took 1.4 s (baseline, part 01.07) because each payload had to be read. The page now browses the newest 20,000; older events stay in the outbox for replay (D-045).
- **ADR-55 Modules call connectors by code through one service.** `hub.call(code, operation, payload)` is the only way to reach an outside service. Retries, timeouts, the breaker, the rate limit, credentials and logging live there, not in modules, so a provider can be replaced without touching a module and every call is logged the same way.
- **ADR-56 Credentials are staged, approved, then active.** A secret entered in a change request is encrypted at once and held as PENDING; the request carries only the key names. Approval promotes it in the approver's transaction. Nothing but the integration service can decrypt, and the approval record never contains a value.
- **ADR-57 AES-256-GCM with a slot-bound nonce.** Each value is encrypted with a key derived from `VAULT_KEY`, a random 96-bit nonce and the connector and key name as additional data. A database copy without the key is useless, and a value moved between rows fails to decrypt.
- **ADR-58 Only provider-side failures trip the breaker.** Timeouts, network errors, 5xx, 408 and 429 count against the provider; a 4xx answer to a bad request does not, or one user's mistake could pause everyone's email.
- **ADR-59 Switching off is immediate, switching on is approved.** An outage needs a kill switch that does not wait for an approver; turning a connector back on is a configuration change and needs the chain.
- **ADR-60 Connector codes are unique across the system.** The public webhook URL identifies the connector by code before any company is known, so a code cannot repeat in another company.
- **ADR-61 Short access token, server-side session.** The access token only names a session; the session row decides whether it is still good. A signed token alone cannot be revoked until it expires, which is too slow for a forced sign-out, so the extra lookup on each request is accepted.
- **ADR-62 Refresh token rotation with reuse detection.** Each refresh replaces the token. A replaced token that comes back means two parties hold the same one, and the whole session ends. The cookie is HttpOnly and SameSite=Strict, scoped to the sign-in routes, and used only with a custom header.
- **ADR-63 Argon2id from Node itself.** Node 24 provides Argon2id, so no native dependency is added. Old hashes are verified by named verifiers and upgraded at the next successful sign-in; nothing writes an old format again.
- **ADR-64 One answer for every sign-in failure.** The same message, status and time for a wrong password, an unknown name, a disabled account and a lock; failures are counted per name, not per account, so the count also exists for names that do not.
- **ADR-65 Second step by policy, not by flag.** Which roles need MFA is policy data. A role on the list with no factor is led into set-up instead of being refused, so enforcing it never locks the last administrator out.
- **ADR-66 The sign-in routes are not behind the feature flag.** `AUTH_MODE=iam` is the switch for sign-in itself; a per-company flag cannot decide how someone who is not yet known signs in. The flag hides the account and administration screens.
- **ADR-67 A thin user store until 02.03.** `iam_users` holds just enough to sign a person in. It is replaced by the user master, and `iam_credentials` keeps its `user_id` meaning.
- **ADR-68 One description drives the organisation lists.** `org/entities.js` declares each entity once; the service, validators and routes are generic over it. Eight entities would otherwise be eight copies of the same create, edit, deactivate and list code.
- **ADR-69 Activation and geofence changes are controlled; drafts are not.** A project or site is created as a draft and edited freely; becoming active, and any later geofence change, need approval. This keeps set-up fast and keeps live attendance fences under maker-checker, and a direct edit is refused rather than silently queued.
- **ADR-70 Effective dates in their own table, current holder mirrored.** `org_assignments` keeps who held a role from when to when; the entity row holds the current holder so every list and join stays a plain read. A future change waits (`applied = 0`) and a daily job applies it.
- **ADR-71 Deactivation blockers are a registry.** The part that owns the open records (attendance, stock, billing) registers a blocker for the entity; this part does not read other modules' tables. Until they exist only the built-in blockers apply, and the registry is how BR-03 stays true as modules arrive.
- **ADR-72 The geofence arithmetic is shared.** `src/shared/geo.js` is used by the server and the browser editor, so what the editor accepts is exactly what the server accepts and what the test button says is what attendance will later decide.
- **ADR-73 Company records are explicit.** A company must exist as a record before its data can be added (a clear refusal otherwise). The system administrator sees every company and creates new ones; everyone else sees their own. Company 1 is seeded.
- **ADR-74 The user record is completed in a one-to-one table.** `ADD COLUMN` cannot be written idempotently in SQLite and would alter a locked table, so the new fields live in `iam_user_profiles` with real foreign keys, backfilled for existing users. `iam_users` keeps its status check and every part-02.01 query unchanged.
- **ADR-75 Sign-in status and lifecycle are kept apart.** `status` answers "may sign in", `lifecycle` answers "where is this person in joining or leaving". One function changes both, so they cannot drift.
- **ADR-76 No access without an approved role, enforced by one gate.** An actor with no roles is flagged and a single middleware refuses everything outside a short list, rather than each route being asked to check. A new module is closed to such a person by default.
- **ADR-77 One account per person for good.** Contact details stay unique across all companies and a deactivated person keeps the account, so a rehire is a reactivation (returning with no role) and history stays on one record.
- **ADR-78 Granting a role is approved, taking one away is not.** Adding access goes through the approval chain; removing it only lowers access, so it is immediate and audited. A deactivated person's roles are removed so reactivation cannot silently restore access.
- **ADR-79 Invitation links are shown to administrators only outside production.** In production an administrator can never see a link, so they cannot accept an invitation in someone else's name.
- **ADR-80 Grants are computed once per request and carried on the actor.** Every layer asks the same object, so the page, the route, the service and the list query cannot disagree. Hand-built actors (jobs, tests) fall back to the role templates in code.
- **ADR-81 A scoped grant is honoured only by code that looks at the record.** The plain permission check means the whole company. This is deliberate: it makes a scoped assignment safe by default, because a module that has not been taught about scope simply refuses it instead of quietly widening it.
- **ADR-82 System roles are code, stored for the engine.** Templates live in `templates.js` (reviewed with the code, one place to change) and are seeded as locked rows; custom roles are data changed only by an approved request. A template change reaches the database at the next start.
- **ADR-83 Deny beats allow.** A deny in any role held, within its scope, removes the permission whatever another role allows (BR-01), and the explainer names the role that denies.
- **ADR-84 The nine old roles are aliases, and their old access is frozen.** Nobody's role code changes. The table of what each could do before is kept unchanged as the "before" of the comparison, so a later template edit cannot hide a regression.
- **ADR-85 Roles stored on the user remain valid.** The role list of part 02.03 is treated as company-wide assignments with no dates, and the engine reads it with the assignment table, so no user needed migrating and nothing could be lost in a migration.
- **ADR-86 Field masks are by role, most open wins.** A person who holds a role that shows a field sees it; otherwise the field's own default (partly shown or hidden). This matches how roles combine everywhere else.
- **ADR-87 Thirty seconds of caching, immediate on the instance that made the change.** A shared cache or an event per change was not needed to meet 60 seconds, and the in-process clear keeps the common case (an administrator's own session) exact.
- **ADR-88 A rule names two sides and how they meet.** A rule is two lists of patterns (a `*` stands for any text) and a scope in which they must not meet: the person (permissions held), the document, the vendor, the period or the project. One engine serves both preventive and detective checks, so a rule is written once. Severity decides the response: block (stop it, name the conflict), warn (allow and record) or detect (record). Changes to a rule go through an approved request, the auditor or the director deciding, never the administrator who asked.
- **ADR-89 The check at assignment is "what the person would hold", never a guess from role names.** Before a role is given, the permission engine is asked what the person would hold with it (`extra` holdings, never cached) and the result is compared with what they hold now: only conflicts the new role introduces are charged to it, so a person who already had a conflict is not blocked from an unrelated role. The same check is made again when the request is approved, because what the person holds may have changed.
- **ADR-90 What people did is a ledger, kept in the approver's transaction.** Action rules compare what a person is about to do with what they already did to the same document, vendor, period or project. The ledger row is written in the same transaction as the act, so a rolled-back act leaves no row; a refusal is recorded after the rollback so the blocked attempt is not lost.
- **ADR-91 Elevation is a dated role holding the engine reads, and the clock ends it.** An approved elevation is a row with start and end times; the permission engine includes it while the clock is inside them and never caches an answer past the moment one starts or ends. Access therefore ends at the end time even if the expiry job has not run; the job only marks the row and publishes the event. An elevation must pass the same segregation-of-duties check as a permanent role.
- **ADR-92 Everything done while elevated is tagged by the request, not by changing every writer.** A middleware writes one log row per request made while a person holds an elevation, with the correlation ID; the audit trail now records that correlation ID by default, so every change made in those requests can be listed with the elevation.
- **ADR-93 A review campaign applies its decisions only when it closes, and cannot close while any line is undecided.** Reviewers certify or revoke lines freely until the close, so a change of mind costs nothing; closing applies the revokes in one transaction, never removes the last active system administrator, and checks everyone affected again for conflicts. A person never reviews their own access.
- **ADR-94 Dormant accounts are reported by default and suspended by policy.** Suspending people automatically is a decision a company makes with a parameter, not a default that could lock out a site. When on, it uses the same lifecycle change as a manual suspension, so sessions end and the history shows why.
- **ADR-95 The existing audit table is kept; the chain is beside it.** core_audit_log has been written by every part since 00.02 and the schema baseline forbids changing it, so each row gets a companion row in core_audit_chain (sequence, company, who and where from, field changes, hash). Old rows are chained once, in order, when the application starts, and stay readable.
- **ADR-96 The hash covers the row and the one before it, and the chain checks for gaps.** Each hash is SHA-256 over the audit row, its chain fields and the previous hash, with consecutive sequence numbers. Changing a row, deleting one, inserting one outside the service or removing the triggers is each reported, with the entry where it was found.
- **ADR-97 Append-only is enforced by triggers and proved by the chain.** The triggers refuse UPDATE and DELETE on the audit tables for every connection. Because SQLite has no roles, the chain is the real evidence: the nightly check reports a break as a critical security event once for each new break.
- **ADR-98 Security events come from the domain events, in the same transaction.** publishEvent writes the matching security event with the event, so every module and parts 02.01, 02.04 and 02.05 are covered without each calling a logger, and an event exists only if its change committed. Failed sign-ins, refused requests and sensitive exports are written where they happen.
- **ADR-99 Sensitive values are masked when the diff is written, not only when it is read.** A sensitive field shows that it changed but never its old or new value in the diff; older raw columns are masked on the way out. A reader of the audit trail therefore never needs to be trusted with a mobile number or an account number.
- **ADR-100 History is for people who may see the record.** The History tab of a record needs the right to view that kind of record (or the auditor's right); an unknown kind of record needs the auditor. Every query is limited to the company.
- **ADR-101 Retention seals months; it never deletes.** The application has no delete path to the audit trail at all. A sealed month records its range, size and closing hash and can be exported; whether to move old months to cold storage is a deployment decision.
- **ADR-102 Routes are declared in one reviewed file, and the application checks the file against itself.** Every route has a line in `platform/security/route-policy.js`: its guard (permission, own account, record rules, public, infrastructure), the permission, scope, rate-limit class and whether it is audited. The application lists its own routes at start-up and compares; an undeclared route stops a staging or production start and fails CI. One file is what a reviewer reads to see who may call what.
- **ADR-103 The permission at the door is checked before the route runs, and again in the service.** A route declared with a permission is closed to anyone who holds none of its permissions, before any handler or validation runs, so a new route cannot be left open by forgetting a guard. The service still checks, with scope, because jobs and other services call it without HTTP.
- **ADR-104 The self-test is the evidence that the declarations are true.** The registry page runs every non-public route with no sign-in (must be 401) and with a person holding no permission (a permission route must be 403) and stores each result. A wrong declaration shows as a failure; the test also runs in CI.
- **ADR-105 Headers, CORS, CSRF and rate limits are a baseline, not a feature flag.** They protect every company and cannot be switched off for one. The feature flag `ff.iam.p0207` gates the central permission check, the registry and settings pages and the export controls. The values themselves are settings changed by an approved request.
- **ADR-106 A content security policy that allows only our own scripts; styles may be inline.** React sets style attributes, so `style-src` allows inline styles; `script-src` is `self` only, and a settings change that would allow inline or eval scripts, or drop `frame-ancestors`, is refused by validation.
- **ADR-107 Rate limits are per address and per person, by class of request.** Sign-in and second-step requests have their own, stricter class; exports too. The count is a sliding minute in memory (D-107). The first refusal in a window is a security event; the 429 says how long to wait.
- **ADR-108 A bulk export of people needs approval once, for exactly what was approved.** Above the threshold (1,000 by default) the request goes to the HR manager or the director; the approval is the requester's, is tied to the report and its filters, and is used once. Every export is in the audit trail and, for personal data, the security log.
- **ADR-109 One JSON file is the design system's source; CSS and Tailwind are generated from it.** `src/shared/design/design-tokens.json` (the reference tokens of the prompt pack, plus a display size, the comfortable and compact densities, a muted status and the status semantics) is turned into `src/client/design-tokens.css` and a Tailwind preset by `scripts/build_tokens.mjs`; the regression fails if either is not what the JSON produces, or if any text pair falls below WCAG AA.
- **ADR-110 Tokens are code, not settings.** A token change goes through review like any code change, so it needs no runtime approval and leaves no partial theme in production; the style guide shows them and never edits them. What a person may change is their own appearance, which is personal and audited.
- **ADR-111 Themes, density and language live on <html>.** data-theme, data-density and lang on the root element switch every variable at once, so a change shows without a reload and a container can carry its own theme (the style guide shows the three side by side). A first visit follows the device (dark, more contrast); afterwards the saved preference wins, on every device.
- **ADR-112 Self-hosted IBM Plex, never inlined.** The fonts come from the @fontsource packages and are served by the application; the build keeps font files as files so the content security policy can stay at font-src 'self'.
- **ADR-113 One icon set behind one component.** Lucide (ISC) provides the outline glyphs, imported one by one from a map generated from the icon registry; the construction glyphs are original drawings on the same grid and stroke. Pages name a registry key, never a glyph, so the set can change in one place.
- **ADR-114 Colour values are refused in component code by a lint rule.** erp/no-hardcoded-color reports a hex, rgb() or hsl() colour in a string, template or JSX text of the client; the client stylesheet is checked by a test. The backdrop and the QR background became tokens.
- **ADR-115 Form definitions are code, seeded by migration.** A form declares its sections, fields, rules, lookups, conditions and grid in a shared module (`src/shared/forms/*.js`) used by the browser and the server; a migration seeds the same definition into `ui_form_metadata`, and a test keeps the two equal. A change is a reviewed code change, as for the tokens (ADR-110); the table allows a company-specific version later without a new mechanism.
- **ADR-116 Drafts are personal, kept on the server, and not audited per save.** Autosave every 30 seconds and on leaving a field would flood the hash-chained audit trail with half-typed text; a draft is not a business record. Discarding a draft is audited; saving the real record consumes the draft in the same transaction. A stale version is refused (409) so two windows cannot overwrite each other.
- **ADR-117 One lookup contract, registered by the module that owns the data.** GET /api/v1/<module>/lookups/<name>?q=&page=&pageSize=&parent=&id= answers code, name and the lookup's extra columns, paginated, inside the person's data scope; `id=` fetches chosen values, `parent=` makes it dependent. Modules register lookups in the platform registry; the routes are mounted behind ff.ui.p0302.
- **ADR-118 The server recomputes every figure and refuses a client total that differs.** The form sends the line amounts and the total the person saw; the server calculates each line with the calculation engine and adds them up, and when the screen and the server disagree nothing is saved (422, the field named). Client validation uses the same Zod schema as the server and never replaces it (BR-01).
- **ADR-119 One List Report contract, declared once per register.** A register declares its columns with defineList (SQL, type, label, what can be sorted, filtered and totalled). The same definition validates the request (filter[key][op]=value with operators per type, sort, page sizes 25-200), builds the WHERE with every value bound, returns the page, the count and the totals of the whole filtered set, and is replayed by exports and export jobs, so the export is always the screen's own query (BR-01, BR-02).
- **ADR-120 A masked column cannot be sorted or filtered.** Masks apply to rows, totals and every export; sorting or filtering on a masked value would reveal its order or range, so the server refuses it (400) and the column description marks it.
- **ADR-121 Exports run on the server; large ones are jobs.** Up to core.export.max_rows the file is returned at once, otherwise a job writes it with the requester's scope and masks and keeps it 7 days under My Exports. Formula-looking text is made inert, every file carries a generated-by/at and filters footer, and every export is audited through the export guard of 02.07.
- **ADR-122 Saved views are configuration a team relies on, so their changes are audited.** Personal views belong to their owner; shared views need ui.view.share and are aimed at roles or projects; one default per person and list; optimistic versions. Column choices outside views live in ui_user_preferences.table_settings_json.
- **ADR-123 The server decides the buttons.** A record's `GET /:id` returns `allowedActions[]`: every action that applies to its status, each with `allowed` and the reason when not. The Object Page draws exactly those (BR-01), so the browser never guesses a rule, and the same rule stops the call on the server.
- **ADR-124 One registry of record types gives every record the shared parts.** A module registers its record type (access, audit entities, approval target, document type, related records, snapshot, masks, print) with platform/objects; timeline, discussion, documents, versions and the comparison, related records and print then work for it through /api/v1/ui/objects/:type/:id/... with the record's own permission and data scope.
- **ADR-125 A rejection or a return changes the record in the approver's transaction.** The approval engine gets an optional `decided` hook next to `apply`: for the reference record a rejection cancels it (it keeps its number) and a return reopens it as a draft, in the same transaction as the decision, so the record and its approval never disagree. Existing types are unaffected.
- **ADR-126 Reasons are codes plus words, kept by the server.** Cancelling, rejecting and returning need a reason code from `ui_reason_codes` and a few words; the dialog shows the codes the server holds and the server refuses a missing or unknown one. The audit entry and the approval comment carry both.
- **ADR-127 The menu is built from a database registry that the server filters for the person.** `ui_navigation_entries` holds every page with its group, route, icon, permission key, feature flag, order, keywords and phone visibility; `GET /ui/navigation` returns only what the person's permissions (held for any project or site) and the feature flags allow, plus the denied entries with the reason, so a page that is not offered can still say why. The client route table stays the table of pages; `scripts/nav_check.mjs` fails the regression when a page has no entry or an entry no page.
- **ADR-128 Account and technical pages are placements of the same registry.** An entry is placed in the menu, the account menu or the Technical Console. Build, audit and design-system pages are console entries and a check keeps them out of business groups (BR-03). The key `self` means any signed-in person, so "no permission key" stays an error except for Home and Profile (BR-01), enforced by a database check, the server and a test.
- **ADR-129 The working context belongs to the person and narrows lists with ordinary filters.** The project and site a person works in are kept on the server (`ui_user_context`) and mirrored to the browser key that forms already read; a list narrows by the same choice through its own project and site filters, so saved views, exports and counts follow without a second mechanism. A choice that leaves the person's scope is dropped on read; changing it with unsaved work asks first.
- **ADR-130 Registry changes are maker-checker requests; import never writes.** A change is raised as a request of type `ui_nav_change` in the 01.03 approval engine and applied, in the approver's transaction, only if the entry is still at the version it was raised on; it is audited with old and new values. Import of settings raises one request per difference. The registry page cannot hide itself or change its own permission, so the registry cannot lock its administrators out.
- **ADR-131 One device layer for the camera, the position, the scanner, vibration and push.** Pages and fields call `src/client/platform/device` (camera, location, scanner, haptics, push, low-bandwidth, queue); none of them talks to those browser APIs on its own. Each piece is plain functions that run in Node for the tests, so what a phone does is the same in the gallery field, the scanner page and the parts that follow (attendance, DPR, GRN, inspections).
- **ADR-132 The service worker keeps the app shell and a few calls of the shell, never business data.** The app (page, scripts, styles, fonts, icons) is cached when a version installs and opens with no connection; pages are network-first, hashed files cache-first. Of the API only the calls that draw the shell (session, menu, launchpad, settings, flags) keep a copy, keyed by the person, dropped on sign-out or when the identity changes, and answered only for a GET. A new version waits until the person agrees. Offline business data belongs to the offline engine (04.15).
- **ADR-133 The position is read once, on a button, after a notice; it is never followed.** A reading is taken only when the person presses the button for a punch, a report or an inspection, with the notice on the screen; there is no background tracking, and a test fails the build if the browser's continuous-watching call appears anywhere. The reading carries its accuracy and hints about whether it may be mocked; these are hints for the reviewer, not verdicts.
- **ADR-134 Web Push is done with node:crypto and only to browser vendors' push services.** The key pair (VAPID), the encrypted message (RFC 8291) and the request need no package. A subscription is accepted only if its address is a known browser push service over https, so a signed-in person cannot make the server call an address of ours or of the network (server-side request forgery); a device the service reports as gone is forgotten.
- **ADR-135 On a touch screen or a phone every control is 44 px, whatever density was chosen.** The compact density (28 px controls) is for a mouse; below 768 px wide or with a coarse pointer the controls, rows and targets stay at 44 px so a thumb can hit them (FR-05). Comfortable and compact still differ in type size and spacing. The shell's fixed layers use the design tokens' z-index scale (header and bottom navigation above sticky bars), and a form's sticky action bar rests on the bottom navigation.
- **ADR-136 One endpoint serves the widgets of every module.** `GET /ui/widgets/:code/data` looks the widget up in `ui_widgets`, checks the permission key the row names, and calls the provider the owning module registered with `platform/widgets`. The provider reads the same tables as the list behind the widget inside the same scope (`scopeFilter`) and mask rule, so a widget can never show more than the list does (BR-01). A catalogue row without a provider is not offered, and a module that is not installed offers none.
- **ADR-137 The default of a role is a maker-checker request; a person's own copy is not.** Changing what everyone of a role sees goes through the approval engine (`ui_dashboard_change`, chain SYSADM, no self-approval, the reason kept, a version check when approved so a stale request cannot overwrite a newer default). A person's own layout is theirs: it is saved at once, audited, version-checked across devices, and "Reset" gives it up for the role's default.
- **ADR-138 A layout is an ordered list flowed on a twelve-column grid, not x and y coordinates.** A place has a width (1 to 12) and a height (1 to 4); the browser flows the list (CSS grid, dense), a phone shows one column and a tablet six. Moving a place is changing its position in the list, by drag-and-drop or by the buttons, so a layout means the same on every device and the keyboard does everything the mouse does.
- **ADR-139 Charts are drawn by our own SVG components, with no chart library.** No package was added: the geometry is a few pure functions tested in Node, the colours are the design tokens (so both themes work), every chart has the same data as a table, and exports are CSV (formula-safe) and PNG (the page's resolved colours written into a copy of the SVG). A library can replace the drawing later without changing the widgets' data.
- **ADR-140 A drill-down address carries the list's filters.** `?filter[status][in]=...&filter[projectCode]=...` is the same form the list sends to the server; the List Report reads it on opening, and a filter from the address beats the working context for the same column, so the list shows the rows and the count the widget counted.
- **ADR-141 Search is SQLite FTS5 with the trigram tokenizer; the prompt's PostgreSQL `body_tsv` becomes the FTS5 table `core_search_fts`.** The database is SQLite (ADR-1). The trigram tokenizer gives substring matching, which is what people need for document numbers (`0123`, `MR/2026-27`) and pieces of names, in any script. Its limit (a word needs three letters) is covered by prefix lookups on the indexed `code_key` and `title_lc` columns and by an `instr` test for one- and two-letter words.
- **ADR-142 The index is a projection kept by events, repaired by a schedule, and never trusted for permission.** A consumer re-indexes the record each domain event names (T-02); a five-minute job indexes whatever changed without an event (the organisation's edits publish few events) and drops orphans; a rebuild per kind is the administrator's tool. Visibility is applied twice: in SQL from the person's grants (so counts and paging cannot leak) and again by reading each returned hit from its record (so a record that was removed or made private after indexing is never shown).
- **ADR-143 Sensitive values are searchable only by roles that see them in full, through a separate index.** A value with a field mask (mobile number, request total) is stored in `core_search_secret`, never in title, subtitle or body, and matched only when the caller's mask rule for that field is `show`. A partly shown value is not searchable (what is shown is not the whole value). Rationale: a search that answers "yes" to a masked number reveals it.
- **ADR-144 Names are matched by sound with a small phonetic key, not by a transliteration table of names.** Devanagari is read as Latin (a fixed table), then vowels fold together and aspirates, sh/ch/ph, w/v and double letters simplify, so शर्मा, Sharma and Sarma meet. It is the lowest-ranked kind of match before typing mistakes, so exact and partial matches always come first. It will give some false matches between unrelated names; that is the price of finding "Sarma" when the record says "Sharma".
- **ADR-145 The palette's actions are a registry, not a table.** Actions are declared by modules in code (`commandRegistry`), filtered per person by permission and feature flag, and offered first on the pages they belong to. A table would let an administrator point an action at a page the person cannot open; the navigation registry (03.05) already holds the editable page list, and its "create" shortcuts appear as actions too.
- **ADR-146 A 60-line translator instead of react-i18next.** The prompt allows "react-i18next or existing". The catalogue must also serve the server (messages, templates, the printed page) and be tested in plain Node, so it is plain JavaScript in `src/shared`, with a React store on top. It does what is needed (placeholders, plural forms, fallback to English, a report of missing keys) and adds no dependency. Replacing it by a library later changes `platform/i18n` only.
- **ADR-147 English is the source of every key; Hindi follows it, and a gap shows English, never a blank.** A test fails when a Hindi text is missing, extra or has other placeholders, so the catalogue shipped is complete; a company override cannot break that (an override must keep the placeholders and cannot be empty).
- **ADR-148 Digits stay 0-9 in Hindi.** Indian business documents and software write numbers in Latin digits; only the words (and the month names) change. Devanagari digits are a later preference if asked for.
- **ADR-149 Wording is configuration: a change is a request another administrator approves.** One open request of this kind at a time, for any number of texts, so a translator's workbook is one decision. A company's wording applies to that company only, over the built-in text; "back to the standard wording" removes the override. Text still reaches the screen through the same catalogue, so there is nothing to deploy.
- **ADR-150 The printed page is English until the PDF writer can embed a Devanagari font.** The standard PDF fonts hold Latin-1 only; embedding needs a subsetting font writer. The amount in words is printed in English; the Hindi words are available on screens and in messages (D-164).
- **ADR-151 Accessibility is tested by the engine, then by the rules we can state.** axe finds what a machine can; the spec also asserts what it cannot (focus returns to the opener, reduced motion gives instant transitions, the focus ring has an outline). Findings of moderate or minor impact are printed, not failing, so they can be worked off without blocking.
- **ADR-152 The search index and its log carry no company foreign key.** They are projections of records that carry their own; the first end-to-end run showed that a record of a company with no organisation row (every test company) could not be indexed and its event became a dead letter. The migration of part 03.08 was corrected before release and the schema baseline re-locked; a test indexes such a record.
- **ADR-153 The migration tracker is generated from the code's own list of pages and kept equal to it by a test.** The inventory of 00.01 was a snapshot; a tracker that can drift is worse than none. The client registry (`registerModule`) is the list of pages; the tracker rows are seeded from it and a test fails when a page is added without a row or a row names no page.
- **ADR-154 "Migrated" is a fact checked by a machine; "Verified" is a person's act.** The seeded rows are Migrated (each page was built on the design system by the part that created it, and `e2e/pages.spec.js` proves the checklist items a machine can prove). Nothing is seeded Verified: that is a module owner's statement after a check with a business user, made in the tracker, in their name, and never by the person who migrated the page.
- **ADR-155 An old address is a redirect row, registered by request and approval.** There is no older product, so no address has ever changed; when one does, the owner registers the old address on the page's row, another system administrator approves it, and the browser follows it with the query and fragment. A redirect can never shadow a real page (refused), and it cannot point to another site (an address must start with one slash).
- **ADR-156 Visual baselines are per platform and are renewed on purpose.** Fonts and anti-aliasing differ between operating systems, so the images are those of the Linux image the tests run on (the default Playwright naming includes the platform). A page whose content is the clock or the whole system is compared with its content masked, so the frame, colours and layout are checked and the data is not.
- **ADR-157 One engine; the stand-in stays as a mirror, per request type.** The change-request engine of part 01.03 has 18 request types, screens and tests built on its table. Replacing it in one step would change all of them at once. Instead the engine decides for a type whose flag is ON and the request row is mirrored from it, so the screens, the handlers and the API are untouched and a type can go back to the old code by turning the flag off. `ui_translation_change` is the first; a test runs the same story under both and compares every observable. The others move one at a time, and the sample material request moves with the approval matrix of 04.02, whose thresholds it needs.
- **ADR-158 The instance copies its steps; a new version is a draft that needs its own approval.** `wf_instances.steps_json` holds the steps the instance started with next to the id and number of the definition, so editing, retiring or deleting a version can never change a running approval (T-04) and the history can always be read as it happened. Activating a version is itself an instance of the engine (`WF_DEFINITION`: SYSADM, the owner of the process, ITADM), so the engine's own rules (nobody approves what they raised, one person one step) protect the chains of every other document.
- **ADR-159 A slot nobody can fill goes to the administrators and waits; it is never skipped or approved.** Resolving a step gives one slot per approver. A role is empty when, in a company that has people in the identity tables, nobody holds it for the project or site (other than the originator); a person, a manager or a resolver is empty when it names nobody or only the originator. An empty slot is a task in `ADMIN_QUEUE` with an alert and an audit entry; only `eng.workflow.admin` assigns it, to someone other than the originator, and it is then an ordinary task. In development-header mode roles cannot be listed, so a role slot is always open to its holders.
- **ADR-160 Rounds, not copies, for returns.** A document returned to its originator and resubmitted stays one instance with the next round number; the earlier tasks stay and are marked superseded so a decision of an earlier round never counts for the new one but stays in the history. A return to an earlier step supersedes the tasks from that step on in the same way.
- **ADR-161 Files of a task go through the file service.** An approver's attachment is an ordinary file linked to the task (`wf_task`), with the type allow-list, size limit and virus scan of the file service; it counts as attached only when it is clean, and `wf_task_attachments` records the ones present when the task was decided.
- **ADR-162 The matrix replaces the steps of a definition only when the definition says so.** A workflow definition (04.01) has a setting "route by the approval matrix". When it is on and `ff.eng.p0402` is on for the company, the engine takes the steps of the instance from the rule of the matrix that fits the document's facts, and copies them into the instance as it already copies the steps of a definition, so a later change touches nothing that is running. A definition made by hand keeps its own steps. The module's default definition turns the setting on, so the reference bands are the routing out of the box.
- **ADR-163 A matrix is versioned rows that take effect from a date, never edited.** A version is a draft, then pending while its chain (SYSADM, then the CFO for financial documents or the process owner) approves it, then active from its date. Resolution picks, for the document's date, the most specific scope (project, then department, then company) and in it the newest version in force. The previous version ends the day before. A draft whose rules leave a gap (a document no rule fits) cannot be activated: the check lays the rules over the values on and next to every bound the conditions name, both truth values and every named value; a rule that can never be reached is reported but allowed.
- **ADR-164 An authority limit checks the step that gives the final approval.** The bands of the reference name cumulative chains (a purchase order of ₹80 L goes to PROCMGR, PM and PD), so a limit cannot mean "skip every role whose limit is below the amount". It means: the step that ends the chain (or any step marked as final authority) must belong to a role that may approve that amount; if it does not, the step passes to the first role above it in the escalation hierarchy that has authority for the document type (a role with no limit row for the type is never chosen), and the trace says so. A role with no limit row for a type is not checked.
- **ADR-165 Escalation adds a person; it does not take the task away.** At the due time a task gets a companion task for the next level of the hierarchy, and at twice the time one for the director. Whichever of them decides settles the slot and closes the others (in a parallel-all step the companion answers for the slot it came from). Reminders, due times and the second point are worked out in working hours at the moment the task is made and stored on it, so a later change of the settings never moves a task already waiting.
- **ADR-166 Delegation is the delegator's authority for a period, recorded as such.** The delegate may decide the delegator's tasks (by name, or by a role the delegator held when they delegated) for the dates, document types and amount cap given; the record says "on behalf of". New tasks of a person who has delegated are made for the delegate. It is refused to oneself, to someone with lower clearance, to someone who raised a document waiting for the delegator, and for more than the delegator's own limit. Over 15 days (parameter) the delegator's manager approves first; until then it is not in force.
- **ADR-167 The inbox is a query of the engine, not a copy of it.** My Approvals reads the tasks the workflow engine says are mine (by name, by a role held for the document's project or site, or by a delegation) and adds what the screen needs: the time left, the amount, the project, whether the task may be approved with others. Nothing about a task is stored for the inbox, so it cannot disagree with the Workflow Instance page. Saved variants reuse the saved views of the List Report (a thin list definition `workflow.inbox`), so they are personal or shared the same way.
- **ADR-168 Evidence is read when opened, by providers the owning module registers.** `evidenceProviders.register(docType, fn)` returns sections (metrics, table, list) and risk flags. The framework adds what the approval itself knows for every type (the approver's authority, the time, the decisions so far, earlier decisions on documents with the same title in the same project). A provider that fails is reported and never stops the rest; a value marked with a field mask is hidden or partly shown by the permission engine; a type with no provider says so in words instead of an empty panel.
- **ADR-169 Bulk approval is a loop of ordinary approvals with a gate in front.** Each task is read, checked against the policy of its document type (eligible type, amount at or under the bulk limit, no risk flag, no attachment or checklist step, no question waiting, the person is the one who may decide it) and then approved through the same call as a single approval, in its own transaction; the answer lists what was refused and why. Only approval is done in bulk.
- **ADR-170 A secure link is a bearer token for one task and one person.** Only its hash is stored; it lives for the minutes the policy gives, is used once (a compare-and-set on the row), and is replaced when a new one is made for the same task. The answer for a token that is not good is always the same. Above the policy's amount the person must also be signed in as themselves (the second endpoint takes the session), which is the re-authentication. The token is shown to the approver and is in no event; delivery to e-mail and WhatsApp is for the notification service, which will call the same function.
- **ADR-171 Seeding defaults inside a transaction is not remembered until it commits.** The first read of a company's matrix, limits, hierarchy, SLA settings or approval policies writes the reference rows; if that read happened inside a transaction that was then rolled back, remembering "already seeded" would leave the company without them. The cache is filled only outside a transaction.

- **ADR-172 Control points are defined in code and owned by the company.** A module declares each control (code `CP-<MODULE>-nn`, stage, enforcement, thresholds, owner, the rule as a function) with `controlRegistry.define`; a company gets its row the first time the control is read or used and owns mode and settings from then on, so a deploy never changes a company's mode. An administrator may also write a control as data (field, operator, threshold). The rule is never SQL or code typed in a screen.
- **ADR-173 The check runs in the caller's transaction; what it found is written after it.** A blocked action rolls its transaction back, and the record that it was blocked must survive. While a transaction is open the result waits in a queue and is written as soon as the stack unwinds (and before any list that reads the log); with no transaction it is written at once. A passing check is only sampled (`eng.pcs.pass_sample_percent`); everything else is always written.
- **ADR-174 One master of reason codes, read by the old dialogs.** `pcs_reason_codes` holds the reasons per action (cancel, reject, return, reverse, deviate, override); the codes of part 03.04 were copied into it. The reason picker still calls `/ui/reason-codes`, which now reads the master and falls back to the old table only where the master has nothing for the action. A company adds its own rows or switches a shared one off for itself with a row of its own.
- **ADR-175 An exception exists only for an action a control really stopped.** The server looks for the failed check of that person on that record (the last seven days) and takes the value at risk, the project and the level from it; the client names only the control and the record. A control that BLOCKs cannot be excepted; an exception is for one action, used once, valid 30 days after approval.
- **ADR-176 Observation comes first, and relaxing a control is as serious as tightening it.** A control goes to ENFORCE only after `eng.pcs.observe_days` (14) days since it entered OBSERVE; a change of a control that is in ENFORCE, or goes to it, is a document approved by the control's process owner and then the auditor or director, so a maker cannot quietly switch a control off. OFF, OBSERVE and WARN are changed directly by the manager of controls and audited.
- **ADR-177 An emergency exception lets the action through and is regularised after.** While it waits for approval inside its window (72 hours by default) the check treats it as usable once; when the window passes, a job climbs the approval task one level (the escalation hierarchy of 04.02), tells the owner and the raiser, and the dashboard shows it. A rejection after use is recorded as `usedBeforeDecision` so the action can be corrected or reversed.
- **ADR-178 A RACI change is the whole answer for a process, not an edit of a row.** The editor sends, for each process it changed, everyone who is R, A, C or I; the server checks that exactly one is Accountable and is a person, and replaces the earlier rows from the new date (the old rows end the day before, or end where they began if they began on that date). History is kept; the answer on any date is one set of rows.
- **ADR-179 The ledger is read from the feeds, from where each stopped.** A cursor per feed (outbox events, audit trail) remembers the last row read; `sync()` runs before every read, from a job every five minutes, and in tests, so a screen is never behind. An entry is unique by company, source, source row and action, so a replay or a second reader changes nothing. A module feeds the ledger with a mapping function, not by writing into the table.
- **ADR-180 The score is arithmetic a person can check, and says what it is for.** On-time share of the timed actions, less up to 30 points for open items past their time (5 each), returns received (2 each) and rejections received (3 each). Exceptions raised are shown and do not reduce it. Every answer and export carries the sentence that it is an input to a human review (07.11), never an automatic consequence.
- **ADR-181 One `notify()`; the recipient decides what is shown.** A module names the template, the people and the facts; the engine, not the module, picks the language, hides what the person may not see, applies their choices and writes the delivery log. A notification is unique per person and source, so a replayed event notifies once.
- **ADR-182 Quiet hours hold the other channels, never the centre.** The centre is where a person looks when they choose to; a message to their phone or mailbox is the interruption. Urgent and mandatory (security, statutory) messages are never held. A held message leaves in one digest, so a night of events is one e-mail.
- **ADR-183 Socket.IO on the application's own HTTP server, replaying from a log.** The layer is attached in `listen()` so every start of the application has it; a join asks for the events after the last number a screen saw, from a log (not from memory), so a restart or a second server loses nothing inside the retention time. Events are ids only, and the guard of 02.07 is the one place that says who may be in a room.
- **ADR-184 The gateway uses the hub's webhook endpoint, not a new one.** The signature check, the replay guard and the log of inbound calls already exist in `/api/v1/core/webhooks/:connector` (01.08); the gateway consumes `core.webhook.received` and reads the provider's payload. A second endpoint would have meant a second place to get signatures wrong. The prompt's `/comm/webhooks` path is therefore not built.
- **ADR-185 Failover is per message, in the order set in Channel Settings.** A message tries the first connector and then the second in the same round; the trail of attempts is kept on the message. A rate-limited connector defers the message instead of failing it over (the second connector is for outages, not for getting round a limit). A refusal by the provider with no chance of success on retry (all connectors answered "not retryable") fails the message at once.
- **ADR-186 One-time codes live in one service; the deliverer can differ.** `comm.otp` makes, hashes, expires, limits and checks the codes for every purpose. Sign-in codes (02.01) keep sending through the connectors the sign-in policy names, by passing a `deliver` function; the message is still written to the log, with the code replaced. The code is never returned by an endpoint and the stored text of a code is wiped after sending.
- **ADR-187 The gateway is in the path of notifications only when its flag is on.** With `ff.eng.p0407` off, 04.06 behaves as before, so the flag can be turned off without losing messages. Messages the gateway refuses (no opt-in, DLT mismatch) are skipped in the delivery log with the reason, not retried.
- **ADR-188 A failed message keeps its text until retention, a code does not.** "Send again" needs the text; a failed code is asked for again by the person. Everything else in the log shows the text with token-like values replaced.
- **ADR-189 Routing names a person the matrix and the data can defend, and says how it got there.** The employee is, in order, the person the RACI names as responsible for the topic's process, the holder of the role with the fewest open tasks, the row's fallback person, the head of the department. Each step that fails is written in the routing trail kept on the task, so a reviewer sees why it went where it did. A missing mapping is not an error for the sender when the department is known: the task goes to its head, who places it (FR-03). With no department either, the instruction is refused, because a task that goes to nobody is worse than one that is not made.
- **ADR-190 Escalation climbs the path of 04.02 and adds watchers; it does not reassign.** The person who is late keeps the task and stays responsible; the people of the next role (and later the top) are made watchers, told, and recorded on `tsk_escalations`, one level at a time (after 1 and 3 days late by default). Moving the work is a decision for those people, taken with the Reassign action.
- **ADR-191 Closing is a separate step from doing.** Completing a task that needs verification waits for the person who gave it; verification is by them or a delegate under 04.02, never by the person who did it, and closes the task. A task that needs no verification closes when it is completed. A finished task can be sent back with a reason.
- **ADR-192 Parameters are read through a store of their own for each read.** The settings are changed through the API's store, whose cache another store cannot see; a long-lived store in the engine would keep the old value until restart. The gateway of 04.07 had the same fault and is changed too.
- **ADR-193 A rule looks at what a module offers, not at its tables.** A module registers a dataset (`alertDatasets.register`) with its fields and a read function; rules name the dataset and compare its fields. This keeps the rule engine from reaching into other modules' tables (section 11) and lets a module change its storage. The library lists the rules for modules that are not built yet; they can be adopted but not switched on until the dataset exists, so nothing is silently "on" and doing nothing.
- **ADR-194 One decision for the run and for the dry-run.** For each match the engine decides NEW (no alert yet, or the last one is resolved and the window has passed), REPEAT (an open alert whose window has passed: the same alert is counted again and the people told again) or THROTTLED (inside the window, even if resolved: a resolved alert does not come back at once). The run and the dry-run call the same function, which is what T-02 checks. A throttle window of 0 raises every time.
- **ADR-195 Only a rule that sends something outside is approved.** The prompt asks for approval of rules "affecting external messages": a webhook, or a notification by e-mail, text message or WhatsApp. Everything that stays inside (the alert centre, the notification centre, a task, an escalation to a role) takes effect when saved, with an audit entry and a version. A rule waiting for approval is not in force and the previous version (if any) keeps running; the rule's creator cannot approve it.
- **ADR-196 Approval supersedes in the same transaction; the watermark is made at download.** The approver's decision makes the new revision current and the old one superseded together, so there is never a moment with two current revisions (BR-01). The stored file of an old revision is never changed; the watermark is stamped on the copy that is sent (pdf-lib for PDF, sharp for images), so a revision that becomes superseded needs no rewrite and the original stays intact for audit.
- **ADR-197 One visibility function for every way to reach a document.** The register, the search entity, the file service, the zip, the viewer and the export all ask the same code whether this person may see this document (project scope, confidentiality, explicit share). A confidential document is therefore absent from a search result rather than shown with a blocked link (BR-03). A person who made a confidential document but lacks `doc.document.view_confidential` finds it in the register (as owner) but not in the search; this is kept deliberately simple and noted as D-232.
- **ADR-198 Types and folder templates change by approval.** They decide who approves every document, so a change is proposed, approved by the workflow engine and only then takes effect; the previous version keeps working meanwhile. Only one proposal may wait at a time, so approvers see one coherent change.

- **ADR-199 The PDF is drawn by a built-in renderer, not a browser.** Templates are written in a controlled subset of HTML and CSS (no scripts, no outside resources, no variables in tags), so a renderer of the subset on pdf-lib (text wrapping with IBM Plex, the Devanagari and rupee fallbacks, tables with repeated header rows and column spans, boxes, rules, images, header and footer on every page) gives the same pages on every machine and needs no Chromium in production. The cost is that CSS outside the subset (flex, grid, floats, web fonts) is not drawn; the editor says so (D-235). WOFF fonts are unpacked once with the native zlib and parsed once per process, which brought a document from about 425 ms to 55 ms.
- **ADR-200 The standard formats are written once, in code, and are ACTIVE shared rows.** The 19 formats of the library come from `tpl-library.js` and the variable catalogue, so a change of a variable and its formats is one change; the module writes them as shared `tpl_templates` rows (company empty, version 1, approved by `system`) when it starts, and a company changes one by making its own version, which goes through maker-checker. A format the catalogue rejects stops the module from starting.
- **ADR-201 Totals are never taken from the caller.** `compute` rebuilds every derived figure (line tax, CGST and SGST or IGST by the state codes, round-off, grand total, payslip net, amount in words) from the lines with exact decimals; a total that the caller sent and that differs is refused with `TOTALS_MISMATCH`. The PDF prints the recomputed figures, so it always agrees with the stored record.
- **ADR-202 An official document is immutable in the database.** Triggers refuse a change of the file, hash, number, version, template or code, and any delete; only the marks `is_current` and `superseded_by` may change. A new generation is a new version with a reason, and the QR code of an old version says it was replaced. The data of a record that already has an official document cannot be changed without a reason.
- **ADR-203 Until a module owns its data, its approved data is handed over as a record.** `tpl_records` and `registerTemplateSource` are the adapter: a module publishes the approved data of a document (or registers a source that reads its own tables) and never calls the renderer. Only approved, non-sample records are printed officially; the editor previews with the catalogue sample or any record.
- **ADR-204 A signature is a row beside the document, never a change to it.** The generated PDF keeps its hash for ever (ADR-202). A signature stores that hash, the signer, the time and a digest chained to the previous signature of the document, so a changed or removed row breaks the chain (the database also refuses to change or delete one). The signature picture and the words of an electronic approval are drawn on a stamped copy made from the original and kept as a copy; the check accepts the original or any copy by its hash.
- **ADR-205 The public check shows only configured fields.** Whatever the settings, the answer is genuine, superseded, cancelled or not found, with the date; the facts that come with it (type, number, issuer, version, date, signers, project, amount) are a company setting changed by an approved change (the administrator proposes, a director approves). An amount is never shown for a payslip or an offer letter. A file is compared by sha256 and a mismatch is a security event.
- **ADR-206 The workflow approvals sign by themselves.** When a document's workflow is approved, or its document is generated after the approval, each approver becomes an electronic approval signature with the time of the approval (an event consumer, once for each approver); the stamped copy is drawn by a job.
- **ADR-207 One engine, many adapters.** A module registers an import type (columns with type, required, lookup and validation; the key columns; how to find an existing record; its own row rules; how to create or update a record through its own service; optionally an export). The engine owns the template, the upload, the check, the preview, the commit and the history. No import writes to another module's tables: a row becomes a record only through the owner's service, so every rule, right, control point and approval of typing the record by hand applies (BR-01). An imported record that needs approval is sent into its chain (draft or submitted) and is never approved by the import.
- **ADR-208 A nested transaction is a savepoint.** `transaction()` used to refuse to start inside another. A bulk import must be one transaction around many calls to module services that have their own, so a nested call is now a savepoint: undone if it throws, kept or undone with the outer transaction. Nothing relied on the old error. A commit is all or nothing, or one transaction for each chunk with the count of rows saved kept for the resume.
- **ADR-209 The file is read twice, and the commit checks again.** The check runs as a job after the upload and writes the errors and the action of each row; the commit reads the stored file again and checks it again inside its job, because the data may have changed since the preview (a code taken meanwhile). If new errors appear nothing is committed and the job goes back to the preview. A background job acts with the roles and identity of the person who uploaded or committed, kept with the job, so it never has more rights than they had (`actor_json`).
- **ADR-210 Formulas are refused coming in and made inert going out.** A cell that holds a formula (an `f` element) or a text that starts with = + - or @ (a number such as -5 is not one) is an error at its row and column; every writer (templates, error files, exports) writes such text with a leading apostrophe. Only .xlsx is accepted (no macros, no CSV).
- **ADR-211 The record is reached only through the object type registry.** Comments, the timeline and the trace never read a module's tables for access: they ask the registered type (`access` with the person's own scope). A module that registers its type gets the three tabs and the feed with no code of its own. Two optional hooks were added to the contract, `summary` (label, status, amount) and `projectRecords` (for the feed). The sample document of the workflow engine was registered as `sample_doc` as the second reference record (the first is the sample material request).
- **ADR-212 A mention is checked against the named person, not the author.** Before a comment is posted every `@username` is resolved to an active person, that person's own actor is built with their current grants, and the object type is asked whether they could open the record. If any cannot, the whole comment is refused with a message naming them (BR-01); a name that is not a person is ignored. Mentioning oneself notifies nobody. A reply notifies the author of the comment replied to, unless that person was also mentioned.
- **ADR-213 The timeline is composed when it is read, from the tables that already hold the facts.** No copy of events is kept (a copy would drift and would need its own access rules). Each source is read with a cap of 600 rows, times are normalised (ISO and SQLite styles), the type's `maskEntries` masks audit values, messages need `comm.log.view`, documents are filtered by their confidentiality against `doc.document.view_confidential` and `view_restricted`. The project feed first resolves the records of the project through the registered types and only lists those the person can open.
- **ADR-214 Trace links are facts written by services; a person may add one only with a reason.** An active pair (from, to, relation) is unique; writing it again is harmless. A link written by a service can never be removed by hand; a link made by hand needs a reason of ten characters or more (also a database check), is audited and can be removed with a reason. The graph is walked up and down separately (a loop does not run for ever), to a depth of 1 to 8 and at most 200 nodes; a record the person cannot open appears as "Restricted record" with no id, label or route. Modules ask for a link by publishing `col.trace.requested`, or by calling the service.
- **ADR-215 The settings are platform parameters, not a table of our own.** The edit window, the longest comment and the reactions switch are parameters (`col.comment.edit_window_minutes`, `col.comment.max_length`, `col.reactions.enabled`) with limits, company scope, a mandatory reason and the audit trail of the parameter engine (02.05). They apply at once.
- **ADR-216 A command is a fact with its own id; the server never guesses.** Every offline change is a command with an id made on the phone, an order number, the form, the values and the time on the device clock. The server keeps one row for each id (unique), so the same command N times is one record and the answer to a replay is the first answer. A command from another person with the same id is refused. A command that depends on a record an earlier command makes waits (`DEFERRED`, `retry`) and is applied when it is sent again, whatever order the batches arrive in; within a batch the order number decides.
- **ADR-217 Conflicts are decided field by field, by the person, never silently.** An update carries the version it started from and the old value of each field it changes. The server compares: a field that only one side changed merges by itself; a field both sides changed to different values is a conflict that holds the old, the person's and the server's value. Nothing is applied until the person chooses keep mine, keep the server's, or a side for each field (or a typed value). The choice is audited with the server values it replaced.
- **ADR-218 The local copy is encrypted with a key the page cannot read, and goes when the person goes.** AES-GCM through WebCrypto, one non-extractable key for each person on the browser, kept beside the data; signing out (after a warning about unsent work), a revoked answer or the explicit wipe deletes the database. A token that merely expires (the phone is offline) does not delete queued work; it locks the cached masters and forms after `expiresAt`, and the queue is sent after the next sign-in.
- **ADR-219 Old work needs a second person.** A command whose corrected time is older than `off.command.max_age_days` is held (`NEEDS_CONFIRMATION`) and saved only when a supervisor with `off.sync.confirm` for the project confirms it; it is applied with the rights of its author, the author cannot confirm it, and a decline leaves nothing behind.
- **ADR-220 The server's clock is the clock of record.** Each sync measures the device clock against the server's; a command's `effective_at` is its device time minus that difference, the device's own time is kept beside it, and a difference above `off.clock.max_drift_seconds` warns the person.
- **ADR-221 One thread index; the old stores are read in place, never moved.** `msg_conversations` indexes every conversation. The conversations made here live in `msg_*`; the external threads (WhatsApp, e-mail, SMS) of the gateway are indexed from `comm_messages` by their `conversation_key` and their messages are read from that table, so nothing is copied, renamed or deleted (BR-03). `GET /msg/verify` shows, for the gateway store, the number of threads and messages and a checksum of (thread, count, last id) at the source, in the index and as read, which must be equal. The record discussions (`col_comments`, `ui_record_comments`, `tsk_comments`) are different things (a record's own Discussion tab) and are listed as kept in place.
- **ADR-222 Membership is the only door, for the API and the socket alike.** A conversation is open to a member (and an external thread to whoever may read the communication log). `conv:<id>` rooms use the same check through `realtimeConversations`, so a person who is not a member cannot join, and one who leaves stops receiving at the next event. Project, site and department channels are automatic: a person's active assignments are compared with the channels of the company whenever they list or open conversations, so the first screen after an assignment is made already has the channel, and the person leaves it when the assignment ends (a member added by hand stays until removed).
- **ADR-223 A record card is drawn for the reader, not for the sender.** A message stores only the record type and id. Each reader's card is made when they fetch the message, through the object type registry with their own rights: label, status and amount for those who may open the record, "Restricted record" for the rest. A sender cannot link a record they cannot open.
- **ADR-224 Deleting is replacing, and the words are kept only as long as policy says.** Inside the edit window the sender replaces a message with "message deleted" for everyone; after it, only an administrator of the conversation can, with a reason. The text stays in the row and the audit trail for `msg.deleted_content_retention_days` and the job `msg.purge` then blanks it. Editing and deleting are open for `msg.edit_window_minutes`.
- **ADR-225 Files go through the file service as the conversation's files.** A person uploads to the entity `msg_conversation` (members only), and a message may attach only files that this person uploaded to this conversation. Voice notes are such files. Forwarding copies the words and record links, not files.
- **ADR-226 Receipts, presence and typing are per person, private by choice, and transient where possible.** Receipts are rows per (message, person); delivered and read are set by the person's own client. A person may stop sharing read receipts and last seen, unless the organisation enforces receipts in the Messaging Settings. Typing and call signals travel as transient socket events and are never stored or logged; presence is a heartbeat (online under 60 seconds, away under 5 minutes).
- **ADR-227 What was said while a person was out is never shown to them.** Membership periods (`msg_member_periods`, kept by triggers on `msg_members`, backfilled) bound history, search, gallery and starred lists; a member who is removed and added again does not see the gap.
- **ADR-228 Edit and delete windows, delete for me, and legal hold.** Edit and delete-for-everyone windows are settings (15 minutes by default); delete for me hides one message for one person (`msg_hidden`). A legal hold on a conversation keeps every message, including deleted text, and makes the purge job skip it; placing needs `msg.legal_hold.manage`, releasing needs another person with a reason.
- **ADR-229 Calls are WebRTC mesh signalled through the server, never recorded.** Up to four people (setting); STUN and TURN servers from the settings, TURN credentials short-lived (coturn REST style, HMAC-SHA1 of expiry and user); an external provider may replace it with an https link. Recording is not possible: the setting is fixed to OFF and refused otherwise (BR-02).
- **ADR-230 Messaging Settings are an approved, versioned configuration.** Windows, retention, limits, receipt policy and call provider change only through a maker-checker workflow (`MSG_CONFIG`), effective from a date, with a mandatory reason and history; the TURN secret is masked on read and kept when unchanged.
- **ADR-231 The Signal library is not used; secure conversations use the platform's WebCrypto API in protocol `erp-e2e-v1`.** libsignal and Signal-Server are AGPL-3.0 (network copyleft), which the licence review (`docs/erp/LICENCE_REVIEW_05.03.md`) proposes to reject. The permitted alternative, Olm/Megolm (Apache-2.0), is not needed: `src/shared/e2e.js` only composes ECDSA and ECDH P-256, HKDF-SHA-256, AES-256-GCM and SHA-256 of the browser and Node.js, so no primitive is written here. It is not Signal: no double ratchet (D-276).
- **ADR-232 The gate is in the code.** Registering a device, starting a secure conversation and switching the policy on all refuse until the licence review of the end-to-end implementation is approved (ITADM, then DIR) and the policy, itself an approved change, is on. The review's decisions are written into the register only by the approved workflow.
- **ADR-233 The server is a relay of ciphertext.** One envelope per receiving device (sender signature, wrapped content key, ciphertext); a send must include every active device of every member except the sender's, else 409 with the devices expected; when a device has fetched its envelopes the ciphertext is emptied and only delivery metadata stays for the policy's days; secure messages are never rows of `msg_messages`, so search, export, hold and AI cannot reach them. A secure conversation is a `GROUP` of the unified index flagged by `sec_conversations`, with its members fixed at creation.
- **ADR-234 Safety numbers cover the set of a person's devices.** The 60 digits are derived from the sorted device fingerprints of both people, so adding or revoking a device changes the number; each browser remembers what it accepted and holds the next message back until a change is accepted. A lost device is revoked by its owner or the IT administrator; what was only on it cannot be recovered, by design.
- **ADR-235 Auto groups are rules, kept by a sync that runs on the event and every minute.** Rules (`msg_auto_group_rules`, versioned, changed only by an approved change) say which project, site, department, team and discipline groups exist and which roles belong; `sync` makes the groups, adopts the ones made by hand in 05.01, adds and removes only members it made (source AUTO) and says so in a system message. An assignment event runs it at once; the job `msg.comcenter` runs it every minute (T-01).
- **ADR-236 An instruction is a message with acknowledgements.** The sender (right `msg.instruction.send`, checked in the project or site of the conversation) marks an own message; the other members at that moment are the recipients (`msg_acknowledgements`); a due time is required so that it can escalate; high and urgent ones are acknowledged one by one, never in bulk. At the due time the people who have not acknowledged are escalated to the managers above them on the escalation path (04.02), the sender and the group are told, and a late acknowledgement still completes it. `msg.instruction.acknowledged` feeds performance (07.11).
- **ADR-237 Announcements go to an audience resolved at publish time.** Places (projects, sites, departments) narrow it, roles narrow it further, "everyone" and roles alone need company-wide rights; the recipients are fixed when it is published (reads are rows), read is recorded when opened, a quiz must be answered right to confirm, expiry closes confirmation.
- **ADR-238 Message to action goes through a registry; only the task is live.** A module registers the kind of record it makes; the others (RFI 11.02, NCR 18.04, site instruction 14.04, material request 15.01, HSE observation 19.04) are listed as not live and refuse with 409. The task is made with the platform task core after the task module's permission rules, attachments are copied by the file service (`copyTo`, new storage key), and the link back is a trace link requested by event.
- **ADR-239 A flagged conversation escalates to managers and a direct one stays private.** Unresolved after the chosen hours, the raiser's managers on the escalation path are told and, in a group, join it; in a direct or secure conversation they see only the reason.
- **ADR-240 A policy is a register row with versions; only a version is edited, approved and read.** `pol_policies` holds the identity (number, title, category, owner, department) and the status shown in the register, derived from the versions: Draft, Published (approved, not yet effective), Active, Under revision (a newer version is being written or approved), Archived. A version is Draft, In approval, Rejected, Published, Active, Superseded or Archived. A published version is never edited (BR-01): a revision is a new draft version made from the one in force and goes through the approval again; the version it replaces is superseded and kept, read-only, for the people who had it.
- **ADR-241 Approval is the workflow `POL_VERSION`: department head, then director.** The first step is the heads of the policy areas (HRMGR, CFO, QCMGR, PROCMGR, ACCMGR, COMMGR, PCMGR, HSEE), the last the director; the owner cannot approve their own policy (distinct approvers). The default chain is also seeded in the approval matrix (04.02). Return gives the draft back to its owner; rejection ends the version.
- **ADR-242 Applicability is a union and is resolved when it matters.** A policy applies to everyone, or to anyone in the listed departments, holding the listed roles, or assigned to the listed sites and projects (any of them). The recipients are resolved at publication (rows in `pol_acknowledgements`, notified, with a due date) and again every hour, so a person who comes into scope later gets the policy too.
- **ADR-243 Acknowledgement is tracked here, announcements of 05.04 are not used.** The acknowledgement must belong to a version, carry a quiz score and a pass mark, and feed HR and performance (`pol.acknowledgement.recorded`), which the announcement tables cannot do. Reminders every three days (at most five), escalation once at the due date to the owner and the managers on the escalation path, review reminders 30 days before and when overdue.
- **ADR-244 Policy-to-protocol drafts are written by the engines, through a registry.** A module that owns an engine registers how a requirement becomes a draft in it (`policyDrafts`); the policy module calls it and never writes into the engine's tables. A draft is inactive by construction: a control point that is OFF, an approval matrix that is a DRAFT version (the new rule first), an alert rule that is switched off. Only the requirements of an approved version are converted; the administrator reviews and activates the draft on the engine's own screen and through its own approval (BR-02).
- **ADR-245 Governed masters are a registry plus a framework-kept record store.** A master registers its fields, unique keys, fuzzy field, financial flag and default rules in `masterTypes` (`platform/mdm`); its records live in `mdm_records` with every version in `mdm_record_versions`. The first master is the business partner (AC-01); 06.04 extends the same type. A later master that keeps its own table can use the same change requests, duplicates, merge map, rules and stewards.
- **ADR-246 Every change is a change request; only non-sensitive changes by an editor apply directly.** New records, sensitive-field changes (PAN, GSTIN, bank, IFSC), inactivation, reactivation and merges go to workflow `MDM_CHANGE`/`MDM_MERGE`: the stewards of the master (resolver `mdm.steward`), then the accounts manager when the master is financial (step condition `financial = true`). A change of other fields by someone with `mdm.record.edit` (or a steward) applies at once, audited, from its date. One open request per record.
- **ADR-247 Duplicates: identical PAN/GSTIN block, identical mobile and similar names warn.** Name similarity is the Dice coefficient of letter pairs after removing company suffixes (Pvt Ltd, LLP, M/s…); the same words in another order score 100; the PARTNER threshold is 85. A warning must be confirmed by the person; the pair is recorded in `mdm_duplicates` and found again by the hourly scan.
- **ADR-248 A merge is a pointer, never a delete (BR-01).** An approved merge writes `mdm_merge_map (from → to)` and marks the merged record MERGED; `resolveId`, `assertSelectable` and the `mdm_record` object type follow the map, and references (tasks, trace links) are shown under the survivor. Nothing in other modules is rewritten.
- **ADR-249 Effective dating by versions with a date; "as of" picks the latest approved version whose date has come.** Past dates are refused; a future-dated approved version is SCHEDULED and the hourly job `mdm.cycle` brings it into force. Quality rules and stewards are versioned configuration changed only by `MDM_CONFIG` (SYSADM proposes, ITADM or DIR approves); the built-in rules of the master apply until a configuration exists.
- **ADR-250 Common masters: a table per master, system rows plus company rows.** Each common master has its own table (as the prompt proposes; other modules join to them and the tax engine of 23.07 reads them) and one generic engine over a definition per master (`modules/mdm/common.js`). A row with no company is a system row every company sees; a company's change of it creates the company's own row with the same key, which replaces the system row for that company only. Seeded statutory values are a starting point an accounts manager reviews.
- **ADR-251 Statutory masters are dated and change only by approval (BR-01).** GST rates, HSN/SAC codes and TDS/TCS sections keep every version with `effective_from`/`effective_to`. A change is a pending row from a date (today or later, after the current row) and a row of the 06.01 change requests table, approved by another accounts manager and then the CFO (workflow `MDM_TAX_CHANGE`, also in the approval-matrix defaults). Approval ends the company's previous row the day before. The rate for a document is the row valid on its date, the company's row first. Import and the API go through the same proposal.
- **ADR-252 Units convert through their category's base unit (BR-02).** A unit has a category, a base unit (its own code for the base) and a factor to the base; a conversion is from-factor ÷ to-factor computed exactly, so a pair and its reverse multiply to 1. The calculation engine's `core_uoms`/`core_uom_conversions` are written from the master (generic units only; item factors stay in 06.03).
- **ADR-253 Lookup lists are served through the 03.02 lookup contract by a lookup family.** `lookupRegistry.registerFamily` lets one module answer any lookup name, so `/api/v1/mdm/lookups/<list>` serves every configured list. The label follows the person's language (`ui_user_preferences`, then the user profile). A value is never deleted: the Lookup List Manager makes it inactive.
- **ADR-254 Items are versioned rows; the selector offers the version in force.** An item is a code with one row per version (`code` + `version_no`, `supersedes_id`, `effective_from`/`effective_to`). A new item and a new version are requests approved by the steward of the category (workflow `MDM_ITEM`, one conditional step per steward role: PROCMGR, STOREMGR, EST, PLANTMGR; the requester never approves). Approval supersedes the previous version the day before and moves the migration map to the new row.
- **ADR-255 Categories are copied from a system tree into each company.** The seed holds a system tree with attribute templates; the first time a company opens the catalogue it gets its own copy, which it then changes (template, prefix, steward, default HSN). Items point to the company's categories only.
- **ADR-256 Item codes come from a counter per category and company.** The numbering service of 01.03 numbers document types and needs a series per company set up by the administrator; item codes are `PREFIX-00001` per category, from `mdm_item_code_counters` (one atomic UPDATE … RETURNING). A manual code is allowed only when migrating an old material (`mdm.item.migrate`).
- **ADR-257 Item conversions live in the calculation engine under `CODE@company`.** The engine's conversion table is shared by the companies and keyed by item code; the item master writes an item's units there as `CODE@companyId`, so two companies may number items alike. A migrated conversion keeps its old code and its old rows, so old references still convert.
- **ADR-258 Old free-text materials are mapped, not rewritten (FR-08).** `mdm_item_legacy_map` links an old code or sample-request line to an item; the old records keep their text. Where used reads the map and the lines the selector writes (`CODE name`).
- **ADR-259 Modules can put their lists on the List Report.** `listExports.register(code, { source, hidden })` lets the export service and list description of 03.03 serve a list another module defines (`mdm.items`): saved views, column chooser and XLSX/CSV/PDF export with the rate hidden from roles without `mdm.item.rate.view`.
- **ADR-260 The business partner master has its own tables; the 06.01 PARTNER type stays the governance pilot.** A partner needs several GSTINs, addresses, contacts, bank accounts, documents and roles, an encrypted bank number and its own statuses, which the generic versioned records of 06.01 do not hold. 06.04 keeps them in `mdm_partner*` tables and reuses the 06.01 formats, similarity and masking. The 06.01 records of type PARTNER are not migrated (D-306).
- **ADR-261 The steward follows the roles.** Vendors, service providers and transporters are kept by the procurement manager; subcontractors, labour contractors, clients and consultants by the commercial manager; business development registers client-only prospects. Activation (`MDM_PARTNER`) has one conditional step per steward role and then the accounts manager; the requester never approves.
- **ADR-262 A bank account number is encrypted with the vault of 04.07.** AES-256-GCM bound to the company and partner, a SHA-256 hash for duplicates, the last four digits for display. Only `mdm.partner.bank.view` (ACCMGR, CFO) shows the full number, and each view is in the audit trail.
- **ADR-263 A bank change is confirmed by the partner before it is approved.** The change holds payments at once. A one-time code goes to the registered primary mobile (or a call-back to a number registered before the change is noted). Then the accounts manager and the CFO approve (`MDM_PARTNER_BANK`). Approval starts a cooling-off period (parameter `mdm.partner.bank_cooling_off_days`, default 3) during which payments stay held.
- **ADR-264 Who may be chosen is answered by the partner master.** `selectable(partner, { purpose, role })` refuses a partner that is not active, and for a PO, work order or RFQ one with an expired document of a type the company lists in `mdm.partner.blocking_documents`; for a payment one whose payments are held. The lookups offer active partners only. Later modules call it and register what they hold in `partnerActivity`.
- **ADR-265 The chart of accounts is a template copied into each company.** The seed holds a chart for an Indian construction company (30 groups on the lines of Schedule III Division I, 43 ledgers with the control accounts, dimension rules, 22 cost heads and 18 cost codes) in rows without a company; the first time a company opens its chart it gets its own copy, which it then changes only through approved changes. The default item category mappings are copied with it.
- **ADR-266 Every change of the finance masters is approved before it applies.** A new or changed group, account, cost head, cost code or mapping, a block or an unblock, and an import are written to `fin_master_changes` and go through `FIN_MASTER_CHANGE`: the accounts manager first when the project controls manager proposed it, then the CFO; the maker never approves. The change is checked when proposed and again when applied (the chart may have moved); a change proposed against an old version is refused at approval. Only an unused account (no postings, not a control account, not used by a cost head or mapping) is deleted directly by the accounts manager, with the audit trail.
- **ADR-267 Postings are counted through a registry.** There is no ledger yet; `accountPostings.register({ code, count(db, companyId, accountId) })` lets the general ledger and the sub-ledgers say how many postings an account has. An account with postings keeps its nature, type, normal side and control setting and is blocked instead of deleted (BR-02).
- **ADR-268 One posting check for every module.** `validatePosting(companyId, { accountId | accountCode, source, dimensions })` answers whether a line may go to an account: active, a control account only from the posting engine unless manual postings are explicitly allowed (BR-01), mandatory and not-allowed dimensions, values that exist in the company, a site of the posting's project. `POST /fin/postings/check` exposes it for forms. The import from Tally maps the Tally groups (Sundry Creditors, Duties & Taxes, Bank Accounts …) to the groups of the chart and becomes one change for the CFO; ledgers whose group is not known are listed and left out.
- **ADR-269 The finance masters are a module of their own (`fin`).** The chart is the first master of finance; later finance parts (general ledger, payables, receivables) live in the same module. Its pages are under `/finance/…` in the navigation group Finance. The flag keeps the name the prompt gave it, `ff.mdm.p0605`.
- **ADR-270 A rate analysis is priced by two formulas of the calculation engine.** `ra.line_amount` (quantity per basis × (1 + wastage %) × rate, rounded once to paise) and `ra.unit_rate` (water and electricity on the direct cost, overhead on cost, profit on cost plus overhead, then contingency, insurance and escalation on that subtotal, each rounded to paise; ÷ basis quantity; GST on the unit rate when added) are built-in formulas, version 1, protected against drift. The order of the add-ons is the formula: a company that needs another order makes a new version of `ra.unit_rate` through the engine's own draft, test and approval flow, and analyses keep the version they were calculated with (`formulas_json`). The service recomputes at every save, recalculation and submit; a client total that differs is refused.
- **ADR-271 The new formulas have golden outputs and a hand-written twin.** `golden/outputs/calc.ra_line_amount.json` and `calc.ra_unit_rate.json` were captured when the formulas were added (the hand-calculated M25 example of T-01 among the cases); `tests/helpers/legacy_calcs.js` holds the same calculation written out with the money helpers, and the engine must match it on every case (as for the four earlier formulas). With no wastage `ra.line_amount` reproduces the golden BOQ line amounts (FR-07). The four earlier golden files are unchanged.
- **ADR-272 Templates are definitions in code, matched to the company's items.** A template (M25 and M20 concrete, brickwork, plaster, reinforcement, earthwork) lists components by kind, a key word, unit, quantity and wastage. Starting from it picks the first active item of that kind whose name contains the key word and counted in that unit, and its library rate; a component that does not match stays a typed line. Nothing about a template is stored but its code on the analysis.
- **ADR-273 A rate analysis is versioned by amendment.** An analysis has a number (`RA-00001`) and versions; a version is DRAFT, then in approval, then released (APPROVED). A released version is never changed (BR-02): amending it makes a new draft version with the same components, which on approval supersedes the released one from the day before its own start. `releasedRate(companyId, workItemId, { region, projectId, date })` gives estimation, BOQ pricing, budgets and variations the rate in force: the project's own first, then the region's, then the standard library's.
- **ADR-274 Project analyses are scoped by the permission engine; the standard library is company-wide.** A project-specific or variation analysis (and a project rate in the library) is seen by those whose grant of `mdm.analyse.view` covers its project (`scopeFilter`/`check`); standard analyses and general rates are seen by everyone who holds the permission. Its approval goes to the project manager of that project (the workflow takes the project from `describe`).

- **ADR-275 An employee has two statuses.** The record (`record_status`: Draft, Submitted, Approved, Returned, Rejected, Cancelled) is approval-controlled by the workflow `HR_EMPLOYEE`; the employment status (`employment_status`: Active, Notice, Separated, Absconding) is separate and changes only by an approved, effective-dated request (`hr_employee_changes`, type SEPARATION). After approval the record is locked: personal data, statutory, bank, employment and status changes are requests approved through their own chains and applied on their effective date by the approval itself (date today or past) or by the daily job (later date). This keeps "approved records are locked" (standard section 7) without freezing a person's life.
- **ADR-276 Statutory identifiers are encrypted or reduced at write time.** PAN is encrypted with the vault of 04.07 and stored with a salted hash (duplicates) and its last four characters; the Aadhaar number is never stored: only its last four digits and a salted hash (standard section 13, DPDP Act purpose limitation); bank account numbers are encrypted with a hash and the last four digits; the payload of a statutory or bank change is encrypted too. UAN and ESIC numbers are stored as typed and masked for others. HR, payroll and the employee see them; every full account view is audited.
- **ADR-277 Who sees whom.** `hr.employee.view` is company-wide (HR, payroll, director, auditor). `hr.employee.team.view` (every internal role) gives the people in the viewer's reporting line (the manager chain, recursively) and the staff deployed to the projects and sites of the viewer's scoped assignments (`scopeFilter`; a company-wide grant adds nothing here), approved records only, basic data. The person sees their own record without any permission (`/employees/me`, `permission_key = 'self'` in the navigation registry); the employee may ask for a change of the limited fields only.
- **ADR-278 "HR executive" is the maker; there is no new role.** The catalogue (06) has no HR executive. The maker is any holder of `hr.employee.create`/`edit`/`submit` (HRMGR); the checker is another HRMGR (`distinctApprovers`, the creator never approves). The chain stays configurable in the approval matrix; a separate role can be added later without code change. Recorded as D-317.
- **ADR-279 Access is removed through user management, and failure is visible.** On the effective date of a separation or absconding the employee master calls `userAdminOf(db).deactivate` with the system as actor (the manager's account as successor when open items need one). When that fails the employee keeps "Access was NOT removed: <reason>", the HR overview raises it as an error and the HR worklist lists it, until someone removes the access in User Management. It never silently succeeds.
- **ADR-280 The headcount plan is an adapter, and no plan means beyond the plan.** Until 17.08 the approved headcount is a row per department (and optionally designation and project) in `hr_headcount_plans`, dated, set by HR with a reason (the old row ends the day before). A requisition is within the plan when people in post plus the open positions of other approved or submitted requisitions plus this one stay within it; a department with no plan has nothing approved, so the requisition is beyond it and the director also approves (BR-01). It is recomputed on the server at submit.
- **ADR-281 Interview feedback is given once by each panel member.** The panel is named users; only they give feedback (permission `hr.interview.give`), once, scores 1 to 5 per criterion and a recommendation. When all have given theirs the interview has its score (the average of the averages) and its result: a fail from anyone fails it, all passes pass it, otherwise hold. A candidate is Selected only after a passed last interview and no failed one. A panel member and the hiring manager see the candidate's basic data, never the pay asked.
- **ADR-282 The offer link carries a secret that is stored only as a hash.** Sending an approved offer makes a link with 24 random bytes; only its SHA-256 is stored and the link is shown once to HR (no e-mail or SMS connector yet, D-320). The public routes need no sign-in, are rate limited, answer once (accept or decline), lapse on the valid date (the daily job) and a decline closes the link. After acceptance the same link takes the pre-joining details, whose sensitive part is encrypted.
- **ADR-283 Rejected candidates are kept for a limited time.** `hr.candidate.retention_months` (12) after a rejection or a declined offer the daily job replaces the name, contact details, pay, details and resume reference with removal markers and records it in the audit trail (DPDP Act purpose limitation); the stage and the source remain for reporting.
- **ADR-284 Revisions instead of edits for requisitions and offers.** An approved requisition or an unanswered approved offer is changed by an amendment: a new revision with the same number, approved again; the approved one stays in force until then and becomes Superseded. Candidates belong to the first revision (the root), so they follow the requisition through its amendments.

- **ADR-285 An approved deployment gives access through a grant source, never by writing into the assignment tables.** The permission engine reads role holdings from the stored role list, the assignment table and elevations; 07.03 adds a fourth input, `grantSources` (`platform/authz/grant-sources.js`): a module registers `(db, { companyId, userId, today }) => [{ roleCode, scopeType, scopeIds, via, ref }]`, and the engine adds those holdings to the person's resolution (cached with the rest, dropped by `invalidate()`, a failing source gives nothing). The deployment source returns the access role of every approved deployment that covers today for the employee linked to the user, scoped to the site (or the project when it names no site), only for an employee in service. The messaging auto groups ask the same question from the place through `holderSourcesOf`, and `hr.deployment.changed` re-syncs them at once. So an approval, an amendment, a closure, a start date and an end date change access without 07.03 touching an `iam_*` table. The roles a deployment may give are the parameter `hr.deployment.grantable_roles` (SE, WSUP, QCE, QS, PLAN, HSEE, HSEO); nothing else can be given this way.
- **ADR-286 One primary deployment at a time is checked four times.** BR-01 is checked when the draft is made or changed, when it is submitted, when an amendment is made and again when the approval lands (against deployments in force), because two drafts for the same dates may wait for approval together. A clash is refused with the number of the deployment it clashes with; the last day is inclusive; the revisions of one deployment (same root) never clash with each other; a secondary posting may overlap. The employee transfer applies in one transaction (the old posting ends on the relieving date, the new one starts after it), so it is never in conflict with itself.
- **ADR-287 The site plan is an adapter table, and outside the plan the project director also approves.** 17.08 resource planning is not built, so the planned posts by designation at a site are `hr_site_plans` (set by `PUT /hr/site-plans`, permission `hr.siteplan.edit`; a new row closes the previous one). A deployment is WITHIN_PLAN when the site has a post for the designation and the people already deployed (approved or waiting, on the start date) plus this one do not exceed it; otherwise OUTSIDE_PLAN (a site without a plan for the designation is outside the plan, as in 07.02). Recomputed on the server at submit. `HR_DEPLOYMENT` is in the approval matrix: within the plan `PM|HRMGR`, outside it `PM|HRMGR` then `PD`.
- **ADR-288 A transfer is routed by resolvers, not by the matrix.** The chain is the current project manager, the receiving project manager (only across projects) and the HR manager. The two managers are different people on different projects, so a role step (which is scoped to the project of the instance) cannot name the receiving one; the resolvers `hr.transfer.from_pm` and `hr.transfer.to_pm` take the project manager recorded in the organisation (`org_assignments`) of each project (never the person who raised it; the PM role when none is recorded). The chain is the definition `HR_TRANSFER`, editable in the workflow designer, and is not in the matrix (D-327).
- **ADR-289 A transfer is applied when it is approved, and undone only before it takes effect.** Approval ends the old primary deployment on the relieving date, creates the new deployment (approved by this chain, `transfer_id` and `source_type = hr_transfer`, carrying the access role and cost allocation of the old one) from the joining date and records what it changed (`applied_json`). The joining date is after the relieving date (the day between is travel). Cancelling an approved transfer, or approving its amendment, reverses that exactly while the joining date is in the future; afterwards the person is moved back by a new transfer. A secondment ends its deployment on the return date and does not resume the earlier posting (D-329).
- **ADR-290 Deployment is the answer to "who is where"; the employee master keeps its own location.** 07.01's location on the employee record changes through its own approved amendment. 07.03 does not write it: the Deployment Board, attendance eligibility (`/hr/deployments/eligibility`, BR-02) and the Employee 360 tab read the deployments.
- **ADR-291 A drag on the board is an amendment sent for approval.** Moving a person to another crew of the site calls `deployments.move`: an amendment with the new crew, submitted in the same transaction. The person stays in the old crew (shown as "change waiting") until it is approved; Undo withdraws it through cancel. Approval is never bypassed by the board.
- **ADR-292 Dated effects have a daily job and a mark.** A deployment approved for a later date, or ending on a date, changes access on its day; `hr.deployment_cycle` (00:35) publishes `STARTED` once for approved deployments whose start has come and `ENDED` once for those whose end has passed (marked by `activated_at` and `ended_event_at`), and tells the project manager of deployments ending within `hr.deployment.notice_days` (7). The access itself needs no job (the grant source compares dates when it is read); the job is for the messaging groups and the consumers of the event.

- **ADR-293 A shift in use keeps its times.** Times are stored in minutes of the day; a shift whose end is not after its start crosses midnight and is a night shift, and its window is anchored on the day it starts (a punch at 06:20 on the 6th belongs to the shift of the 5th). Once a shift is in an assignment, a roster pattern or a roster change, only its name and status can change (409 otherwise), so attendance already worked is never reinterpreted; a new shift is made for new times.
- **ADR-294 Resolution is attribute by attribute, most specific first.** An assignment says a policy, a shift, a weekly off, a holiday calendar, or some of them; for each, the first of employee, crew, site, company (in force on the date) that says it wins, and `sources` names the level. The crew and site come from the employee's approved deployment on the date (07.03) and crew membership. Over the assignment, the roster applies: an approved roster change (or swap), else the rotating pattern of the crew, else of the site. A new assignment of the same place ends the one before it the day before and replaces it whole; one that would start inside a later one is refused.
- **ADR-295 A policy change is a new version with its own date.** Versions of a code are approved separately; the version in force on a date is the latest approved with an effective date on or before it, so a new version never touches earlier days (BR-02). Pay-impacting (overtime, a deduction for lates, early going or a missing punch, comp-off) adds the director to the HR manager; the matrix row `HR_ATT_POLICY` carries it. An effective date inside a closed period is refused when made and again when approved.
- **ADR-296 The attendance period is its own thing, closed in order.** `att_period_defs` give the start day (1 to 28) from a date; `att_periods` are cut from them on demand and closed by the HR manager after their last day, in order. A close is final: assignments, policy versions, roster changes and period definitions cannot reach into it, and the event `att.period.closed` tells payroll.
- **ADR-297 Rosters of the future are direct, of the present are approved.** A rotating pattern starts tomorrow or later and is made by whoever plans rosters of the project; a change of one day (today or later) or a swap goes to the supervisor and the project manager (the project manager alone when the supervisor raised it), is applied only when approved, and a cancelled approved change puts the day back. The swap's two shifts are read on the server at the moment it is asked for. The workflow engine now also asks the holder sources of 07.03 who holds a role at a site, so a supervisor whose access comes from a deployment is found as an approver.

- **ADR-298 The server decides every punch, from what the phone says and what the site is.** A punch is judged in one place (`decide`): the person is deployed at the site on the day (07.03) or a visit is asked for; the online clock may differ from the server by `att.punch.max_skew_seconds` (300), else rejected as CLOCK_SKEW; a mock location (declared, or an accuracy of exactly zero) is rejected (`att.punch.mock_action`); an accuracy worse than the site's reject limit (200 m) is rejected, worse than its flag limit (50 m) accepted with a flag; the position is tested against the fence with the site's tolerance (10 m): outside by more than tolerance plus the reported accuracy is rejected as OUTSIDE_FENCE, outside by less is accepted with the flag EDGE_UNCERTAIN (it may well be inside); a site with no fence drawn accepts with the flag NO_FENCE. Rejected punches are stored with the reason and never count (BR-03). The thresholds are parameters with per-site overrides in `att_site_settings`.
- **ADR-299 Anomalies are raised from what the server knows, never from what the phone claims.** Impossible travel compares the punch with the nearest accepted punch before and after it in time (so an offline sync in any order gives the same answer; speed above `att.punch.max_speed_kmph`, 150, and more than 500 m); repeated low accuracy looks at the last three punches; a phone used by two people the same day (SHARED_DEVICE, high) and a second phone for one person (NEW_DEVICE, low) use `att_device_bindings` (an id the browser makes for itself, not a hardware id); an out punch with no in is flagged and the flag goes when the in punch arrives later. Face matching is a parameter that is off (D-338).
- **ADR-300 Offline punches keep their device time.** The attendance punch is a form of the offline engine: the engine replays commands in order, corrects the device time for the clock difference it measured and passes the command id, which is the client id of the punch (so a replay is the same punch). An offline punch is not rejected for clock skew; it is rejected when it is in the future or older than `att.punch.max_offline_age_hours` (96), and flagged LATE_SYNC when it arrives more than `att.punch.late_sync_minutes` (30) after it was made. Records are ordered by effective (device) time, not by arrival. A selfie of an offline punch follows through the engine's media upload (flag SELFIE_PENDING).
- **ADR-301 A reviewer settles an anomaly; the repeated case goes to the HR manager too.** Accepting an outside-fence punch turns it into a counted, flagged punch (REVIEW_ACCEPTED); rejecting any anomaly takes the punch out of attendance (ANOMALY_REJECTED). A person for whom `att.anomaly.repeat_threshold` (3) outside-fence acceptances were made in `att.anomaly.repeat_days` (30) has the next one routed through `HR_ATT_ANOMALY` (supervisor or project manager, then the HR manager); the reviewer is the maker and cannot approve it. Nobody reviews a punch of their own.
- **ADR-302 A visit is a record of its own.** A punch at a site where the person is not deployed needs a reason; it is PENDING and creates `att_visits` for the day and site, approved by the reporting manager (the manager of the employee record; the HR manager when there is none) and the project manager of the site. Later punches of the day at that site follow the visit. Rejection rejects the punches.
- **ADR-303 The register is a table computed from the inputs, never typed.** `att_daily` holds one row per person and day, made by one deterministic function from the punches, the policy, shift, roster and holidays that resolve for the person, and the approved regularisation, manual entry, visit and overtime of the day. Late marks and weekly overtime depend on earlier days, so a recompute takes a person day by day to the end of the period. The same inputs give the same row (BR-01). Overtime is paid for the minutes the punches show, up to the policy limits and up to the hours approved; unapproved overtime is not paid and is flagged.
- **ADR-304 A locked row is never rewritten; the difference is arrears.** Locking (per period and site, or all sites) needs the period to have ended, no request waiting and no day with a missing punch. After it a recompute that would change a locked day writes `att_arrears` (before, after, deltas) and the event `att.arrears.raised`; a change that is undone removes the entry. A request for a locked day must say `arrears: true` or it is refused (409 PERIOD_LOCKED). Reopening is a workflow (HR manager, then finance head) and recomputes the period; open arrears are folded into it.
- **ADR-305 One shape for the three requests.** Regularisation, overtime and manual entry share the factory in `att-requests.js` (draft, submit, withdraw, cancel, amend, history, print) and differ in fields and band. Bands: a fourth regularisation in a month goes to the HR manager as well; overtime beyond 4 hours a day or 50 hours a month goes to the project manager, and beyond the policy (not eligible, or over its daily limit) to the HR manager too; a manual entry needs the HR manager and the maker cannot check. Approval chains are in the matrix (`HR_REGULARISATION`, `HR_OVERTIME_REQUEST`, `HR_ATT_MANUAL`, `HR_ATT_REOPEN`). The first level is a role (supervisor or project manager), not the reporting manager, because the platform "manager" resolver is the head of the department.
- **ADR-306 Changes of inputs are worked off together.** A punch event only queues the person and the earliest day; a timer (1.5 s) recomputes each person once with one set of facts. Approvals recompute their day at once. A nightly job (01:05) recomputes the last three days. This keeps a morning burst of thousands of punches from recomputing thousands of times.
- **ADR-307 A device file is a log.** The import type `ATT_DEVICE_PUNCH` goes through the 07.05 punch core with method DEVICE, skipping only the phone age rule (flag IMPORTED); the client id is a hash of device, person, type and time, so the same event in one file or in two files is stored once.
- **ADR-308 Balance is the sum of the ledger.** `lv_ledger` holds every movement (opening, accrual, comp-off, adjustment, availed, reversal, lapsed, encashed); `lv_entitlements` is a roll-up written from it after each movement, never edited. A movement with a key (an accrual month, a day of comp-off, a leave application, a year-end step) happens once, so every job is safe to run again. A person's balance can be explained line by line.
- **ADR-309 Days are worked out on the server from the shift calendar.** `countDays` takes the day type of each date from the attendance service (07.04: weekly off, holiday, roster) so the leave and the register agree. Off days at the start or end of a range are never leave; inside it they count only for a type with the sandwich rule. A half day is one working day. A leave stays inside one calendar year (the leave year); a longer one is two applications.
- **ADR-310 Leave reaches attendance through a source, not a write.** The register (07.06) asks `registerLeaveSource` for an approved leave on a working day nobody worked; approval and cancellation only queue a recompute of the person. Unpaid leave shows as loss of pay in the register. Approved leave is charged to the ledger when the last approver decides; waiting leave is reserved against the balance (not charged).
- **ADR-311 Approvals.** Leave goes to the reporting manager (the manager on the employee record; the HR manager when there is none) and also to the HR manager beyond 10 days or for a special type (band EXTENDED). The adjustment of a balance is a matrix document (`HR_LV_ADJUST`, HR manager; the maker cannot check). A leave that has started is changed only by an amendment (new revision, approved again, the difference goes back); one that has not started is cancelled directly by the person or HR.
- **ADR-312 Year-end.** Run once for an ended year and only when no application of the year waits: encash up to the encashment limit (when the type allows), carry forward up to the carry-forward limit (opening of the next year), lapse the rest; a negative balance is carried as it is. One event per person and type tells payroll what to encash.
- **ADR-313 A worker is one row for ever; an amendment is a revision applied to it.** `lab_workers` has the approved worker (the root row) and, when something changes after approval, a revision row with its own approval; on approval the revision's values are copied to the root row and the revision is marked superseded. Deployments, punches, the card and the crew keep the same worker id and code. The ID number is kept as its last four digits and a salted hash (to find a duplicate); the bank account is stored encrypted and shown only as its last four digits.
- **ADR-314 The rules of labour are guards, not screens.** Age (BR-01) is checked on every way to create or change a registration; induction and medical clearance, the licence in force and the licensed number (BR-02, BR-03) are guards that the deployment service asks for every worker (`deploymentGuards`), so an import or an amendment cannot skip them; clearance is a block or a warning by the parameter `lab.deploy.clearance_mode`. A blacklisted or departed worker cannot be deployed or punched in. The licensed number counts the contractor's workers with an approved or submitted deployment on the start date.
- **ADR-315 Wage rates are effective-dated documents.** A minimum wage notification (state, skill, optionally trade) and a contract rate (contractor, trade, skill, state) are approved documents; an approved rate is never changed, a later one replaces it from its date. A contract rate is compared with the minimum wage in force on its start date (daily and hourly are compared at eight hours a day) on submission and again when it is approved; a piece rate is not compared. The rate to pay is the contracted rate, never below the minimum.
- **ADR-316 The card holds a token, not an identity.** The QR on the labour card is `LAB:` and a random token of the card; the kiosk finds the worker by it (or by the typed worker code). A reissue makes a new token and the old card stops working. Workers punch through the kiosk and the crew punch (07.05), with the same checks as an employee, as person type WORKER.
- **ADR-317 A profile change is the change document of 07.01.** Self-service does not keep a second table for it: the page sends `POST /hr/employees/me/changes` and lists the employee's own changes; `ess_requests` holds letters only. One approval path (HR, bank and statutory by the HR manager) and one place where a change is applied.
- **ADR-318 Self-service rights go to everyone; the data scope decides.** `hr.ess.*` are held by the employee and every internal role. What a person sees is limited in the service: their own record, and for a manager the people in their reporting line (direct and indirect, by recursive query). Non-sensitive fields only for a reportee; bank rows are not sent to a manager at all.
- **ADR-319 A letter is approved, then issued.** The HR manager approves the request in the workflow; issuing is a separate HR step that publishes a certificate record and generates the PDF from the template library with its number and QR. A salary certificate needs the gross monthly salary, typed by HR until payroll (M24) can give it.
- **ADR-320 Hindi comes from one namespace.** Every label of the five pages is a key of `ess` in English and Hindi; the language follows the user's appearance setting.
- **ADR-321 Approval follows the matrix: only an external session with a fee has a chain.** The approval matrix of the part names one chain, the manager then the HR manager, for an external training with a cost. An internal session or one without a fee is open for nomination when it is submitted; the audit trail records that it opened by rule. A locked session is changed by cancelling it and planning another; the calendar moves only drafts and returned sessions.
- **ADR-322 A certificate counts only when somebody else verified it.** HR, the safety team and each person for themselves record certificates; the person who recorded one never verifies it, and a change of a verified certificate starts the verification again. `certs.check` answers per type VALID, EXPIRING, EXPIRED, UNVERIFIED, REVOKED or MISSING, and is the one place other parts ask (permits, operator assignment, planning, the deployment service).
- **ADR-323 Posting is guarded by the post's certificates.** A certificate type lists the designations (employees) and trades (workers) that need it; the deployment service asks `assignmentGuards` for every person, so an expired operator licence blocks the posting by the same rule as the check. The daily job tells HR and the holder once for each state (expiring, expired) by the date, verified or not.
- **ADR-324 QR sign-in is for the person, with a window.** The QR holds the address of My Training with a random session token; the person signs in for themselves from one hour before the start to two hours after the end, a seat must be free, and a walk-in is recorded as such. The trainer marks everybody else (and workers, who have no user account). Score and pass mark live on the attendance row; a passed course that carries a certificate type gives the certificate at completion.

- **ADR-325 A KPI names a metric the system can compute, and every figure carries its evidence.** The library holds a formula reference into a registry of metrics (`METRICS`); a value stores the query parameters, the days left out and the records behind it, so the same figure is computed again from the same evidence (T-01). A figure that needs another module's data waits until that module adds its metric; a manual kind lets a manager enter a value with a note as the evidence.
- **ADR-326 Fairness is built in.** Approved leave and the days of a transfer are left out of every metric (BR-01); a person can dispute a value, which freezes it (the computation never overwrites a disputed or adjusted value) until HR upholds it with a corrected value and a reason or rejects it; a final rating is not sent while a dispute of the person is open. The person sees their KPI evidence at all times, and does not see the manager's rating, the calibration and the development plan until the final rating is approved.
- **ADR-327 A rating is a human judgement.** The KPI score and the goal score are shown beside the rating and never replace it. The manager rates, HR calibrates (a rating that differs from the manager's carries its reason) and the final rating is approved by the manager, the skip-level reviewer and the HR manager, with the director for senior grades; nothing computes or changes a rating by itself. The approval chain follows the reporting line through resolvers, so it is not in the approval matrix (as leave).
- **ADR-328 A KPI changes with two people.** A new or changed KPI is a draft until somebody other than the last editor activates it; every change is in the audit trail with the old and the new values, and a retired KPI is never reused.
- **ADR-329 The expense chains follow the reporting line and the bands of the reference matrix.** The matrix document type `EXP` of 04.02 resolves "MANAGER" as the head of the department, which is not the reporting manager; the three workflow types here use a reporting-line resolver and the bands of the reference (₹25,000, ₹1 lakh) as conditions of their steps, so the chain is data of the workflow definition and editable there. A policy deviation, an old bill (BR-03) or a duplicate sent with a warning moves the claim one level up.
- **ADR-330 Every figure of a claim is computed on the server.** Per diem and mileage are days or kilometres times the rate of the most specific active policy; a client amount that differs is refused; limits, receipt rule, GST rules, duplicate detection and flags are computed again at save and at submit, and the same function serves a preview so that the form shows what the server will keep. A flagged line (limit, old bill, a duplicate sent with a warning) needs a justification that the approver sees; a missing receipt above the threshold and a duplicate in BLOCK mode stop the claim.
- **ADR-331 An advance is paid out after approval and outstanding from then.** Approval makes it payable (event for payment 23.04); accounts record the payment (reference, date), which makes it outstanding and, for a salary advance, plans the instalments from the next month for payroll (24.02) to read and record. A travel or imprest advance is settled against a claim at the claim's approval with what is outstanding then; cancelling the approved claim puts the settlement back.
- **ADR-332 Passing for payment is a step after approval.** The chain decides whether the expense is right; the accounts manager (not the claimant) then verifies and passes it for payment (`exp.claim.passed`) and records the payment (`exp.claim.paid`); posting (23.02) reads `exp.claim.approved`.
- **ADR-333 A separation reuses the change documents of the employee master.** Acceptance writes a NOTICE change (today, when the last working day is ahead) and a SEPARATED change effective on the last working day through `employees.exits.schedule`; the daily cycle of 07.01 applies it and removes access (BR-02), so there is one place where status and access change. Cancelling an accepted separation before the last day cancels the scheduled change.
- **ADR-334 Clearances belong to the departments and are checked against what the system knows.** Departments, owners and items are the parameter `hr.exit.clearance_departments`; an item cannot be cleared while the fact says otherwise (account still active before the last day, advances outstanding above the recovery noted, no exit interview). HR may waive a department with a reason, never their own.
- **ADR-335 Full-and-final inputs are computed, blocked, then frozen.** Leave to encash, notice served, recovery or pay in lieu, gratuity eligibility (`hr.fnf.gratuity_min_years`), pending claims and recoveries are computed live; release (422 `FNF_BLOCKED` until every clearance is cleared or waived and the last day has passed, BR-01) stores them in `fnf_json` and raises `hr.fnf.released` for payroll 24.05.
- **ADR-336 An anonymous grievance keeps no identity; disciplinary cases are restricted and audited.** An anonymous grievance stores no complainant or raiser; only a SHA-256 of the company and a 12-character code shown once, which is the only way to follow it. Disciplinary cases are seen by `hr.disciplinary.view`; every view of a case is audited; the employee sees their own cases without the file and inquiry notes and answers a show-cause.
- **ADR-337 An opportunity has a go-ahead and a stage, and they are different.** The approval status (workflow `BD_OPPORTUNITY`: a business development colleague, then the director above ₹10 crore, parameter `bd.go_ahead.director_above_minor`) is the permission to pursue a tender; the stage is the pipeline position, moved by the owner. A stage from Pre-bid needs the go-ahead; the value and the client are locked by it and change by amendment; tracking fields (stage, probability, dates, competitors, owner) change on an approved record.
- **ADR-338 A win has two doors.** `awardFromTender` (a service call for the tender award of 08.03, no route) and the direct award approved by the director (`BD_DIRECT_AWARD`). Tracking, import and the API cannot set Won (BR-01).
- **ADR-339 An amendment is a new approval of the same record.** The snapshot is kept in `bd_amendments`, the record returns to draft and is approved again under the workflow document id `<id>-A<n>` linked to the earlier approval, because the engine locks an approved document id.
- **ADR-340 Reviewers are colleagues; scope is ownership.** The reviewer resolver `bd.reviewer` offers the other BD users (the director when there is none), never the maker or owner; BD sees their own records and those they review (open or decided by them); EST, COMMGR and DIR see all by `bd.view_all`. The forecast sums value times probability rounded once per opportunity, the same rounding in SQL and in code.
- **ADR-341 Clients are read from the partner master.** BD reads code, names, status and role of Client partners through a read-only adapter (no PAN, GSTIN or bank); the influence map is `bd_contacts`, owned by this module, because the partner contacts of 06.04 are governed.
- **ADR-342 A tender has a registration and a stage.** The approval status is the registration (a colleague of the estimation team checks the reference, authority, dates and cost: workflow `TDR_TENDER`); the stage is the progress: Open, Bid or No bid (by the approved decision), Ready, Submitted, Awarded or Lost. Readiness is the only way to Ready (BR-01) and returns to Bid when an addendum arrives.
- **ADR-343 The bid capacity is a formula of the calculation engine.** `tdr.bid_capacity` = A × N × factor − B (A and B from the tender or the company profile parameters `tdr.profile.*`, N the completion period in years, factor `tdr.capacity_factor`); the server recomputes it at every save and the criterion Bid capacity follows it; a figure against a figure is never typed in as pass or fail, it is waived with a reason or corrected.
- **ADR-344 The bid or no-bid decision is scored on the server.** Five criteria scored 1 to 5 with weights adding up to 100 (`tdr.bid_weights`) give the score and the recommendation (`tdr.bid_score_threshold`); a decision against the recommendation needs reasons; the chain is a colleague of the estimation team, then the director; the approved decision sets the stage.
- **ADR-345 An opportunity converted to a tender makes the draft tender in the same transaction** through `convertHooks` (a service call, not an event consumer, so the tender exists when the conversion returns); the opportunity then knows its tender (`tender_ref`).
- **ADR-346 Tender documents live in the document service.** The tender links its documents (`doc_links`, entity `tdr_tender`) and the register lists them through `documentsOf(db).documents.list` with the new link filter; a new document type `TENDER_DOCUMENT` is seeded; ad-hoc files are attached through the file service.
- **ADR-347 Reminders are keyed by date and offset.** The daily job reminds the owner and the people with open tasks on the offsets of `tdr.reminder_offsets_days` before the pre-bid, submission and opening dates and before a task is due, once for each tender, date and offset; a date that moves is told again.
- **ADR-348 The EMD and the fee are requests to finance, not payments.** A `tdr_emd` row asks for the EMD or the tender fee of a tender (mode BG, DD, online or exempt; the amount is the tender's, an exemption needs its reason, a fee is never a guarantee); estimation, the accounts manager and the CFO approve it (workflow `TDR_EMD`), and the accounts manager records the instrument. Payment (23.04) and the register of securities (21.02) are not built: `bd.emd.requested` and `bd.emd.issued` are the hand-off. The instrument number is masked except for its maker and holders of `bd.emd.instrument`.
- **ADR-349 The refund of an EMD follows the result.** When the award or loss is approved the EMD of the tender falls due (`result_on` = the date of the letter, or the day of the decision); the register shows the days since then in buckets 0-30, 31-60, 61-90 and 90+, and the daily job `bd.emd_daily` reminds the requester and accounts every `tdr.emd.refund_followup_days` days (keyed by the multiple, so once each) and warns `tdr.emd.expiry_warning_days` before a guarantee lapses (BR-02).
- **ADR-350 The final bid equals the approved estimate unless the director approves the difference.** The submission keeps the estimate and the bid; a difference needs a reason of ten characters and the chain `TDR_SUBMISSION` (estimation colleague, then the director) approves it (BR-01). Estimation (09.03) is not built, so the estimate is entered by hand and marked `MANUAL` with its reference. Submitting needs a ready tender, the checklist of `tdr.submission_checklist` complete, and the EMD and fee approved and issued; the portal upload is then recorded with its acknowledgement and calls `markSubmitted`.
- **ADR-351 Opening results are entered whole and ranked by the server.** A PUT replaces the opening of a tender; the server ranks the qualified prices (L1 the lowest, equal prices share a rank, a disqualified or unpriced bid has none) and stores the distance from L1 in basis points (T-01). Every other bidder is matched to `tdr_competitors` by its normalised name, which feeds the analysis by competitor, sector, region and month.
- **ADR-352 The award is the end of the tender and the start of the project.** `tdr_awards` records a win (letter of acceptance, date, value; the director accepts it: workflow `TDR_AWARD`, the director step only when won) or a loss (who won, a reason from `bd.lost_reasons`). Approval marks the tender awarded or lost, makes the EMD refund due, wins or loses the opportunity through `awardFromTender` / `loseFromTender` (08.01), and publishes `tdr.tender.awarded` or `tdr.tender.lost`; project creation (10.02) is not built and will consume the first.
- **ADR-353 An estimate is a set of versions sharing a number.** `est_estimates` rows with one `doc_no` and `version_no` 1, 2, 3; a new version copies the items, components, indirects and risks of any version (an approved one only by amendment, with a reason). One version at a time is in approval; the approved one supersedes the version approved before. Items are matched across versions by their BOQ item number, which is unique in a version.
- **ADR-354 Every figure of an estimate comes from the calculation engine.** Three new formulas: `est.item_rate` (selling rate = cost rate x (1 + markup), rounded to paise; cost and selling amounts), `est.percent_amount` (an indirect on a percentage of the direct cost; the exposure of a risk) and `est.estimate_total` (HO overhead on direct plus indirect; contingency = the risks plus a percentage of that base; escalation; total cost; margin and margin %; GST on works contract; bid value), with `ra.unit_rate`, `ra.line_amount` and `boq.line_amount` of earlier parts. The grid is saved whole and priced on the server; no amount sent by a client is accepted.
- **ADR-355 An item priced from an analysis uses its direct cost per unit, not its unit rate.** The analysis' own overhead and profit would be counted twice with the estimate's markup and indirects, so the cost rate is the analysis' direct cost divided by its basis quantity (`ra.unit_rate` with no add-ons). An item whose analysis has a newer released version is flagged; re-pricing moves it to that version on request, and submit is refused while any item is flagged (BR-01). A manual build-up keeps its component rates until it is priced again.
- **ADR-356 Costs are a permission, not a page.** `est.estimate.cost` shows cost rates, markups, component rates, indirects, risks, cost totals and margins; without it (QS, PM) the same pages, API, list, export and print show quantities and selling rates only (BR-02). Project estimates follow the project grant (`scopeFilter` on `project_id`); tender estimates are company-wide.
- **ADR-357 Until the review of 09.03, an estimate is approved by a colleague of estimation and the director.** Workflow `EST_ESTIMATE` (resolver `est.reviewer`: another EST user, else the director; then DIR). The approved estimate publishes `est.estimate.approved` with its resources for the material take-off (09.02) and is the estimate the bid submission (08.03) starts from (`estimate_source` ESTIMATE).
- **ADR-358 A take-off and a BBS are revisions of a drawing, released by a checker.** `mto_takeoffs` and `mto_bbs` rows share `doc_no` with `revision_no` 0, 1, 2 and carry the drawing number and its revision (typed until 11.01 holds drawings; the drawing itself is attached through the file entities `mto_takeoff` and `mto_bbs`). Workflows `MTO_TAKEOFF` and `MTO_BBS`: one checker step (resolver `mto.checker`: a QS or design lead other than the preparer, else the project manager). A released revision never changes; a new drawing revision is a new revision (a released one only with `amend` and a reason), and its release supersedes the previous one (BR-02).
- **ADR-359 Measurements, cut lengths and weights are formulas of the calculation engine.** `mto.measure` (number x length x breadth x height less deductions; the template of the line says which dimensions it uses), `mto.bbs_line` (legs of the shape plus hooks less bend deductions, in bar diameters; weight per metre d x d / 162 rounded down to three places as in the tables, so 12 mm is 0.888 kg/m and T-01 gives 532.8 kg) and `mto.requirement` (BOQ quantity x quantity per unit, then the wastage). The IS 2502 shape codes and the bend deductions are the parameters `mto.bbs.shape_codes` and `mto.bbs.bend_deductions` (BR-01).
- **ADR-360 Deltas are against the previous released revision.** A take-off is compared BOQ item by BOQ item (lines grouped by reference and unit); a BBS bar mark by bar mark (member and mark) and by diameter. The release publishes the delta counts with `est.takeoff.released` / `est.bbs.released`.
- **ADR-361 The explosion reads the bill of resources of 06.03 and stores what a release needs.** A take-off line with a work item is multiplied through `mdm_item_resources` (read-only; the items service has no read call for it) with the component wastage; an engineering MTO line with a material item is taken as it is; a BBS gives the steel by diameter (an item code per diameter is the parameter `mto.bbs.steel_items`). On release the rows go to `mto_material_requirements` (source type and id of the revision) and into the event, for MRP (15.02) and procurement.
- **ADR-362 A released take-off feeds a draft estimate by BOQ item number.** `POST /est/takeoffs/:id/apply` calls `estimates.applyQuantities` of 09.01: the items of the draft with the same item number take the quantity and are priced again on the server; the others are reported, never created.
- **ADR-363 The estimate is approved by the commercial manager's review and the director; the review checklist is a step checklist of the engine.** The default definition of `EST_ESTIMATE` becomes REVIEW (role COMMGR, with the five checklist items of `REVIEW_ITEMS`) then DIR, replacing the estimation colleague of 09.01 (ADR-357). The engine refuses to approve the review step until every item is ticked, from the inbox or from the Estimate Review panel (which records `est_reviews` and acts on the reviewer's task). A definition already stored for a company stays until it is changed in the workflow designer.
- **ADR-364 The bid price is the sum of its parts, by the engine.** `est_bid_summary` holds the parts from the estimate (direct, indirect, overhead, contingency, escalation, profit = selling − cost), the discount, the price before GST, GST and the bid price, worked out by the new formula `est.bid_price` and kept in step while the estimate is a draft; the panel shows the check that cost + profit − discount + GST = bid price (BR-01).
- **ADR-365 A discount above the threshold waits for the director.** `est.bid.discount_director_pct` (2 %): above it the summary needs `EST_DISCOUNT` (the director) and the estimate is not sent until it is approved (a gate of `estimateHooks`); at or below it no approval is needed, but a reason is. A new version copies the register, not the discount.
- **ADR-366 Sensitivity keeps the markup of each item.** +/- x % on a resource (the eight largest by cost, and each kind) raises the cost per unit of every item that uses it (analysis lines with wastage, build-up components); each item keeps its markup through `est.item_rate`, and the bid price follows through `est.bid_price` with the same discount and GST; the profit if the price is kept is shown beside it (T-01).
- **ADR-367 Only an approved estimate goes to the bid, and with its bid price.** The approval event carries `bidSummary` (discount, net, GST, bid price); the bid submission of 08.03 starts from the price after the discount (`estimates.netOf`). The priced BOQ of an estimate not yet approved is marked as a draft, not for submission (BR-02). Downloads go through the API with the person's credentials and are audited.
- **ADR-368 The project master is a 1:1 extension, not a second project.** `proj_projects` (unique on `project_id`) enriches the project of the organisation master (02.02: code, name, type, branch, sites, geofences); the organisation project stays the identity every other module uses. Its status follows the lifecycle through one call (`applyProjectStatus`: Setup draft, Mobilisation and Execution active, Suspended on hold, Substantially complete and DLP completed, Closed and Archived closed), never by hand. The plain activation request of the organisation master is refused for a project that has a master (`activationGuards`), so the approval of this part cannot be bypassed.
- **ADR-369 The wizard is one transaction on the person's authority.** `POST /proj/projects` makes the organisation project, its sites with geofences, the project master, the numbering series (`proj.numbering_templates`), the document folders (`proj.folder_template`) and the key dates together, and sends the project for activation when asked; any refusal rolls all of it back. The organisation, numbering and document services are called as the same person with the roles those services require (SYSADM, PCMGR, DOC): the right to do so is `proj.project.create`.
- **ADR-370 Activation is an approval; the sites activate with the project.** Workflow `PROJ_ACTIVATION` (project director other than the maker, then the director); its approval moves the project to Mobilisation, activates the project and the draft sites of the organisation master and publishes `proj.project.activated` (numbering, folders, messaging groups through the auto-group sync, Project 360 later). The checklist of the activation is ticked before sending and kept in the log.
- **ADR-371 A move of the lifecycle has a checklist; suspension and closure have a chain.** The allowed moves are a table (`TRANSITIONS`); each has a checklist (`proj.lifecycle_checklists`) that is ticked in full and logged, readiness checks (blocking: sites, team, contract data; warnings: the budget of 12.01 and the baseline schedule of 13.03 until those parts register their providers, BR-01), and, for Suspend and Close, `PROJ_TRANSITION` (project manager other than the requester, project director, director). A returned or rejected request ends; a new one is raised.
- **ADR-372 The contract terms of a live project change only by approved amendment.** Contract value, type, number, dates, defect liability, retention, mobilisation advance and the client are refused on a live project; `POST /proj/projects/:id/amend` (`PROJ_CHANGE`: project director, then the director) keeps before and after in the log and applies them on approval, also to the dates and client of the organisation project (BR-02; the contract module of 21.01 will take the value over).
- **ADR-373 Health is the worst of its parts.** The schedule health (open milestones overdue, the completion date passed) comes from this part, in SQL for the list and in code for the page; later parts add theirs through `healthProviders`; the time elapsed is the share of the period gone.
- **ADR-374 The project from an award is the wizard of 10.01 plus a copy, in one transaction.** `POST /proj/projects/from-award` builds the wizard request from the tender and its approved award (client, place, contract type, LoA number, awarded value, end date = start + the period tendered) and calls the project service of 10.01 (nothing is copied from it); then it copies the BOQ and drafts the baseline pack in the same transaction (savepoints), so a refused part leaves nothing. A tender must be awarded with an approved WON award and have an approved estimate; one project per tender.
- **ADR-375 The BOQ is copied into `proj_boq_items` until 10.04 builds the WBS and BOQ.** Each line keeps its quantity, rates, markup and amounts exactly as integers of the estimate line and a link to it (`estimate_item_id`, `source_type`); T-01 compares them column by column. 10.04 takes the table over (adds the WBS link); nothing else writes it.
- **ADR-376 The baseline pack is a frozen snapshot with a hash.** Draft packs are rebuilt from the approved estimate on request and when sent for sign-off; sending freezes the snapshot and stores its SHA-256; an approved pack is never changed (409; correction = a superseding pack with a reason and the same approval, BR-01). `GET .../verify` recomputes the hash, so a pack changed behind the application is shown. The snapshot holds money as text, so the pack reads the same for ever whatever happens to the estimate afterwards.
- **ADR-377 Sign-off is `PROJ_BASELINE`: EST, COMMGR, PD, and DIR when the contract value is ₹ 50 crore or more.** The director step is a conditional step of the workflow definition (`when amount >= 50 crore`, in rupees), so the matrix can change it; distinct approvers and the sender-never-signs rule are the engine's. On approval the pack is signed off, the pack it supersedes becomes SUPERSEDED, and `proj.baseline.signed_off` is published for 12.01, 21.01, 23.11 and 23.12 (`baselineOf(db).signedOff(companyId, projectId)` returns the frozen pack).
- **ADR-378 Costs and margins are shown only with `proj.baseline_pack.cost`.** The API, the print, the exports and the comparison mask costs, margins, risks, norms, quoted rates and productivity for everyone else (the project controller and the project manager see the selling side and the contract). The snapshot itself is built on the system's authority from the approved estimate, whoever drafts it.
- **ADR-379 Handover actions are tasks.** Each action of a handover meeting becomes a task of the task service (04.08) assigned to its owner, with the action's own source key so that two actions never share a task; editing keeps the tasks of unchanged actions and removing the meeting cancels them.
- **ADR-380 Baseline vs Current has a registry for its current side.** `currentProviders` is filled by the budget (12.01) and the forecast (23.11); until then the report shows the baseline alone, by section, with the reason. The Excel import of packs is not offered: a pack is made by the server from approved sources, and an import would bypass them (the standard endpoint list is otherwise followed).
- **ADR-381 The WBS is a tree of ids with weights in percent x 10 000, codes unique within the project.** Codes are generated (parent code + next number) or typed; a node keeps its code when moved. The weights of the active children of a node sum to 100 % (BR-02): adding or changing a weight that would exceed 100 % is refused, a group below 100 % is reported, "Normalise" scales proportions (equal shares when all are zero; the remainder to the first node) and the baseline is refused until every group sums to 100 %.
- **ADR-382 Links are by id, so a move keeps them; a node in use is deactivated, never deleted (BR-01).** "In use" is the work packages and the matrix cells today, plus whatever a later part registers in `usageProviders` (BOQ 10.04, schedule 13.01, measurements 22.01); the same for locations (`locationUsageProviders`). A node with nodes under it is not deleted at all; deactivation takes the subtree.
- **ADR-383 Baselining locks the structure; changes are versions.** The project manager or the project controls manager baselines (version 1 with its snapshot). From then on adding, moving, deleting, deactivating, recoding and re-weighting happen only through `PROJ_WBS_CHANGE` (planning, the project manager, the project controls manager; the sender never signs): a request holds operations and a reason, is dry-run in a transaction that is rolled back (it must leave the WBS valid and change something), and is applied again, in one transaction, at the last approval; the version keeps the snapshot and the diff. One open change per project. Name, discipline, responsible person and description stay direct edits. Import, template, copy and bulk control-account edits are refused after the baseline.
- **ADR-384 The matrix and the work packages are not baselined.** They are working structures (a node is in one work package of each type; the matrix is kept for the lowest active nodes and locations); the WBS they refer to is what is controlled.
- **ADR-385 Locations follow type rules.** What may sit under what is a table (`LOC_RULES`); chainage is in metres, only for chainage segments and structures; sibling segments do not overlap; a structure lies inside its segment; a segment is not shrunk below the structures in it; latitude and longitude come together.
- **ADR-386 WBS templates are code, not a parameter.** Five templates (building, road, bridge, water pipeline, industrial plant) with disciplines and control accounts; the parameter store limits a value to 2 000 characters, so a company's own templates arrive with the configuration part (D-408).
- **ADR-387 BOQ versions are new tables; the thin copy of 10.02 is the source of a tender version.** `proj_boq_versions` and `proj_boq_lines` hold versions and their hierarchy; `proj_boq_items` of 10.02 stays untouched as the copy made at the award and `POST /proj/versions` with `from: AWARD` turns it into a tender version (sections and items, the client rate or the selling rate), so nothing is typed again.
- **ADR-388 Only the lowest lines carry quantity, rate and amount; amount = quantity x rate on the server.** Quantities x 1 000, rates x 10 000, amounts in paise rounded half up (`lineAmount`); the version total is the sum of the lowest lines and is recomputed at every write; bills and sections are summed when read. A line that gets sub-items gives up its own quantity (refused while it is mapped or has norms).
- **ADR-389 Contract and revised versions are frozen by approval; a tender version is not.** `PROJ_BOQ_FREEZE` (QS, commercial manager, project manager) freezes a contract or revised version and publishes `boq.version.frozen`; one contract BOQ per project; a frozen version answers 409 to every write. A revised version is made only from an approved variation (`variationProviders`, filled by 21.05): until it registers, none can be made (BR-02).
- **ADR-390 Mapping splits sum to the item quantity; mapping and norms after the freeze are a request.** Splits (WBS node, optional location, quantity) are validated whole and replace the old ones; mapped quantity cannot be changed without clearing the mapping. After the freeze `POST /versions/:id/amend` holds the new splits or norms, is dry-run checked in a rolled-back transaction, goes through `PROJ_BOQ_MAPPING` (QS, project manager; the sender never signs) and is applied again at approval. Unmapped items are a warning at the freeze, not a block (the evidence panel shows the count).
- **ADR-391 A large import is staged in chunks.** The request body is limited to 50 KB, so a client BOQ is sent in chunks of up to 300 rows to `proj_boq_import_rows`, checked as one (every error with its sheet row; duplicates across chunks found) and committed as one transaction; the column headings are kept so the BOQ exports in the client's columns. The Import Center type `PROJ_BOQ_LINE` takes a workbook into a draft version.
- **ADR-392 Rates and amounts need `proj.boq.rates`.** Site roles read quantities, mapping and norms without rates, amounts, totals or comparison deltas (API, print and export); exports need `proj.version.export`.
- **ADR-393 A team member is a request approved by PM and PD, then a request to the role engine.** `PROJ_TEAM` (project manager, then project director; the sender never signs) approves the membership; on approval the service asks the role engine (02.04, `accessOf(db).requestAssignment`, on the system's authority) for the role of the person scoped to this project for the dates given, which has its own approval chain. The member page shows the access as Granted, Waiting for the role engine or Not requested. Messaging group membership (05.04) follows the `iam.assignment.created` event the role engine already publishes: nothing is written to messaging here. Ending a membership ends the assignment (taking access away needs no approval).
- **ADR-394 Minutes are issued by the chair; the actions become tasks at issue.** The minute-taker (never the chair) sends the minutes; `PROJ_MEETING` has one step, the chair (the project manager when the chair is also the sender). Approval issues the minutes (locked, 409 on every write), turns each action into a task of its owner with its due date through the task service (04.08), tells the attendees (04.06, template `proj.mom.issued`), records the distribution (people told, external attendees with their e-mail) and publishes `proj.meeting.issued`.
- **ADR-395 A correction is a revision with the same number.** `POST /proj/meetings/:id/amend` makes a draft with the next revision number and the content and actions (with their tasks) of the issued minutes; when it is issued the earlier one is superseded, unchanged actions keep their tasks and an action that was removed or changed has its task cancelled and a new one made.
- **ADR-396 An action's status is its task's status.** The tracker joins the action to its task; an owner updates their own action (`proj.action.update`), which starts, blocks or completes the task through the task service; another person needs `proj.meeting.approve`. Overdue is worked out from the due date and the open states.
- **ADR-397 Contact details are a separate right.** E-mail and phone of a stakeholder need `proj.stakeholder.contact`; the API, the export and the page show nothing for others. The people lookup of the project module is available to everyone who may see meetings, not only to those who may see projects, so a minute-taker can pick the chair and the owners.
- **ADR-398 Meetings are not imported.** Minutes are written, sent and approved; an import would bypass the chair (the standard endpoint list is otherwise followed).
- **ADR-399 The assessment is the server's.** The score is the probability times the worst of the four impacts (1 to 25); the level comes from thresholds the project sets (default medium from 5, high from 10, critical from 15, kept in `proj_risk_settings`); the probability scale gives the chance behind 1 to 5 (10, 30, 50, 70, 90 percent by default). EMV = probability percent x most likely cost, in paise with the percentage at x 10 000. A posted score or EMV is refused as an unknown field. Changing the thresholds re-levels every open item at once.
- **ADR-400 Closing is graded by level.** The owner (or someone who may approve) asks to close with a justification of at least 10 characters. A low or medium item closes at once; a high or critical one goes to workflow `PROJ_RISK_CLOSE` where the project manager (resolver `proj.riskpm`: the project's manager, another project manager when the sender is one, else the project director) approves. A rejected or returned closure leaves the item open; closing releases the unused allocation and cancels the open action tasks; "occurred" turns it into a linked issue.
- **ADR-401 A trigger raises the alert through the alert engine.** A reading is compared with the threshold; passing it sets the trigger to FIRED once, publishes `proj.risk.trigger_fired` and runs the company's copy of the library rule `risk.trigger_fired` (dataset `proj.risk_trigger`), created active on the first reading so the alert exists at once; the rule's own schedule (daily) keeps nudging a fired trigger that is not re-armed.
- **ADR-402 Contingency is a ledger, drawdown is a request.** Allocations come out of the project pool and cannot exceed it; a drawdown request cannot exceed the risk's allocation less earlier requests. Only a request is recorded (`REQUESTED`) and the event `proj.risk.drawdown_requested` is published; the budget (12.02) marks it `EXECUTED` through `settleDrawdown`. Opportunities carry no contingency.
- **ADR-403 The monthly review is a frozen snapshot.** A review per month is prepared with the figures of the register, re-taken when it is sent, approved by the project manager and then the project director (workflow `PROJ_RISK_REVIEW`) and never changes after approval; the exposure trend of the dashboard reads the approved snapshots and adds a live point.
- **ADR-404 Issues have their own lifecycle without a workflow.** Open, in progress, resolved (by the owner with a resolution of at least 10 characters), cancelled; `submit` resolves, `withdraw` takes back one's own resolution, `amend` reopens. The standard endpoint list is otherwise followed; import is a JSON batch (all or none), not an Excel type.
- **ADR-405 A layer or overlay change is a proposal until the project manager approves it.** The live columns hold the approved content; an edit stores the new content as `pending_json` and the map keeps showing the live content. Approval (workflow `PROJ_GIS_CONFIG`, resolver `proj.cfgpm`: the project's manager, another project manager when the maker is the manager, else the project director) makes the proposal live from today and raises the revision; rejection or return leaves the live content as it was. The document id carries the row version so a second proposal on an approved layer is a new workflow instance.
- **ADR-406 Leaflet draws the map, loaded on demand.** Leaflet 1.9.4 (BSD-2-Clause, no network copyleft) is added as the only new dependency and is imported dynamically, so pages without a map do not carry it. All layers are drawn as vectors (circle markers, GeoJSON), so no marker images are needed. The list below the map shows the same data and is the degraded mode: it is used on request and automatically when the map cannot be drawn.
- **ADR-407 The base map is off until an administrator allows it.** `gis.tile_url` defaults to `NONE`. Tiles are images from another host, which the content security policy (02.07: `img-src 'self' data: blob:`) rightly blocks; showing them needs the tile address set and the host added to `img-src` through an approved security-settings change. Nothing is loosened here.
- **ADR-408 Punches are aggregates of at least five people.** Punch positions are rounded to 3 decimals (about 110 m) and grouped; a cell is returned only when at least five different people punched in it in the last 7 days; the response has latitude, longitude, people and punches only, never an id, a time or a device (BR-01).
- **ADR-409 Other modules plug points into the map through a registry.** `pointProviders` lists DPR photos, inspections, NCRs, incidents and equipment; one without a `query` is shown as "module not live yet". A module that goes live sets its query and returns `{ id, lat, lng, title, status, date, route }`; the route is what a click opens.
- **ADR-410 Progress is recorded here until 14.05.** `gis_progress` keeps readings by location and activity; the latest reading of each counts; a location's heat is the average over its activities; a strip-chart row is length-weighted over the chainage segments. 14.05 replaces the source and the figures follow.
- **ADR-411 A record page is marked `menu: false` and needs no navigation entry.** Pages opened from a list with an id (a lead, a tender, an estimate, a project, a meeting, a risk, an issue and 24 others) are routed but belong in no menu; the client route says `menu: false`, the navigation check (03.05) then requires that they have no entry, the legacy menu and the start-page choices leave them out. Every other page keeps exactly one entry, and the entry carries the page's own permission (the page is the guard; migration 160 aligned the seven that differed).
- **ADR-412 Project 360 is a page of slots, not a page of queries.** The slots are rows of `proj_360_widgets` (widget, tab, order, the permission that shows it, the part that supplies it); a module that is live registers a provider (`registerProject360Widget`) and the slot fills, a module that is not live leaves its slot as an empty state naming the part. Nothing is stored as a figure; every live figure comes from the service of the module that owns it (risks, issues, map, meeting actions, activity feed) or from that module's own tables, and carries the link to its list or record.
- **ADR-413 A live widget is shown only to a person who may use its module (BR-02).** The page does not show a locked box for it: it is absent. An empty slot of a module that is not live is shown to everyone, because it holds no data. Rates and amounts need `proj.boq.rates`, so the contract value and the BOQ value are hidden from those who lack it, and the header says why.
- **ADR-414 No data is not green.** The health has six dimensions (time, cost, quality, safety, cash, risk); time and risk are worked out now from the milestones and the risk register against the company's thresholds (parameter `proj.rag_thresholds`, changed through the parameter engine's own approval); the others are "no data" with the part that will supply them until that part registers a health source. The overall level is the worst of those that have data.
- **ADR-415 The header does not depend on the project master's view permission.** Only four roles hold `proj.project.view`, but every member of the project team sees Project 360 (`proj.p360.view`); the header reads the project master's own fields directly and applies the same masking of amounts.
- **ADR-416 Three KPI widgets join the dashboard framework (03.07).** `proj.risks.critical`, `proj.milestones.late` and `proj.map.located` are rows of `ui_widgets` with providers in the shared registry; they count inside the person's project scope and drill to the lists.


- **ADR-417 The approval-controlled record is the revision, not the drawing.** A drawing is a register entry that lives on; each revision has its own status (draft, waiting, issued, returned, rejected, cancelled, superseded) and its own approval. The drawing carries the denormalised current revision, current IFC and last response so lists and the site view read one row.
- **ADR-418 Only IFC goes through the three-step approval.** IFC (document controller checks, design coordinator approves, project manager releases) is the revision that may be built from, so it is approved; IFR, IFA and as-built are information and are issued by the document controller on submit. The first step names another document controller than the sender and falls back to the construction manager when there is none.
- **ADR-419 Supersession by rank in one transaction.** IFC replaces IFR, IFA and IFC; IFA replaces IFR and IFA; IFR replaces IFR; as-built replaces as-built only, so an as-built does not take away the IFC. The old revision, its copies, the replacement copies, the notifications and the events are one transaction with the issue.
- **ADR-420 The file service decides who sees a drawing file.** The file entity `engg_drawing_revision` lets everyone who may see drawings read an issued revision and only the register staff (edit or approve right) read a draft, waiting or superseded one. "Hidden from the site" is therefore enforced where the bytes are served, not only on the page.
- **ADR-421 The use check answers, it does not block.** `drawingUseCheck` and `/engg/drawings/use-check` return usable or not with the reason; work authorisation (14.01) decides to warn or block. Transmittal numbers are `TRN-nnnnn` per company from this module until the numbering series (04.05) is wired to it.
- **ADR-422 A response is per drawing, and the drawing keeps the latest.** The code A to D is stored on the transmittal item; the drawing shows the most recent response for its current revision. A transmittal closes when every item has an answer; an answered transmittal is closed, not cancelled.

- **ADR-423 Photos and markups use the file service, not a table of their own.** `engg_rfi_attachments` of the proposal is not created: files are linked to the RFI through the file entity `engg_rfi`, with the same scan, size and signed-link rules as every attachment, and the stage (question or answer) follows from the status when the file was added.
- **ADR-424 Two approvals, one record.** Issuing an RFI to the consultant (the design coordinator checks) and closing it (the design coordinator, then the raiser's lead) are separate workflow documents of the same RFI, because they happen weeks apart and a returned closure must leave the RFI answered, not draft.
- **ADR-425 The consultant's answer is recorded by the design coordinator until the portal (25.04).** The permission `engg.rfi.respond` is held by the design coordinator; external roles get no grants by the role templates, so the portal part will add its own scoped grant.
- **ADR-426 SLA by priority and one escalation.** 2, 5, 7 and 14 days from issue for critical, high, medium and low priority; an RFI past its SLA or its required-by date is escalated once. The check is a service call (`/rfis/escalate`) that a scheduled job will call; the age and the SLA are computed on the server, never stored.
- **ADR-427 The delay draft is ours until 13.05 exists.** A time-impact answer inserts one draft row (`engg_rfi_delay_drafts`) and publishes it in the event; when the delay register is built it reads and takes over the drafts (`TAKEN_OVER`).

- **ADR-428 The internal approval comes before the consultant, and a response is per revision.** A submittal is approved inside first (quality control manager for materials, construction manager for method statements and shop drawings) and only then goes to the consultant; each cycle is a row of `engg_submittal_revisions` with its code, so a C does not erase the history. The workflow document id carries the revision (`id.revision`) so each cycle is its own approval.
- **ADR-429 An approved make belongs to the approval that made it.** Approving a MAR with a make writes one `engg_approved_makes` row for that submittal; amending or cancelling the submittal withdraws it. Procurement and receiving inspection read the rows (and `procurementCheck`), never the submittal's own fields.
- **ADR-430 The purchase-order check answers and the company decides.** `procurementCheck` returns OK, WARN or BLOCK with the reason (pending, rejected, make not approved); the parameter `engg.po_mar_control` (WARN by default, BLOCK, OFF) says how strict. An item with no material approval registered is not held back: the requirement is the existence of a MAR for it.
- **ADR-431 Documents use the file service.** `engg_submittal_docs` of the proposal is not created: documents are linked to the submittal through the file entity `engg_submittal`; sending needs at least one document.

- **ADR-432 Progress is computed, never typed.** A deliverable's progress is the weight of the milestone it has reached (parameter `engg.progress_weights`), recorded as basis points and recomputed on every change; project, discipline and package figures are the weight-weighted average, on the server. A change of the weights applies at the next recomputation.
- **ADR-433 Which status changes count.** IFR, IFA and as-built are recorded by the people who manage the deliverables (date today or earlier, in order); IFC is a release that waits for the discipline lead, the engineering manager and the project manager and counts only when approved. Reopening an approved release is an amendment with a reason.
- **ADR-434 S-curve at month ends.** Planned progress at a date is the highest milestone planned on or before it; actual progress the highest recorded on or before it; both weighted by deliverable weight. The curve has one point per month end between the first and last planned date, and none of actual progress in the future.
- **ADR-435 The purchase order is a reference until 15.05.** A vendor document requirement and a hold carry the PO number as text; the tracker groups by project, PO and vendor. When purchase orders exist the number becomes a link and the vendor portal (25.02) records the submission.
- **ADR-436 The vendor review code is approved before the vendor is told.** The reviewer proposes A to D; the engineering manager approves; A and B accept, C and D start another cycle. The event `engg.vdr.reviewed` is what the portal will send to the vendor.

- **ADR-437 A letter is numbered when it becomes official.** An inward letter takes its number `PROJECT/IN/nnnn` when it is registered; an outward letter takes `PROJECT/OUT/nnnn` when it is approved, so rejected and abandoned drafts leave no gaps, and only an approved outward letter is printed on the letterhead (BR-01).
- **ADR-438 A time bar is its own record.** The obligation to give a notice within a number of days of an event is `engg_time_bars` with a deadline; the outward notice that serves it names it, and issuing that letter closes the bar (in time, or lapsed if issued late). A letter does not carry the countdown itself.
- **ADR-439 The countdown is a service call with a set of steps.** `/letters/alerts` alerts at the company's steps (default 7, 3 and 1 days) once each, marks lapsed bars and alerts overdue replies once; a scheduled job will call it. Each step is its own notification source so the notification service does not suppress it as a repeat. The same bars are offered to the alert engine as dataset `engg.time_bar`.
- **ADR-440 Confidentiality is a permission, not a flag on the screen.** `engg.letter.view_confidential` decides who sees a confidential letter in the list, the search, the thread, the files and the export; registering one needs the same right.
- **ADR-441 Standard texts live in the service until the print templates exist.** Six texts with the project, the reference of the letter answered, its date and the clause filled in; the template engine (04.11) will take them over without a change to the letter record (`template_code` is stored).
- **ADR-442 The budget is generated from two sources, each for what it is good at.** Quantities and the WBS split come from the approved BOQ (10.04: items, norms, WBS mapping); the rates come from the signed-off baseline pack (10.02), matched on norm type and description. A norm without a rate in the pack is an unrated line: the preview names it, the preparer can supply the rate, and the budget cannot be sent while a line is unrated. An item without norms is budgeted at the cost rate of the baseline.
- **ADR-443 Generated values are kept beside the adjusted ones.** `bud_lines` holds `gen_qty`, `gen_rate` and `gen_amount` as generated and `qty`, `rate`, `amount` as adjusted; every adjustment needs a reason and is audited, and a line added by hand is marked MANUAL with its reason.
- **ADR-444 Margin is a warning on direct cost, overheads and contingency; the reserve is outside it.** BR-01 compares those three with the contract value less the target margin (`bud.target_margin_pct`, default 5 %). The management reserve is shown beside the result and is not part of the test. The warning never blocks; it is shown on the workbench, sent to the project manager and shown to every approver as evidence.
- **ADR-445 An approved budget is locked; a revision is a new version.** Original is version 1. Revising copies the lines and phasing into a draft with a reason; the original stays in force until the revision is approved and then becomes SUPERSEDED. A cancelled or rejected version does not hold its version number.
- **ADR-446 Phasing must add up before the budget is sent.** S-curve, even, front- and back-loaded profiles spread each line over the months of the contract period; the last month takes the rounding. Changing the amount of a line removes its phasing, which must be done again. Phasing from the schedule waits for 13.02 and is refused with that message until then.
- **ADR-447 Approval is PCMGR, PM, PD, and the director from ₹ 50 crore.** The preparer (quantity surveyor or project controls manager) never signs; the budget total is the amount of the band step, as in the baseline pack.
- **ADR-448 A budget change is its own record; approved, it makes a new approved version.** `bud_changes` and `bud_change_lines` hold the request with the values before and the signed deltas; approval applies them to the budget in force as a new version (`source_type = bud_change`), the old version becomes SUPERSEDED, and `bud.budget.revised` is published. The approved version is never edited (12.01 ADR-445).
- **ADR-449 One change of a project in approval at a time, decided against the budget in force.** A change carries the budget it was drafted on; if another change was applied since, it must be given again before it is sent. A 12.01 revision draft and a change in approval exclude each other. This keeps every approver's numbers true.
- **ADR-450 A drawdown names only what receives money.** The service takes the same amount from the contingency lines; the contingency left is the contingency in force less the drawdowns already waiting, so two waiting drawdowns cannot spend the same money (BR-01).
- **ADR-451 Bands by share of the budget.** Revision, transfer and variation drafts: project control manager, project director, and the director when the share (the change of the total, or the amount moved for a transfer) is above 5 % (`when pct > 5`); drawdown: project manager then project director. The share is computed by the server at submit and is the workflow context.
- **ADR-452 Variations reach the budget by an event.** 21.05 is not built; the consumer `bud.variation` listens to `ctr.variation.approved` ({ projectId, variationId, variationNo, title, amount, lines }) and drafts one VARIATION change per variation for the project manager to check and send. 21.05 must publish that event (D-459).
- **ADR-453 Phasing follows a changed line.** The new amount of a changed line is spread in the proportions of its old phasing; a new line is spread evenly over the months still ahead of the budget's phasing, so an applied version is always fully phased.
- **ADR-454 Available is budget less open commitments less every actual; the same money is never counted twice.** BR-01 reads "less open commitments and actuals not linked to commitments". Counting only unlinked actuals would let a receipt of 40 against a commitment of 100 look like 60 spent. Here the open part of a commitment (amount − consumed − released) and every posted actual are subtracted: 60 committed + 40 actual = 100, and an actual above its commitment is cost beyond it (T-02).
- **ADR-455 A commitment is one row per document line, moved by amendments.** The key is company, source type, source id and line id. The same document again is an amendment by the difference (T-01), never a second commitment; short-close releases the open part and keeps the consumed part as cost; cancel is the same when nothing was consumed; a PR is replaced by the PO that names it (`replaces`). `bud_commitment_log` records every movement and sums to the open amount, which the tests reconcile.
- **ADR-456 Actuals are idempotent by source and consume a commitment at most once.** A repeated event changes nothing; a reversal restores the consumed part to its commitment and cancels the actual.
- **ADR-457 Result per setting: warning inside the tolerance, then by mode.** The most specific setting in force (cost head and stage, cost head, stage, default) decides; no setting means off. Over budget within the tolerance is a warning in both modes; beyond it, warn mode warns and block mode blocks. A project with no approved budget warns.
- **ADR-458 A block is lifted only by the protocol and control engine.** `CP-BUD-01` (enforcement EXCEPTION, mode ENFORCE) is checked from the form (`POST /check` with the document's source) so that the person can raise an exception with evidence; the ledger consumes the approved exception when the commitment is recorded, for that document only. There is no override in the ledger itself (BR-02).
- **ADR-459 The ledger is fed by events and a system endpoint.** Event families `proc.pr|po|hire_order|service_order`, `ctr.workorder` (`approved`, `amended`, `closed`, `cancelled`) and `inv.grn|issue`, `ap.bill`, `hr.payroll`, `plant.cost` (`posted`, `reversed`) carry the payload documented in ARCHITECTURE section 95; `POST /ingest/*` takes the same payload for the system administrator (`bud.ledger.post`), because the modules that publish them are not built yet (D-463).
- **ADR-460 Settings are maker-checker.** A proposal is a row waiting for approval (`BUD_CHECK_CONFIG`, the project director); the proposer never approves; approval supersedes the earlier setting of the same cost head and stage and publishes `bud.check.config_changed`; everything is audited.
- **ADR-461 One budget per cost centre and year, in versions.** A cost centre of type COST linked to a department (or to nothing) has at most one open version and one approved version in force per financial year (partial unique indexes); an approved budget is locked and a new version (a copy of its lines) supersedes it only when approved.
- **ADR-462 The department head step is a resolver, and nobody approves their own.** `bud_dept_head` finds the head of the department of the cost centre (HEAD assignment, else the head on the department); if that person sent the budget, the head of the department above decides; if nobody is found the step waits for a workflow administrator, as the engine does for any empty step. The CFO and director steps are roles. There is no department-head role code in the catalogue: preparing is granted to the head-office manager roles and is limited to a department by a department-scoped assignment.
- **ADR-463 Ledger actuals by event and a system endpoint.** The general ledger (part 23) is not built; `fin.gl.posted` and `.reversed` are consumed and `POST /dept-actuals` (system administrator only) takes the same payload, once per source line; a different amount for a recorded line is refused until the document is reversed. The report says when no actual has arrived.
- **ADR-464 Allocation arithmetic is whole paise.** Each share is rounded down; the residual (less than one paisa per project) goes to the largest basis value (the first on a tie), so the shares equal the pool exactly; the run table has a CHECK that allocated equals pool.
- **ADR-465 Bases and rules.** Revenue = contract value of the active projects until part 23 gives the revenue of the months; direct cost = actual cost posted in the ledger of 12.03 for the months, else the direct cost of the approved project budget; fixed percentages must add up to 100. The pools of the rules in force of one year may not overlap. A rule is drafted by one person and put in force by another and is then locked; a run for the same rule, months and source is posted once until it is reversed.
- **ADR-466 CPM in working-day units of the schedule calendar.** The passes use the integer arithmetic of the precedence diagramming method (ES of the first activity 0, EF = ES + D, FS/SS/FF/SF with lags; total float = LF − EF; free float = the least slack to a successor, to the project finish when there is none; critical = total float ≤ 0). Dates are the working days of those units. An activity on its own calendar takes its duration in that calendar, converted where it starts. Results are checked against hand-worked reference networks and, on 300 random networks, against an independent relaxation solver.
- **ADR-467 Progress keeps the logic.** At a data date a finished activity is fixed and has no float, a started one finishes its remaining duration from the data date, and nothing open starts before the data date. The logic of an approved schedule is locked, but its progress is updated and it is recalculated (the dates move; the network does not).
- **ADR-468 LOE and WBS summaries take no part in the passes.** A level-of-effort activity runs from the earliest start of its predecessors to the latest finish of its successors; a summary spans the activities of its WBS node and below.
- **ADR-469 Delayed means negative float.** Until baselines exist (13.03) an activity is shown as delayed when its total float is negative (it cannot meet a constraint or the logic); the delay against a baseline comes with 13.03.
- **ADR-470 Calendars and templates are maker-checker without a workflow document.** A planner drafts, the project controls manager puts in force; the drafter can never put their own in force; an active one is locked and replaced by cancelling and drafting another (as the allocation rules of 12.04).
