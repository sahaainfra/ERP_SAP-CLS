Entries are append-only. Approved golden-output changes use the line format `GOLDEN-APPROVED: <id> <sha256> <reason>` (BR-03).

## 2026-10-30 - Greenfield codebase (part 00.01)
`ERP_SAP CLS` is a new codebase. The owner chose not to audit `ERP_Construction` or `ERP_SAHAA INFRA`. The discovery baseline is therefore empty.

## 2026-10-30 - Technology stack (part 00.02)
Owner chose Node + SQLite over PostgreSQL because PostgreSQL and Docker are not installed on the development machine.

- Server: Node 24 (ESM), Express 5, `node:sqlite`, Zod for input validation.
- Client: React 19, Vite.
- Tests: `node:test` for unit and API tests; Playwright (installed Chrome, no browser download) for E2E.
- Consequence: the pack's `NUMERIC(18,2/4/3)` and `EXPLAIN` on 100k rows do not map onto SQLite. Money and quantities must be stored as integer minor units or as text decimals, never REAL. A move to PostgreSQL later needs a migration plan; the migration files are plain SQL kept simple for that reason.
- Consequence: `timestamptz` is stored as ISO-8601 UTC text.

## 2026-10-30 - Schema baseline locked at the end of part 00.02
00.01 found no database, so its baseline is empty and could not protect anything. `schema/baseline.json` was locked from migrations `20261030000001` to `20261030000003`. From now on schema-diff fails if any of those objects is altered or dropped. New tables, new indexes and new nullable (or defaulted) columns are allowed. To re-lock after an approved change run `node scripts/schema_diff.mjs --lock` and record the reason here.

## 2026-10-30 - Feature-flag data model
One table, `core_feature_flags`. A row's scope comes from its columns: environment default (`environment` set), company override (`company_id`), project override (`company_id` and `project_id`), flag default (all NULL; `default_enabled`). Overrides apply in every environment. Flags are defined by reference-seed migrations, never created through the API.

## 2026-10-30 - Golden outputs
`golden/registry.mjs` holds deterministic runners; `golden/outputs/*.json` holds the captured results, compared byte-for-byte. The first registered output is the flag-evaluation matrix, because no business calculations exist yet.

## 2026-10-30 - CI/CD and release engineering (part 00.03)
- One quality-gate command, `npm run erp:regression`, is both the local check and the CI `verify` job, so the two cannot drift.
- Staging and production hosting are not chosen. Deploy, rollback, backup and smoke-test tooling is written against a directory-based environment and rehearsed there; moving it to a real host means replacing the start/stop and copy steps in `scripts/lib/deploy.mjs`.
- Database rollback prefers the down-migrations of the build being removed (keeps new data) and falls back to the pre-deploy restore point (loses data written since). Restore points are SQLite `VACUUM INTO` copies.
- Coverage gate: line coverage of changed JavaScript files under `src/server` and `scripts/lib`, minimum 60 %, to be raised to 80 %. The server entry point is excluded because it is exercised as a separate process. Client code is covered by the E2E suite, not by line coverage.
- Build ID is `<timestamp>-<commit>` locally and `<run number>-<commit>` in CI. Versions are bumped by hand with `npm run release -- patch|minor|major`; the changelog comes from the `P<part>:` commit subjects and business-language notes from `Release-note:` lines.
- The About page and `GET /api/v1/core/about` are limited to `core.about.view` (SYSADM, ITADM). The build ID appears nowhere else in the UI.
- Security scans: `npm audit` (high and critical block), a built-in secret scanner (`scripts/lib/secrets.mjs`) and CodeQL in the workflow. No third-party secret scanner is installed.

## 2026-10-30 - Application architecture and API conventions (part 01.01)
Architecture decision records. The reference text is `docs/erp/ARCHITECTURE.md`; each record here gives the reason.

- **ADR-01 Layers.** route -> controller -> service -> repository, one file each per resource. Business rules, the permission guard and the data-scope check live in the service so jobs, imports and other modules that call it are protected like HTTP requests. Tests fail if a controller, route or validator contains SQL.
- **ADR-02 Module ownership and registry.** `src/server/modules/<code>/` owns its tables; `modules/registry.js` lists modules and mounts them under `/api/v1/<code>`. The existing flags, about and session code was moved into module `core`, which is the reference implementation. Nothing outside this repository's own code needed an adapter.
- **ADR-03 Platform libraries.** Cross-cutting code (`config`, `db`, `http`, `auth`, `validation`, `pagination`, `money`, `health`, `audit`, `events`) lives in `src/server/platform/` and never imports from `modules/`. Old file paths were not kept as re-export shims: all imports were updated, so each thing has one location.
- **ADR-04 One error envelope and one error-code registry.** `platform/http/errors.js` holds the codes; the handler, the guide page and the tests read the same list. Malformed JSON used to fall through to a 500; it is now a 400 `BAD_JSON`, and an oversized body a 413. That is a bug fix: the old response was an unhandled-error 500, not a designed shape. Unexpected errors return a generic 500 and the stack stays in the server log under the correlation ID.
- **ADR-05 Request logging.** One JSON line per request with correlation ID, method, path, status, duration and user. Query strings and bodies are never logged, so a search term or an amount cannot leak into logs.
- **ADR-06 Lists.** `parseListQuery` implements `page`, `pageSize` (max 200), `sort`, `q`, `filter[column]`, `from`, `to`. `sort` and `filter` accept only columns the endpoint allow-lists (otherwise 400) and `ORDER BY` is built from a column map. Express 5 does not nest `filter[x]`, so the keys are matched by pattern.
- **ADR-07 Decimals.** No floats for business numbers. `src/shared/decimal.js` is a BigInt-based exact decimal, rounding half-up (ties away from zero) by default, used by the server and the browser. Money 2, rate 4, quantity 3, percent 4 places; rounding happens once at the end; `allocate` splits an amount without losing paise. A number with a fraction must be passed as a string.
- **ADR-08 Health.** `/health/live` is public. `/health/ready` is for ITADM/SYSADM or a monitoring token (`HEALTH_TOKEN`, 16 characters or more, compared in constant time) because it names failing dependencies. Database, queue (outbox) and storage are checked; a failing dependency returns 503, a backed-up outbox is `degraded` (200). `/api/health` stays unchanged.
- **ADR-09 Events.** `publishEvent` writes the standard envelope (`eventId`, `occurredAt`, `companyId`, `projectId`, `siteId`, `entity`, `entityId`, `version`, `actorId`, `data`) to the outbox in the caller's transaction. Rows written by part 00.02 have the older flat payload; the dispatcher in 01.04 must accept both (D-016).
- **ADR-10 Frontend.** One API client (retries idempotent GETs only, one correlation ID per call, errors normalised to `ApiError`), TanStack Query for server state with a key factory, and a module route registry. Navigation hides entries the user has no permission for and entries whose feature flag is OFF; the page itself still shows a no-permission or not-enabled state when reached by URL. The guide is rendered by a small parser that builds React elements, so no HTML is ever injected.
- **ADR-11 Contract snapshot.** `tests/contract.test.js` records 25 requests to the pre-existing routes and replays them against the data that existed then (migrations up to `20261030000004`), so later reference seeds do not look like contract changes. Permission lists may grow, never shrink. Re-record only on purpose and say why here.
- **ADR-12 Gated coverage.** The coverage gate now also covers `src/shared` and the plain-JavaScript client platform files (API client, registry, markdown, formatting, query keys). React components stay covered by the E2E suite.
- **ADR-13 Feature flag.** The guide ships behind `ff.core.p0101`: default OFF, ON in development and test. The API answers 404 "not enabled" and the navigation entry is hidden while it is OFF for the user's company.

## 2026-10-30 - Database foundation, migration framework and data integrity (part 01.02)
- **ADR-14 Money and numbers are whole integers.** The pack asks for NUMERIC(18,2) and similar; SQLite has no exact decimal type, and REAL is a float. Business numbers are therefore stored as INTEGER minor units: money in paise, rates x10000, quantities x1000, percentages x10000, converted with `toUnits` and `fromUnits` (exact, half-up). SQL can add, compare and index them exactly, so "header total equals the sum of its lines" is an exact `<>` test. The schema lint rejects REAL, TEXT or untyped money-like columns. When the database moves to PostgreSQL the columns become `NUMERIC(18,2)` (money), `NUMERIC(18,4)` (rates), `NUMERIC(18,3)` (quantities), `NUMERIC(9,4)` (percentages) in one migration that divides by the scale, and indexes are then created `CONCURRENTLY` outside the transaction. SQLite integers are 64-bit; `toUnits` refuses values above 2^53 paise (about 90 trillion rupees).
- **ADR-15 Migration zero.** Part 00.01 found no database, so there is nothing to baseline from outside. Migration `20261030000001` is migration zero and `docs/erp/DB_BASELINE.md` (generated, checked in CI) is the schema at the end of this part. `schema/baseline.json` was re-locked from migrations up to `20261030000007`; objects in it can never be altered or dropped, only added to.
- **ADR-16 Idempotency.** Keys are scoped to the user and the endpoint. First request: the handler runs and a 2xx response is stored for 24 hours. Same key and same body: the stored response is returned with `Idempotency-Replayed: true`. Same key, different body: 422 `IDEMPOTENCY_KEY_REUSED` (BR-02). Same key while the first is still running: 409 `REQUEST_IN_PROGRESS`. Non-2xx responses are not stored, so a client that fixes a validation error can reuse its key. The body is hashed after sorting object keys, so key order does not matter. The key is required on submit, post, payment, stock and approval endpoints (`required: true`) and optional on the flag change and the integrity run, where it is honoured when sent. Stored responses hold whatever the endpoint returned, so they are business data with a 24-hour life (D-019).
- **ADR-17 Integrity checks.** Seven checks, each with a severity; a failed Critical check blocks CI (BR-03) and `--fail-on` raises or lowers the bar. Business tables are found by convention (column names) and modules add what the schema cannot say through `integrityRegistry.register`. A check with nothing to look at reports `not_applicable`, never a pass, so an empty database cannot look healthy. Results are stored one row per check per run. Samples hold identifiers only (table, id, company, key) so ITADM, who has no business-data access by default, never sees amounts, rates or personal data. A check that throws is reported as a failure with the reason instead of hiding the other checks.
- **ADR-18 Company scope.** `companyScope`, `findScoped` and `listScoped` are the way business queries read a company's data. An actor without a company is refused (deny by default), a row of another company is "not found", and a scoped list must have a limit of 1 to 200.
- **ADR-19 Back-fills.** A back-fill is a function that does one batch and returns its cursor. The batch and its ledger update commit in one transaction, so there is no state where data changed but the ledger did not. Failed batches roll back and the ledger records the error; the next run resumes. No real back-fill exists yet: the registry (`backfills/`) is empty and the framework is tested with fixtures.
- **ADR-20 Backups.** A backup is a `VACUUM INTO` copy plus a manifest (file hash, SQLite integrity result, row count and hash of each table, schema hash). Restore verifies the manifest first, never touches the target if verification fails, and re-checks the restored file against the manifest. The helpers moved from the deploy tool into `scripts/lib/backup.mjs`; the deploy tool uses them.
- **ADR-21 Test data.** The generator creates its own `perf_*` tables in a scratch database, not in the application's migrations, so performance data can never leak into a real schema. It is deterministic for a seed (fixed timestamps included) and its tables follow every standard, so the integrity suite and the schema rules run against something realistic.
- **ADR-22 Data Health.** `/admin/data-health`, API `POST /api/v1/core/integrity/run` (ITADM, `core.integrity.run`), `GET .../integrity/summary` and `.../integrity/runs` (ITADM and SYSADM, `core.integrity.view`), behind `ff.core.p0102`. The run is synchronous: the suite takes about half a second on 100,000 documents; long runs belong to the job scheduler of part 01.04 (D-018).
- **ADR-23 Numbering counters.** One counter row per series and period key, advanced by a single `INSERT ... ON CONFLICT ... RETURNING` statement, so concurrent requests and processes cannot receive the same number. A gap-free series issues only inside the caller's transaction (a rollback gives the number back); a non-gap-free series may be issued on its own. Cancelled numbers stay in `core_number_issues` as CANCELLED and are never reused.
- **ADR-24 Series scope.** The most specific series wins: project, then branch, then company. A reset rule needs matching tokens in the format (a financial-year reset needs `{FY}`, `{FYS}` or `{YYYY}`), so numbers cannot repeat. Statutory numbers are at most 16 characters of letters, digits, `/` and `-` (GST rule 46).
- **ADR-25 Period control.** Statuses are per module and per month. Soft-closed accepts only actors with `core.period.post_soft_closed`. Closing is by the Accounts Manager; reopening needs an approved request (ACCMGR then CFO) and is applied in the transaction of the final approval.
- **ADR-26 Parameters.** Typed (string, integer, decimal, boolean, date, json), with limits, allowed values and scopes declared in code. Rows are never edited: a new value closes the old one the day before it starts. Past dates are refused. System scope needs `core.param.configure_system` (IT Administrator); company scope needs `core.param.configure`.
- **ADR-27 Interim approvals.** `platform/approvals` supports role chains, segregation of duties (the requester cannot approve), comments and a handler that applies the change in the same transaction as the last approval. Delegation, SLA and configurable chains belong to the workflow engine (04.01, D-022).
- **ADR-28 Excel import.** Holiday import reads `.xlsx` in the browser (`read-excel-file`) and sends rows as JSON, so the server needs no spreadsheet parser. The import is all or nothing: every bad row is reported and nothing is saved.
- **ADR-29 Outbox stays as it is.** `core_outbox` (part 00.02) is the event log and is not altered: its `published_at` means "the relay has fanned this event out". Per-consumer state lives in the new `core_inbox`, so no pre-existing object changes. The outbox is never purged, because it is the replay history.
- **ADR-30 Delivery model.** At-least-once delivery with de-duplication: one inbox row per (consumer, eventId), a handler and its processed mark in one transaction, retries with exponential back-off (30 s doubling to 1 h), dead letter after `maxAttempts`. Handlers are synchronous. Exactly-once effect depends on the handler writing only inside its transaction; effects outside the database (mail, SMS) must check `ctx.replay` and be idempotent on their own.
- **ADR-31 Request types are not a CHECK constraint.** `core_change_requests.type` listed its values in a CHECK, so each new approval-controlled change needed a table rebuild. Migration `20261030000013` rebuilds the two change-request tables once without it (rows, ids and indexes kept; its down migration restores the constraint and removes `schedule_change` requests). The approval engine already refuses a type with no registered handler.
- **ADR-32 Single database, no external queue.** The bus and the job runner use SQLite tables and polling workers; several instances sharing the file are safe because every claim is a single statement or a `BEGIN IMMEDIATE` transaction. A message broker or Socket.IO relay is not built (D-026); the interface (`publishEvent`, `subscribe`, `enqueue`) does not change when one is added.
- **ADR-33 Schedules.** Cron in IST with five fields; a missed slot runs once; a schedule is defined in code (seeded once) and changed only through a maker-checker request (ITADM asks, SYSADM approves). Schedule rows are system-wide; the request is filed under the requester's company.
- **ADR-34 Console scope.** Events, dead letters and jobs are shown for the actor's company plus system-wide ones (no company). Payloads are masked (identifiers, bank, salary, rate and cost fields) in the console, the dead-letter viewer and CSV exports.
- **ADR-35 Access follows the record.** The file service has no permissions of its own for reading, attaching or removing: it asks the module that owns the linked record (`fileEntities`). A module that registers a record type therefore decides who can see its files, and a cross-company or unknown record is "not found". Only administration (overview, settings, rescan) uses `core.files.*` permissions.
- **ADR-36 Type checking.** An extension must be in the company's allow-list and the leading bytes must match what a real file of that type starts with; Windows, Linux and macOS programs and scripts are refused under any name. Archives (zip), HTML and SVG are not on the list: they can hide or carry active content, and the system cannot check what is inside.
- **ADR-37 Scan before use.** A stored file is PENDING until the scan job gives a verdict; nothing but CLEAN is ever served, not even to an administrator. The built-in scanner finds only the EICAR string and an ERP test string (so the quarantine path works everywhere); real protection is ClamAV through clamd, which the system checks and uses when `CLAMAV_HOST` is set. A scan that errors is retried, never treated as clean.
- **ADR-38 Resumable uploads.** Offset-based chunks into a temporary file, a session per upload, the server as the source of truth for how many bytes it has (a half-received chunk is discarded). Completing re-runs every check, so the two upload paths cannot differ in what they accept.
- **ADR-39 Signed links.** A link is a short-lived bearer: HMAC over file, expiry, variant and disposition. Permission is checked when the link is issued, not when it is used, so a link keeps working until it expires even if the record's permissions change. The life is short (default 120 seconds) and a company setting. `FILE_URL_SECRET` is required in staging and production so every instance signs and verifies alike.
- **ADR-40 Metadata and privacy.** Capture time and GPS position are read from a JPEG's EXIF into the record. "Strip" on upload removes every metadata block from the stored JPEG or PNG (camera, serial, owner, thumbnails) except the orientation, so the picture still shows the right way up; time and position stay in the record only. The checksum is of what is stored.
- **ADR-41 Files are never destroyed by the application.** Delete is a soft delete and a superseded version stays; quarantined files are moved, not deleted. Retention classes are recorded per file from the category setting, but no job purges by retention yet (D-036).
- **ADR-42 The calculation language.** Formulas are programs in a small language parsed and evaluated by our own code: decimals, text, yes/no, arithmetic, comparison, `if`, and the functions round, min, max, abs, floor, ceil, percent and sum. It is deliberately not JavaScript: nothing can loop, read the environment or run for long. A division keeps 12 decimal places and the output is rounded once; 3,000 random cases of each built-in formula matched the original code to the paisa (D-038 names the theoretical limit). Rounding policies are named (`half_up`, `bankers`, `down`, `up`) and apply to every `round()` and to the outputs of a formula unless a call names a mode.
- **ADR-43 Versions are immutable and approved.** A version is a draft until it is activated; after that its calculation cannot change (a database trigger refuses it), and a change is a new version. Activation is a request to the approval chain of the owning module (project controls manager for BOQ, accounts manager for tax, billing and stores, IT administrator for core), plus the CFO for financial formulas. The built-in version 1 of each existing calculation is seeded as active by the system, because it is the code that already ran; starting the application fails if the stored definition and the code differ. Two versions may not start on the same day or out of order, so history is never rewritten.
- **ADR-44 A document keeps its formula versions.** The sample bill stores the versions it was calculated with. A draft is recalculated with the versions in force today; a submitted bill only with its stored versions, and the result must equal what is stored (BR-01). The same rule applies to every module that adopts the engine.
- **ADR-45 Traces.** The engine can store, for a record, the inputs, every step with its formula and value, the roundings, the outputs and the formula version (`core_calc_traces`). Showing a trace needs view permission on the record, decided by the module that owns it (the same registry the file service uses). Traces are for audited values; the test bench keeps nothing.
- **ADR-46 Shadow mode.** A version in SHADOW is evaluated next to the active one whenever the active one is used for a record or the bench with recording on; it never decides a result and cannot calculate a record by itself. Results go to `core_calc_shadow_results`. The activation request shows how many real calculations were compared and how many differed.
- **ADR-47 Units of measure.** Until the UOM master of part 06.02 exists, units and factors live in `core_uoms` and `core_uom_conversions`. A factor is a decimal text; a chain of factors is multiplied as an exact fraction and rounded once. An item row beats a generic row for the same pair, and rows are shared by every company (D-042).
- **ADR-48 Golden outputs for calculations.** Golden files for the built-in formulas were captured from the code the engine replaced (`tests/helpers/legacy_calcs.js`, which uses no formula language) on fixed cases that include rounding boundaries. They are compared with the engine's output by `npm run erp:golden` and by the full regression.
- **ADR-49 Redaction by key and by pattern.** Every log entry is redacted before it is written or buffered: by the name of the field (secret keys fully, identifiers keep four characters, document content omitted) and by pattern in free text (PAN, GSTIN, Aadhaar, IFSC, e-mail, bearer tokens, JWTs, long digit runs). Redaction is the logger's job, not each caller's, so a new log line cannot forget it (BR-01).
- **ADR-50 Pseudonymised user in logs.** Logs carry `u_` plus ten hex characters of an HMAC of the user name, never the name. An administrator who needs the person looks up the pseudonym through the audit trail, which does record the user.
- **ADR-51 Own tracer instead of the OpenTelemetry SDK.** The SDK is not installed and nothing is added without need. A small tracer keeps W3C `traceparent` and exports OTLP/JSON, so an OpenTelemetry collector can take the traces later without changes to the code that creates spans (D-046).
- **ADR-52 Metrics by route pattern.** Metrics are keyed by the matched route pattern, not the URL, so identifiers never create new series; a URL that matches nothing is counted as "unmatched". Latency is a fixed-edge histogram per minute, which makes percentiles cheap and objectives computable over days from hourly roll-ups.
- **ADR-53 Objectives and alert rules change by request.** A change to an objective or an alert threshold can hide a real problem, so it follows maker-checker like other configuration (ITADM asks, SYSADM approves) and is audited.
- **ADR-54 The event log shows the latest 20,000 events.** At 100,000 events the unfiltered log took 1.4 s (baseline, part 01.07) because each payload had to be read. The page now browses the newest 20,000; older events stay in the outbox for replay (D-045).
- **ADR-55 Modules call connectors by code through one service.** `hub.call(code, operation, payload)` is the only way to reach an outside service. Retries, timeouts, the breaker, the rate limit, credentials and logging live there, not in modules, so a provider can be replaced without touching a module and every call is logged the same way.
- **ADR-56 Credentials are staged, approved, then active.** A secret entered in a change request is encrypted at once and held as PENDING; the request carries only the key names. Approval promotes it in the approver's transaction. Nothing but the integration service can decrypt, and the approval record never contains a value.
- **ADR-57 AES-256-GCM with a slot-bound nonce.** Each value is encrypted with a key derived from `VAULT_KEY`, a random 96-bit nonce and the connector and key name as additional data. A database copy without the key is useless, and a value moved between rows fails to decrypt.
- **ADR-58 Only provider-side failures trip the breaker.** Timeouts, network errors, 5xx, 408 and 429 count against the provider; a 4xx answer to a bad request does not, or one user's mistake could pause everyone's email.
- **ADR-59 Switching off is immediate, switching on is approved.** An outage needs a kill switch that does not wait for an approver; turning a connector back on is a configuration change and needs the chain.
- **ADR-60 Connector codes are unique across the system.** The public webhook URL identifies the connector by code before any company is known, so a code cannot repeat in another company.
- **ADR-61 Short access token, server-side session.** The access token only names a session; the session row decides whether it is still good. A signed token alone cannot be revoked until it expires, which is too slow for a forced sign-out, so the extra lookup on each request is accepted.
- **ADR-62 Refresh token rotation with reuse detection.** Each refresh replaces the token. A replaced token that comes back means two parties hold the same one, and the whole session ends. The cookie is HttpOnly and SameSite=Strict, scoped to the sign-in routes, and used only with a custom header.
- **ADR-63 Argon2id from Node itself.** Node 24 provides Argon2id, so no native dependency is added. Old hashes are verified by named verifiers and upgraded at the next successful sign-in; nothing writes an old format again.
- **ADR-64 One answer for every sign-in failure.** The same message, status and time for a wrong password, an unknown name, a disabled account and a lock; failures are counted per name, not per account, so the count also exists for names that do not.
- **ADR-65 Second step by policy, not by flag.** Which roles need MFA is policy data. A role on the list with no factor is led into set-up instead of being refused, so enforcing it never locks the last administrator out.
- **ADR-66 The sign-in routes are not behind the feature flag.** `AUTH_MODE=iam` is the switch for sign-in itself; a per-company flag cannot decide how someone who is not yet known signs in. The flag hides the account and administration screens.
- **ADR-67 A thin user store until 02.03.** `iam_users` holds just enough to sign a person in. It is replaced by the user master, and `iam_credentials` keeps its `user_id` meaning.
- **ADR-68 One description drives the organisation lists.** `org/entities.js` declares each entity once; the service, validators and routes are generic over it. Eight entities would otherwise be eight copies of the same create, edit, deactivate and list code.
- **ADR-69 Activation and geofence changes are controlled; drafts are not.** A project or site is created as a draft and edited freely; becoming active, and any later geofence change, need approval. This keeps set-up fast and keeps live attendance fences under maker-checker, and a direct edit is refused rather than silently queued.
- **ADR-70 Effective dates in their own table, current holder mirrored.** `org_assignments` keeps who held a role from when to when; the entity row holds the current holder so every list and join stays a plain read. A future change waits (`applied = 0`) and a daily job applies it.
- **ADR-71 Deactivation blockers are a registry.** The part that owns the open records (attendance, stock, billing) registers a blocker for the entity; this part does not read other modules' tables. Until they exist only the built-in blockers apply, and the registry is how BR-03 stays true as modules arrive.
- **ADR-72 The geofence arithmetic is shared.** `src/shared/geo.js` is used by the server and the browser editor, so what the editor accepts is exactly what the server accepts and what the test button says is what attendance will later decide.
- **ADR-73 Company records are explicit.** A company must exist as a record before its data can be added (a clear refusal otherwise). The system administrator sees every company and creates new ones; everyone else sees their own. Company 1 is seeded.
- **ADR-74 The user record is completed in a one-to-one table.** `ADD COLUMN` cannot be written idempotently in SQLite and would alter a locked table, so the new fields live in `iam_user_profiles` with real foreign keys, backfilled for existing users. `iam_users` keeps its status check and every part-02.01 query unchanged.
- **ADR-75 Sign-in status and lifecycle are kept apart.** `status` answers "may sign in", `lifecycle` answers "where is this person in joining or leaving". One function changes both, so they cannot drift.
- **ADR-76 No access without an approved role, enforced by one gate.** An actor with no roles is flagged and a single middleware refuses everything outside a short list, rather than each route being asked to check. A new module is closed to such a person by default.
- **ADR-77 One account per person for good.** Contact details stay unique across all companies and a deactivated person keeps the account, so a rehire is a reactivation (returning with no role) and history stays on one record.
- **ADR-78 Granting a role is approved, taking one away is not.** Adding access goes through the approval chain; removing it only lowers access, so it is immediate and audited. A deactivated person's roles are removed so reactivation cannot silently restore access.
- **ADR-79 Invitation links are shown to administrators only outside production.** In production an administrator can never see a link, so they cannot accept an invitation in someone else's name.
- **ADR-80 Grants are computed once per request and carried on the actor.** Every layer asks the same object, so the page, the route, the service and the list query cannot disagree. Hand-built actors (jobs, tests) fall back to the role templates in code.
- **ADR-81 A scoped grant is honoured only by code that looks at the record.** The plain permission check means the whole company. This is deliberate: it makes a scoped assignment safe by default, because a module that has not been taught about scope simply refuses it instead of quietly widening it.
- **ADR-82 System roles are code, stored for the engine.** Templates live in `templates.js` (reviewed with the code, one place to change) and are seeded as locked rows; custom roles are data changed only by an approved request. A template change reaches the database at the next start.
- **ADR-83 Deny beats allow.** A deny in any role held, within its scope, removes the permission whatever another role allows (BR-01), and the explainer names the role that denies.
- **ADR-84 The nine old roles are aliases, and their old access is frozen.** Nobody's role code changes. The table of what each could do before is kept unchanged as the "before" of the comparison, so a later template edit cannot hide a regression.
- **ADR-85 Roles stored on the user remain valid.** The role list of part 02.03 is treated as company-wide assignments with no dates, and the engine reads it with the assignment table, so no user needed migrating and nothing could be lost in a migration.
- **ADR-86 Field masks are by role, most open wins.** A person who holds a role that shows a field sees it; otherwise the field's own default (partly shown or hidden). This matches how roles combine everywhere else.
- **ADR-87 Thirty seconds of caching, immediate on the instance that made the change.** A shared cache or an event per change was not needed to meet 60 seconds, and the in-process clear keeps the common case (an administrator's own session) exact.
- **ADR-88 A rule names two sides and how they meet.** A rule is two lists of patterns (a `*` stands for any text) and a scope in which they must not meet: the person (permissions held), the document, the vendor, the period or the project. One engine serves both preventive and detective checks, so a rule is written once. Severity decides the response: block (stop it, name the conflict), warn (allow and record) or detect (record). Changes to a rule go through an approved request, the auditor or the director deciding, never the administrator who asked.
- **ADR-89 The check at assignment is "what the person would hold", never a guess from role names.** Before a role is given, the permission engine is asked what the person would hold with it (`extra` holdings, never cached) and the result is compared with what they hold now: only conflicts the new role introduces are charged to it, so a person who already had a conflict is not blocked from an unrelated role. The same check is made again when the request is approved, because what the person holds may have changed.
- **ADR-90 What people did is a ledger, kept in the approver's transaction.** Action rules compare what a person is about to do with what they already did to the same document, vendor, period or project. The ledger row is written in the same transaction as the act, so a rolled-back act leaves no row; a refusal is recorded after the rollback so the blocked attempt is not lost.
- **ADR-91 Elevation is a dated role holding the engine reads, and the clock ends it.** An approved elevation is a row with start and end times; the permission engine includes it while the clock is inside them and never caches an answer past the moment one starts or ends. Access therefore ends at the end time even if the expiry job has not run; the job only marks the row and publishes the event. An elevation must pass the same segregation-of-duties check as a permanent role.
- **ADR-92 Everything done while elevated is tagged by the request, not by changing every writer.** A middleware writes one log row per request made while a person holds an elevation, with the correlation ID; the audit trail now records that correlation ID by default, so every change made in those requests can be listed with the elevation.
- **ADR-93 A review campaign applies its decisions only when it closes, and cannot close while any line is undecided.** Reviewers certify or revoke lines freely until the close, so a change of mind costs nothing; closing applies the revokes in one transaction, never removes the last active system administrator, and checks everyone affected again for conflicts. A person never reviews their own access.
- **ADR-94 Dormant accounts are reported by default and suspended by policy.** Suspending people automatically is a decision a company makes with a parameter, not a default that could lock out a site. When on, it uses the same lifecycle change as a manual suspension, so sessions end and the history shows why.
- **ADR-95 The existing audit table is kept; the chain is beside it.** core_audit_log has been written by every part since 00.02 and the schema baseline forbids changing it, so each row gets a companion row in core_audit_chain (sequence, company, who and where from, field changes, hash). Old rows are chained once, in order, when the application starts, and stay readable.
- **ADR-96 The hash covers the row and the one before it, and the chain checks for gaps.** Each hash is SHA-256 over the audit row, its chain fields and the previous hash, with consecutive sequence numbers. Changing a row, deleting one, inserting one outside the service or removing the triggers is each reported, with the entry where it was found.
- **ADR-97 Append-only is enforced by triggers and proved by the chain.** The triggers refuse UPDATE and DELETE on the audit tables for every connection. Because SQLite has no roles, the chain is the real evidence: the nightly check reports a break as a critical security event once for each new break.
- **ADR-98 Security events come from the domain events, in the same transaction.** publishEvent writes the matching security event with the event, so every module and parts 02.01, 02.04 and 02.05 are covered without each calling a logger, and an event exists only if its change committed. Failed sign-ins, refused requests and sensitive exports are written where they happen.
- **ADR-99 Sensitive values are masked when the diff is written, not only when it is read.** A sensitive field shows that it changed but never its old or new value in the diff; older raw columns are masked on the way out. A reader of the audit trail therefore never needs to be trusted with a mobile number or an account number.
- **ADR-100 History is for people who may see the record.** The History tab of a record needs the right to view that kind of record (or the auditor's right); an unknown kind of record needs the auditor. Every query is limited to the company.
- **ADR-101 Retention seals months; it never deletes.** The application has no delete path to the audit trail at all. A sealed month records its range, size and closing hash and can be exported; whether to move old months to cold storage is a deployment decision.
- **ADR-102 Routes are declared in one reviewed file, and the application checks the file against itself.** Every route has a line in `platform/security/route-policy.js`: its guard (permission, own account, record rules, public, infrastructure), the permission, scope, rate-limit class and whether it is audited. The application lists its own routes at start-up and compares; an undeclared route stops a staging or production start and fails CI. One file is what a reviewer reads to see who may call what.
- **ADR-103 The permission at the door is checked before the route runs, and again in the service.** A route declared with a permission is closed to anyone who holds none of its permissions, before any handler or validation runs, so a new route cannot be left open by forgetting a guard. The service still checks, with scope, because jobs and other services call it without HTTP.
- **ADR-104 The self-test is the evidence that the declarations are true.** The registry page runs every non-public route with no sign-in (must be 401) and with a person holding no permission (a permission route must be 403) and stores each result. A wrong declaration shows as a failure; the test also runs in CI.
- **ADR-105 Headers, CORS, CSRF and rate limits are a baseline, not a feature flag.** They protect every company and cannot be switched off for one. The feature flag `ff.iam.p0207` gates the central permission check, the registry and settings pages and the export controls. The values themselves are settings changed by an approved request.
- **ADR-106 A content security policy that allows only our own scripts; styles may be inline.** React sets style attributes, so `style-src` allows inline styles; `script-src` is `self` only, and a settings change that would allow inline or eval scripts, or drop `frame-ancestors`, is refused by validation.
- **ADR-107 Rate limits are per address and per person, by class of request.** Sign-in and second-step requests have their own, stricter class; exports too. The count is a sliding minute in memory (D-107). The first refusal in a window is a security event; the 429 says how long to wait.
- **ADR-108 A bulk export of people needs approval once, for exactly what was approved.** Above the threshold (1,000 by default) the request goes to the HR manager or the director; the approval is the requester's, is tied to the report and its filters, and is used once. Every export is in the audit trail and, for personal data, the security log.
