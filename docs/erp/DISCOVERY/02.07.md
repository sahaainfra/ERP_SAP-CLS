# Discovery note 02.07

Inspected: the application has an authentication step (02.01) and a permission engine (02.04), each route guards itself with `requirePermission` in its route line or `assertPermission` in its service (about 270 routes, no list of them anywhere), three static security headers, no content security policy, no CORS handling beyond the browser default, a CSRF header check only on the refresh and logout routes, a per-address limit of 30 a minute on the sign-in routes written inside the iam module, no rate limiting elsewhere, connector credentials encrypted under `VAULT_KEY` with no rotation procedure, a secret scan in CI, `npm audit` and CodeQL in CI, no socket server, no Dockerfile, no threat model and no server-side export (searched: core_route_registry, pipeline, registry, route, secret, helmet, csp, cors, csrf, rate, socket.io, export). Parts 02.04 and 02.06 are built and accepted.

| Requirement | Existing | Decision | Where |
|---|---|---|---|
| FR-01 route registry: permission key, scope resolver, validation schema, rate class and audit flag for every route; CI fails if a route lacks a declaration | Guards inside each route or service; no list | New | `platform/security/route-policy.js` (278 lines), `routes.js`, `registry.js`, `core_route_registry`, `npm run erp:route-check` in the regression and CI |
| FR-02 one pipeline for REST, sockets and jobs acting for users | Authenticate step only | Extend | central Authorise stage (`policy.js`), `authorise`, `validate` and `audit` middleware, room guard for sockets (`rooms.js`), `actAs` for jobs |

Departures from the pack: the policy was drafted from the source and then proved by the self-test (D-111); there is no socket server or Dockerfile to attach controls to yet (D-109, D-110); rate counts are per process (D-107); server-side exports exist for people's records only (D-113).
