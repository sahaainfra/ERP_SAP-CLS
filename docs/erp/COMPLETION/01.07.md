## 1. Discovery summary
The application had a request logger with the raw user name, a correlation ID middleware, health endpoints, the event and job monitor of 01.04, and a client API client that sends a correlation ID. It had no redaction, no metrics beyond event and job counts, no tracing, no browser reporting, no objectives, no alerts and no load test. Decision per requirement: `docs/erp/DISCOVERY/01.07.md`. Departures from the pack: the OpenTelemetry SDK is not installed, so the application has its own tracer with W3C trace context and OTLP/JSON export (D-046); email and WhatsApp cannot be sent because no notification engine exists (D-047); login, attendance, DPR, purchase order and payment have no routes yet, so their objectives show "no data" (D-049).

## 2. What was built
- **Tables** (migrations `20261030000018` and `20261030000019`, up and down): `core_slo_definitions`, `core_alert_rules`, `core_alerts`, `core_metric_samples`, `core_client_events`; flag `ff.core.p0107` (default OFF, ON in development and test).
- **Logs**: every entry is redacted before it is written (secret keys fully, identifiers keep four characters, document content omitted, patterns removed from free text); correlation ID and a `u_` pseudonym of the user on every line; request line has route pattern, module, status, duration.
- **Correlation**: the ID travels browser, request, event envelope, consumer, job and back into log lines; the trace follows the same path.
- **Tracing, metrics, database instrumentation**: spans per request, query, consumer and job; per-minute histograms by route pattern; slow-query record; cache hit rates; `GET /metrics` in Prometheus format (token or `core.ops.view`).
- **Objectives and alerts**: eight journeys with error budget and burn rate; eight alert rules checked every minute with open, resolve, cooldown and de-duplication; sending is pluggable, none connected.
- **Maker-checker**: changes to an objective or alert rule are requests (ITADM asks, SYSADM approves) and audited.
- **Browser reporting**: script errors, rejected promises, failed API calls (network, 5xx) and page-load time, de-duplicated, batched, redacted on the server, 60 a minute per user.
- **Page**: Operations Health (Administration > Operations, `/admin/operations/health`): tiles, objectives with error-budget bars, alerts and incidents, routes, slow queries, alert rules, traces with waterfall, follow-a-correlation-ID, baseline, "force a test error".
- **Baseline**: `npm run erp:perf-baseline` (nine journeys, 20,000 documents, 20,000 bills, 100,000 events); stored in `docs/erp/perf/baseline.json`.
- **Roles**: SYSADM `core.ops.view`; ITADM `core.ops.view` and `core.ops.manage`.
- Docs: `ARCHITECTURE.md` section 16, `DECISIONS.md` ADR-49 to ADR-54, `DEFECTS.md` D-044 to D-051, `DB_CHANGES.md`, `DB_BASELINE.md`, `openapi.yaml`; `schema/baseline.json` re-locked.

## 7. How to verify manually
1. `npm run build`, `npm start`, role ITADM, Administration > Operations > Operations Health.
2. Press "Force a test error": a correlation ID appears. Paste it under "Follow a correlation ID": log lines, the event, the job and the trace waterfall are listed.
3. Alert rules: "Request change" on error_spike; as SYSADM approve it under Approvals; the rule changes.
4. `GET /metrics` with header `x-health-token`, or as a signed-in ITADM.
5. `npm run erp:perf-baseline -- --compare docs/erp/perf/baseline.json` to compare a new run with the stored baseline.
6. `NODE_ENV=test node --test tests/observability.test.js tests/ops-observability-api.test.js`; `npm run erp:regression` runs everything.
