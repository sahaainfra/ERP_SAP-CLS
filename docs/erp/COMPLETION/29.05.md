## 1. Discovery

Every kind of legacy data already has a loader in its owning module. The cockpit plans, maps, trials, reconciles and signs off around those loaders. See the [discovery note](../DISCOVERY/29.05.md).

## 2. What was built

The page is `/admin/data-migration` (**Administration → Migration Cockpit**): a board.

**Tiles**: objects, signed off, loaded, and the cut-over state.

**Lanes**: Planned → Trial loads → Waiting for sign-off → Signed off → Loaded.

Selecting an object opens its panel:

- **Plan (FR-01)**: the migration lead (ITADM, SYSADM) adds an object with its code, name, kind of data, phase (masters, open documents, balances), sequence and owner role. The kind is an import type of the Excel engine (the 29.04 templates), the opening trial balance or opening stock.
- **Mapping workbook (FR-02)**:
  - legacy column names to columns;
  - for each column, legacy codes to new codes, upper case, a default when blank, and dropping the row when blank.
  - Each save is a new version, and voids the trials and any sign-off.
  - The workbook downloads as Excel.
- **Loads (FR-03, FR-04)**: the owner uploads or pastes the legacy extract (CSV) with the legacy controls: record count; total debit and credit for the trial balance; stock value.
  - **Trial load**: the real load runs through the owning service, as the person, inside a savepoint. It is reconciled and then rolled back, so nothing is left but the run.
  - **Reconciliation**: rows loaded; for the trial balance, every account tied out to the legacy closing plus total debit and credit; for stock, lines and stock value. Each row shows legacy against migrated, with the differences in red.
  - **Final load**: kept only if it reconciles; otherwise it is rolled back (the rollback point).
  - **Delta load**: skips records that already exist.
- **Sign-off (FR-05, BR-01)**: after two passed trials on the current mapping, the lead asks for sign-off. The owner role signs, then the CFO for financial objects (opening trial balance, opening stock, finance masters). The final load needs that sign-off, the cut-over freeze, and every earlier phase loaded.
- **Cut-over runbook (FR-04)**:
  - a freeze window and rollback point;
  - eight steps to tick, each with who and when;
  - start the freeze, close the cut-over.

Migration is desk work: the page says so on a phone, and the lanes stack. Labels are en/hi/te (area `mig`).

**Permissions**:

| Role | Grant |
|---|---|
| ITADM, SYSADM (migration lead) | Plan, map, ask for sign-off, cut-over |
| Module owners (ACCMGR, FINEX, STOREMGR, HRMGR, PROCMGR, CFO and others) | Run loads (each load also needs the data's own permission); sign off by chain role |
| AUD and the other module roles | Read |

## 6. Known limitations

D-793:

- Trials run in the same database, rolled back.
- No AP/AR open-item loaders, so no ageing reconciliation.
- The opening journal is then posted through the journal approval.
- Duplicates are resolved in 06.01.
- The whole-database restore point is the 29.06 backup.

## 7. How to verify manually

1. In a test company, set `ff.admin.p2905`.
2. As ITADM, open **Administration → Migration Cockpit**. Plan **OB-TB**: Opening trial balance, Balances, owner ACCMGR. In its mapping, map the legacy column names and legacy account codes.
3. As FINEX, paste the legacy trial balance and **Run trial load** twice. Both pass, and no journal exists.
4. As ITADM, **Ask for sign-off**. ACCMGR, then the CFO, sign off.
5. As ITADM, plan the cut-over and **Start the freeze**. As FINEX, run the **Final load**. The opening journal's balances equal the legacy closing.
