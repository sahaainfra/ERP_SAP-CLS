## 1. Discovery summary
After 02.02 users were a thin store (D-059): a script created them, there was no lifecycle, invitation, employee link, department, profile, user page or import. Sign-in, sessions and MFA (02.01) and the organisation master (02.02) exist and were called, not copied. The employee master (07.01) and the role engine (02.04) do not exist, so the employee link is a code (D-076) and roles are granted through the interim approval engine (D-077). Decision per requirement: `docs/erp/DISCOVERY/02.03.md`. Departures from the pack: the new user fields live in a one-to-one table, not new columns on `iam_users` (ADR-74); numbering (01.03) and the calculation engine (01.06) are not used because nothing here needs a document number or a calculation.

## 2. What was built
- **Tables** (migrations `20261030000026` and `20261030000027`, up and down): `iam_user_profiles` (lifecycle, type, language, employee code, department, home project, photo and signature files, preferences; backfilled for existing users), `iam_invitations`, `iam_role_grants`; flag `ff.iam.p0203` (OFF by default, ON in development and test). No existing table altered.
- **Lifecycle**: Invited, Onboarding, Active, Suspended, Deactivated. One function changes it and keeps the sign-in status in step.
- **Invitations**: by email, text or WhatsApp through the integration hub; only the token hash is stored; resend replaces the link (one per 30 seconds, five per 24 hours); seven days, once; a daily job marks expired ones. The person sets a password on the invitation page and becomes Onboarding, or Active if a role is already approved.
- **Restricted onboarding state**: a person with no approved role gets 403 `ONBOARDING_RESTRICTED` on every route except their profile, sessions, devices, password change, session summary, feature-flag lookup and the document service. They see a welcome page, their profile and their security pages; the menu appears when a role is approved, without signing in again.
- **Role requests**: request type `user_role_assignment` (SYSADM; privileged roles SYSADM then ITADM; from a system administrator ITADM, plus DIR for a privileged role); the requester cannot decide; applied in the approver's transaction; grant history kept. Taking a role away is direct and audited.
- **Deactivation**: a check lists approval requests the person raised, approval steps only they can decide, organisation roles and items other modules register; a successor takes over the movable ones; sessions end at once; roles are taken away; history stays. The last active system administrator and one's own account are protected.
- **One account per person**: email, mobile (stored as +91XXXXXXXXXX), username and employee code unique; the invite form warns while typing; a deactivated person keeps the account (reactivate, returning with no role).
- **Import and bulk**: CSV with row-level errors (check first; a wrong row stops the whole file unless "only the valid rows"); bulk invite and suspend with a result per person.
- **Pages** (flag `ff.iam.p0203`): Users (search, filters, sort, column chooser, saved views, bulk actions, CSV export, invite and import dialogs), a page per person (details, assignments, sessions, login history, approvals, timeline), My Profile (name, language, theme, notification choices, photo and signature through the document service), the welcome page, and the invitation page.
- **Roles**: SYSADM and HRMGR manage; ITADM views and suspends; everyone has their own profile. The mobile number is masked for a role that only views.
- **Events**: `iam.user.created|updated|invited|activated|suspended|reactivated|deactivated|roles_changed|profile_updated|imported`.
- Docs: `ARCHITECTURE.md` section 20, `DECISIONS.md` ADR-74 to ADR-79, `DEFECTS.md` D-076 to D-082 (D-059 closed), `DB_CHANGES.md`, `DB_BASELINE.md`, `openapi.yaml`, `.env.example` (`APP_URL`); `schema/baseline.json` re-locked (224 objects; 205 unchanged, 19 new).

## 4. Tests
- Unit, API, permission and contract: 471 tests, all passing (`npm test`, inside the regression). New in this part: 20 in `tests/users-api.test.js`. Three earlier tests were updated for this part (ITADM permission list, migration down-count, and a password in a test file moved behind a variable for the secret scan).
- E2E: 154 tests (77 on desktop 1280x800 and 77 on mobile 360x740, real Chrome), all passing in the full regression; 6 are new (users list, import and deactivation; a read-only role; the invitation to access).
- Full regression `npm run erp:regression`: PASSED (lint, type check, tests with coverage, coverage gate, migration check, schema lint, integrity, schema-diff, golden outputs, secret scan, build, E2E).
- Performance, measured in memory on 100,000 users: a list page 95 to 300 ms at the median and at most 310 ms at the 95th percentile (target 500 ms); search by name or employee code the slowest at about 300 ms; a duplicate check 0.3 ms; one user 0.5 ms.
- Behaviour changes to earlier parts: `.actions` now wraps (buttons that ran off a 360 px screen); `GET /iam/me` always refetches on page open and also returns the new profile fields; the shell hides the project switcher for a person in onboarding.
- Flaky by nature, not changed: the sign-in screen allows 30 attempts a minute per address, so two sign-in-heavy specs back to back can hit it; the new spec waits and retries.
- Not run: GitHub CI, a real email, SMS or WhatsApp gateway, PostgreSQL.

## 5. Data changes
Two migrations (three tables, one index and a backfill of one profile row per existing user; flag seed), tested up, down and re-up. No existing object altered or dropped.

## 6. Known limitations / deferred items
D-076 (employee link is a code until 07.01), D-077 (interim approval chains, no scope by project or site), D-078 (CSV only, 2,000 rows), D-079 (checklist gaps: XLSX/PDF, Hindi, saved views per browser), D-080 (service accounts cannot authenticate; portal users have no portal role), D-081 (invitations checked only against the sandbox provider; link lifetime is a constant), D-082 (approvals in the browser test are made by API; performance measured in memory; second step asked at first sign-in).

## 7. How to verify manually
1. Start the sample sign-in server (people seeded with password `Excavator-Test-9-Pw`; it shows the invitation link on screen because it runs in development): `npm run build`, then `AUTH_MODE=iam NODE_ENV=development PORT=3000 DATABASE_PATH=data/e2e-iam.sqlite node scripts/e2e_iam_server.mjs`, and open http://localhost:3000.
2. Sign in as `hr-d` (HR manager). Administration > Users > Invite user: type a name and an email, leave "Send the invitation now" ticked. Try the same email again to see the duplicate warning. The notice shows the development link.
3. Open that link in a private window: choose a password (a common one such as `password123` is refused). Sign in as the new person: only Welcome, My Profile, Security and My Sessions are offered, and typing `/admin/users` shows the welcome page.
4. As `hr-d`, open the person > Request a role > Project manager. Sign in as `approver-d` (system administrator; the sign-in asks to set up an authenticator first) and approve it under Approvals. The new person's menu appears after a refresh.
5. As the new person: My Profile > change language and theme, upload a photo.
6. As `hr-d`: Users > Import users > paste a few rows including a duplicate email > Check the file > read the row errors > import only the valid rows. Select two people > Send invitations; select one again straight away to see the 30-second pause refused.
7. Open the new person > Deactivate. Make `hr-d` the head of a department first (Organisation) and deactivate `hr-d`'s colleague to see the hand-over list and choose a successor.
8. `NODE_ENV=test node --test tests/users-api.test.js`; `npx playwright test e2e/users.spec.js`; `npm run erp:regression` runs everything.
