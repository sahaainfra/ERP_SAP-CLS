## 1. Discovery summary
`core_audit_log` had been written by every part (121 call sites) but nothing stopped an UPDATE or DELETE, entries were not linked, nothing recorded where a request came from, there was no viewer, no record history, no export logging, no retention, and security history lived only in sign-in events. Decision per requirement: `docs/erp/DISCOVERY/02.06.md`. Departures from the pack: no table partitions (SQLite), so finished months are sealed and exportable instead (D-101); append-only is enforced by triggers, with the hash chain as the evidence if someone with the database file removes them (D-100); notifying administrators of a tamper alert waits for 04.06 (D-105).

## 2. What was built
- **Audit service** (`platform/audit`): `writeAudit` (unchanged for its 121 callers) and `record(db, entity, id, action, before, after, reason, context)` write the row and a chained companion in the same transaction. The existing table is not altered (ADR-95): `core_audit_chain` holds sequence, company, person, address, device, field changes, previous hash and hash.
- **Field-level diff**: technical columns ignored; a sensitive field shows that it changed but never its values; older raw columns are masked on the way out. The request pipeline now supplies company, person, address and device to every entry.
- **Hash chain and verification**: SHA-256 over the row, its chain fields and the previous hash, with consecutive sequence numbers. `core.audit_verify` runs nightly (and "Verify now"); it finds a changed row, a removed row, a row inserted outside the service and removed protection. A break is a critical security event and the event `core.audit.tamper_detected`, once for each new break.
- **Append-only**: triggers refuse UPDATE and DELETE on the audit log, its chain, the security events and the sealed segments.
- **Security event log** (`core_security_events`): sign-in, MFA and PIN failures; refused requests; sensitive exports; and, through `publishEvent` in the same transaction, sign-ins, suspicious sign-ins, lockouts, token reuse, password and MFA changes, role and assignment changes, SoD rule changes and violations, elevation, access reviews, dormant suspensions and audit tampering, each with a severity.
- **Export and print logging**: `POST /core/audit/export-log`; every CSV export and every print from the browser is recorded with the report, format, rows and filters.
- **Retention**: `core.audit_seal` seals each finished month (range, size, closing hash); sealed months are listed, exportable as NDJSON against the closing hash, marked past retention under `core.audit.retention_months`, and never deleted.
- **Legacy**: old audit rows are chained in order at start-up; old sign-in failures are copied once into the security log.
- **API** (`/api/v1/core`): `GET /audit`, `/audit/history`, `/audit/entities`, `/audit/verification`, `POST /audit/verify`, `/audit/segments`, `/audit/segments/{period}/export`, `POST /audit/export-log`, `GET /security-events`.
- **Pages**: Audit Explorer (filters by person, record kind, record, action and date; record timeline; entry details with correlation ID and hash; chain status; verify now; CSV), Security Events (severity tiles, critical banner, filters, CSV) and the `RecordHistory` component (`client/platform/audit`), used on the SoD rule page.
- **Roles**: AUD reads the trail and verifies; SYSADM, ITADM and AUD read security events; anyone who may view a kind of record sees its history, masked, in their company.
- Sample documents now write old and new status to the audit trail so their entries carry a real diff.
- Docs: `ARCHITECTURE.md` section 23, `DECISIONS.md` ADR-95 to ADR-101, `DEFECTS.md` D-100 to D-106, `DB_CHANGES.md`, `DB_BASELINE.md`, `openapi.yaml`; `schema/baseline.json` re-locked (291 objects; 275 unchanged, 16 new).
