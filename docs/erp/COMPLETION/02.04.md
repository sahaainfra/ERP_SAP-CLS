## 1. Discovery summary
Permissions came from one constant table of nine roles, a person's roles were a list on the user record, scope was the company only (D-060, D-068) and two fields were masked by hand-written code. There was no registry, role table, assignment, explainer or comparison. Decision per requirement: `docs/erp/DISCOVERY/02.04.md`. Departures from the pack: the approval authority of a role is the catalogue's wording plus a confidentiality clearance, with money bands left to the approval matrix (D-085); the salary and bank account fields are declared for the employee master and demonstrated with a declared field, because the master does not exist (D-088); no record type has an owner or a confidentiality level yet, so the reporting-hierarchy rule and the clearance check are built and tested but wait for those records (D-084).

## 2. What was built
- **Engine** (`platform/authz`): grants are computed once per request and carried on the actor; `check(actor, permission, record)`, `scopeFilter(actor, permission, columns)` and `mask(actor, entity, record)`. Deny by default; a deny in any role held beats an allow; grants within a scope are a union; a record above a role's clearance is refused. Cached 30 seconds, cleared at once by the instance that makes a change. If the database cannot answer, the system roles' code templates answer, so health routes still report the outage.
- **Scope**: a role is held for the whole company or for branches, departments, projects, sites or the person's own records, from a date to a date. The plain permission check means "the whole company": a role granted for one project never opens a route that does not look at the record. The organisation projects, sites and cost centres, the shell switcher and the sample documents honour scope now.
- **Roles** (`iam_roles` and friends): the 44 templates of the role catalogue (23 owner roles, 17 supporting, 4 external), seeded as locked system roles, each with its grants, masks, clearance and approval-authority wording. Clone one into a custom role (a draft); what a custom role grants, its masks and clearance, and its activation or retirement change only by an approved request (IT administrator, plus the director when the role holds a sensitive permission). A role in use cannot be retired.
- **Assignments**: a request (system administrator; a privileged role then the IT administrator or the director; a finance approver or the Super Admin role needs the director; a system administrator asking cannot approve their own request). Approved assignments take effect on the person's next request. Ending one is immediate and audited. A daily job moves people between Onboarding and Active as dates pass.
- **Masks**: the registry of sensitive fields, rules by role (hide, partly show, show in full; the most open rule among the roles held wins). The user's mobile number and a company's PAN now run through it.
- **Explainer and comparison**: for any person (and optionally a record) every permission with allowed or refused, the reason and the roles that grant or deny it; and a per-user comparison of the old nine-role access with the engine's, with lost and gained access both required to be empty.
- **Pages**: Roles (list, compare two, clone), Role (permission matrix by module, field masks, people holding it, approvals, details), Assignments (list and the assign form with a scope picker), Effective Permissions, Legacy Access Comparison; `useCan()`, `<Can>` and `menuFor` for the browser.
- **Roles**: SYSADM maintains roles and assignments; ITADM and DIR check; AUD reads; ITADM and DIR also see the pages.
- **Events**: `iam.role.created|changed`, `iam.assignment.created|ended`.
- Docs: `ARCHITECTURE.md` section 21, `DECISIONS.md` ADR-80 to ADR-87, `DEFECTS.md` D-083 to D-091 (D-060 and D-068 closed), `DB_CHANGES.md`, `DB_BASELINE.md`, `openapi.yaml`; `schema/baseline.json` re-locked (246 objects; 224 unchanged, 22 new).

## 4. Tests
- Unit, API, permission and contract: 487 tests, all passing (`npm test`, inside the regression); 16 new tests in `tests/authz-api.test.js` and `tests/access-client.test.js`. Earlier tests changed: the ITADM permission list, the migration down count, the chain a privileged role request now gets (`SYSADM` then `ITADM or DIR`).
- E2E: 162 tests (81 on desktop 1280x800 and 81 on mobile 360x740, real Chrome), all passing in the full regression; 8 are new (roles, assignments and reports, a read-only role, and a scoped person signing in).
- Full regression `npm run erp:regression`: PASSED (lint, type check, tests with coverage, coverage gate, migration check, schema lint, integrity, schema-diff, golden outputs, secret scan, build, E2E).
- Cross-checked while building: every earlier API and browser test passes against the engine unchanged apart from the three above, which is the evidence that nobody's access changed.
- Not run: GitHub CI, PostgreSQL, more than one server instance (the 30 second refresh is tested with a clock, not with two processes).

## 5. Data changes
Two migrations (six tables; flag seed), tested up, down and re-up. No existing object altered or dropped. System roles, their grants and masks and the old-role mapping are written at start-up from the code templates.

## 6. Known limitations / deferred items
D-083 (scope enforced on the organisation records and sample documents; each new module must call the engine), D-084 (reporting-hierarchy rule waits for records with an owner), D-085 (no money bands), D-086 (interim approvals), D-087 (checklist gaps), D-088 (only mobile and PAN are live masked fields), D-089 (30 second cache), D-090 (no break-glass session), D-091 (two ways to hold a company-wide role).

## 7. How to verify manually
1. Start the sign-in sample server (people with password `Excavator-Test-9-Pw`): `npm run build`, then `AUTH_MODE=iam NODE_ENV=development PORT=3000 DATABASE_PATH=data/demo-iam.sqlite node scripts/e2e_iam_server.mjs`, and open http://localhost:3000. Sign in as `approver-d` (system administrator; the first sign-in sets up an authenticator).
2. Administration > Roles: 44 system roles. Open `PM`: a locked permission matrix. Select `PM` and `HRMGR` to compare. Clone `PM` as `SITELEAD`, open it, click cells to allow, deny or clear, open Field masks and choose a rule for the employee salary, then Request activation.
3. As the IT administrator (`itadm-d`, authenticator on first sign-in) and the director (`dir-d`), approve the request under Approvals. Reopen the role: Active.
4. Administration > Assignments: give `PM` to `scoped-d` for one project (create two projects first as `pmx-d`, a project manager, under Projects & Sites). The request needs the IT administrator and the director. Sign in as `scoped-d`: Projects & Sites lists only that project; the other one gives "not found" by any route.
5. Administration > Effective Permissions: choose `scoped-d`, record type project and the other project's number: permissions such as managing it are refused with the reason; choose the assigned project: allowed, with the roles that grant it.
6. Administration > Legacy Access Comparison: "Clean", with a mapping table of the nine old roles.
7. `NODE_ENV=test node --test tests/authz-api.test.js tests/access-client.test.js`; `npx playwright test e2e/roles.spec.js e2e/zz-scope-isolation.spec.js`; `npm run erp:regression` runs everything.
