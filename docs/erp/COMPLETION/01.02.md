## 1. Discovery summary
The database layer had a migration runner, an up/down check, schema-diff and a restore point inside the deploy tool, and nothing else of what this part asks for. Decision per requirement: `docs/erp/DISCOVERY/01.02.md`. The one departure from the pack is ADR-14: money and quantities are stored as INTEGER minor units, because SQLite has no exact decimal type.

## 2. What was built
- **Tables** (migration `20261030000006`, up and down): `core_idempotency_keys`, `core_integrity_runs`, `core_backfill_runs`. Flag `ff.core.p0102` seeded by `20261030000007` (default OFF, ON in development and test).
- **Baseline and conventions**: `docs/erp/DB_BASELINE.md` (generated, checked in CI), `docs/erp/MIGRATIONS.md` (how to write a migration, back-fill, integrity rule, backup), `npm run migration:new` (writes a standard-compliant table), `npm run erp:db-lint` (standard columns, an index on every foreign key, integer money, `(company_id, doc_no)` key, every migration listed in `DB_CHANGES.md`, baseline up to date). Schema-diff baseline re-locked (18 objects).
- **Integrity suite**: seven checks (orphan foreign keys, duplicate business keys, header totals against lines, unbalanced journals, negative quantities, rows without a company, invalid statuses), found by convention and extended through `integrityRegistry.register`. `npm run erp:db-check` (`--fresh`, `--db`, `--record`, `--json`, `--fail-on`); a Critical failure exits 1 and is a stage of `erp:regression`. API: `POST /api/v1/core/integrity/run` (ITADM), `GET .../integrity/summary` and `.../integrity/runs` (ITADM, SYSADM). Each run is stored (one row per check), audited, and queued as the event `core.integrity_run.completed`.
- **Page**: Administration > Data Health, "Database Integrity Report": summary tiles, one row per check with severity, result, counts, failure samples, a history drill-down per check, "Run checks now" (ITADM; disabled with a reason for SYSADM), CSV export. Behind `ff.core.p0102`; navigation entry hidden without permission or while the flag is OFF.
- **Idempotency**: `idempotency(db, { required })` middleware. Same key and body replays the stored response; same key with a different body is 422; a still-running request is 409; only 2xx responses are stored; keys are scoped to user and endpoint; expired keys are purged. Applied (optional key) to the flag change and the integrity run; the client sends a fresh key per mutation.
- **Company scope**: `companyScope`, `findScoped`, `listScoped` (deny by default, bounded lists).
- **Back-fills**: `runBackfill` (resumable, logged, atomic per batch) and `npm run backfill`.
- **Backup and restore**: `npm run db:backup` (file + manifest with integrity result and per-table checksums), `npm run db:restore` (verify, restore, re-check; refuses to overwrite without `--yes`), `npm run db:rehearse`.
- **Test data**: `npm run erp:gen-data` (deterministic, separate `perf_*` tables, integrity suite and query timings).
- **Money units**: `toUnits` and `fromUnits` in `src/shared/money.js`.
- Docs updated: `ARCHITECTURE.md` (section 10 Database foundation), `DECISIONS.md` (ADR-14 to ADR-22), `DEFECTS.md`, `DB_CHANGES.md`, `openapi.yaml`.

## 7. How to verify manually
1. `npm install`, copy `.env.example` to `.env`, `npm run build`, `npm start`, open http://localhost:3000.
2. Role bar: ITADM. Open Data Health: seven checks listed as "Not run yet" with a "No integrity run yet" panel. Click "Run checks now": six show "Nothing to check yet" (there are no business tables yet), one shows "Passed", none fail; the last-run line shows your name.
3. Click History on a check: the nested table lists its runs. Click Export CSV.
4. Switch to SYSADM: the report is readable and the Run button is disabled with the reason as its tooltip. Switch to PM: no-access message, no nav link.
5. See a violation caught: `NODE_ENV=test node --test tests/integrity.test.js` seeds one of each kind; or build a database with `npm run erp:gen-data -- --documents 500 --out data/perf.sqlite`, change one `perf_documents.total_amount` in it, and `node scripts/db_check.mjs --db data/perf.sqlite` exits 1 naming the document. (The perf tables are not registered in the application, so use the test for the application's own rules.)
6. `npm run db:rehearse` prints the backup and restore timings and "Checksums identical after restore".
7. `npm run migration:new -- demo_table --table demo_things --numbered --money total_amount` creates a migration pair (delete it afterwards); `npm run erp:db-lint` and `npm run erp:migration-check` accept it once it is listed in `DB_CHANGES.md`.
8. Send the same flag change twice with one `Idempotency-Key` (see `tests/idempotency.test.js`): the second answer carries `Idempotency-Replayed: true` and nothing is applied twice.
9. `npm run erp:regression` and open the report.
