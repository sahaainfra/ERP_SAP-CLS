## 1. Discovery summary
The outbox table and `publishEvent` already existed (part 00.02) and every module calls it, but nothing read the outbox: no relay, consumers, retries, dead letters, replay, jobs or scheduler. Decision per requirement: `docs/erp/DISCOVERY/01.04.md`. Departures from the pack: per-consumer delivery state is in a new `core_inbox` rather than extra columns on `core_outbox` (the pre-existing table is not altered, ADR-29); no message broker and no Socket.IO relay (D-026, ADR-32).

## 2. What was built
- **Tables** (migrations `20261030000011` to `20261030000013`, up and down): `core_event_types`, `core_inbox`, `core_jobs`, `core_schedules`, `core_projection_event_counts`; flag `ff.core.p0104` (default OFF, ON in development and test); the change-request tables were rebuilt once without the request-type CHECK so schedule changes can use the approval engine (ADR-31).
- **Events**: standard envelope; catalogue of 24 core event types with versions and payload schemas, validated on publish and mirrored to `core_event_types`; relay (`relayOnce`), delivery with exponential back-off (30 s doubling to 1 h), dead letters after `maxAttempts`, re-drive and discard (audited, reason required), replay by type, date range, consumer and company with `ctx.replay` suppressing side effects, metrics (throughput, relay lag, delivery lag, dead letters, per consumer).
- **Jobs**: queue with atomic claim, progress, log, result, cancellation, retries with back-off, recovery of jobs left RUNNING by a dead worker, `core.job.completed` and `core.job.failed` events. Job types shipped: `core.event_replay`, `core.housekeeping`, `core.integrity_run`.
- **Schedules**: five-field cron in IST (shared with the browser's preview), seeded schedules `core.integrity_nightly` (01:30) and `core.housekeeping_daily` (03:00), compare-and-swap so one instance queues each slot, missed slots run once, changes through maker-checker (IT Administrator asks, System Administrator approves).
- **Workers**: the server starts the polling loops (`startWorkers`); one bus, runner and scheduler per database (`runtimeOf`).
- **Consumer in use (AC-01)**: `core.projection.event_counts` listens to the sample-document events and keeps a per-company count, which is also the read model replay rebuilds.
- **Pages** (behind `ff.core.p0104`): Events & Jobs Monitor (tiles with drill-down, consumers, busiest types, event log with masked data, catalogue, replay dialog), Dead-Letter Queue, Background Jobs, Scheduled Jobs (cron editor with next-run preview, pending requests with approve and reject). The monitor, queue and job lists refresh every five seconds.
- Docs updated: `ARCHITECTURE.md` (section 13), `DECISIONS.md` (ADR-29 to ADR-34), `DEFECTS.md` (D-026 to D-030), `DB_CHANGES.md`, `DB_BASELINE.md` (regenerated), `openapi.yaml`; `schema/baseline.json` re-locked with the new objects.

Three migrations (tables; flag seed; request-type rebuild), each tested up, down and re-up. Migration 13 rebuilds `core_change_requests` and `core_change_request_steps` with their rows, ids and indexes; its down migration restores the CHECK and removes `schedule_change` requests. `core_outbox` is untouched.

## 6. Known limitations / deferred items
D-026 (no Socket.IO or broker; polling), D-027 (one real consumer; replay is one job), D-028 (jobs run in the web process), D-029 (schedules cannot be created from the page), D-030 (console exports and languages; no browser re-drive test). D-022 (stand-in approvals) still applies to schedule changes. Handlers must be synchronous and must check `ctx.replay` before any outside effect.

## 7. How to verify manually
1. `npm install`, `npm run build`, `npm start`, open http://localhost:3000 (flag `ff.core.p0104` is ON outside production). Role bar: ITADM, open Operations.
2. Monitor: tiles show events in the last hour and day; the consumers table lists `core.projection.event_counts`; Recent events shows each event with its data masked (Show); the catalogue lists the event types.
3. Raise events: as SYSADM create a sample document through the API or the Company Settings page; within seconds the event appears and the consumer's processed count rises.
4. Replay: ITADM, Replay events, types `core.sample_document.*`, tick "Empty the consumer's projection first", add a reason. Open Jobs: the job runs to Done; open its log.
5. Dead letters: `NODE_ENV=test node --test tests/ops-api.test.js` creates a failing consumer, a dead letter, its masked view and the re-drive. The page shows the queue empty when nothing has failed.
6. Schedules: ITADM, Request change on a schedule, type a cron (the next five runs appear; an invalid one shows the error), send for approval. Switch to SYSADM: Approve; the schedule shows the new cron and next run.
7. `NODE_ENV=test node --test tests/jobs.test.js` runs the four-process proof that a slot is queued once.
8. `npm run erp:regression` runs everything.
