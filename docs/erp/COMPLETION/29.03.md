## 1. Discovery

The request pipeline (02.07) and the role engine already enforce permissions, so the public API is a gateway onto the internal routes rather than a second implementation. See the [discovery note](../DISCOVERY/29.03.md).

## 2. What was built

**The public API** is served at `/api/public/v1`:

- **Tokens (FR-02)**: `POST /oauth/token` implements OAuth2 client credentials (JSON, or a form with Basic auth). It gives a one-hour bearer token for the granted scopes, or fewer if asked.
- **Catalogue (FR-01)**:
  - items;
  - material requests (read and raise);
  - purchase orders;
  - daily progress reports;
  - device punches;
  - machine positions and telematics readings.
- **Each call**:
  - the gateway checks the token, version, deprecation, scope and the client's rate tier;
  - it then hands the request to the internal API as the client's service account. That account holds only its scopes' permissions, and only for its projects when it has them. So the same permission checks, validation, idempotency, read-only mode and audit apply (BR-01).
- **Deprecation**: `/v1/dpr` is deprecated. It answers with Deprecation, Sunset and Link headers, and will answer 410 after its sunset.
- **Bulk**: `/v1/bulk` takes up to 100 write calls. Each one goes back through the gateway with its own idempotency key, and the answer is 207 with each result.
- **Rate tiers (FR-05)**: Basic 60, Standard 300 and Premium 1,200 calls a minute, with RateLimit headers and 429 plus Retry-After.

**The page** is `/admin/api` (**Administration → API Clients & Webhooks**), with pill tabs:

- **Clients & keys (FR-02)**:
  - Create a service account with a role, scopes, tier, sandbox or live, and optional projects.
  - The role must hold every permission of the scopes, and an administrator role is refused.
  - The secret is shown once.
  - A client with a write scope waits for the director's approval (section 9).
  - **Rotate** gives a new secret and keeps the old one valid for 24 hours. **Revoke** ends every token and disables its webhooks.
- **Webhooks (FR-03)**:
  - Subscribe a client to events within its scopes, as exact types or `module.*`. The signing secret is shown once and stored encrypted.
  - A bus consumer queues one delivery per event, with the payload masked like every event.
  - A job posts each delivery with `x-signature` (HMAC-SHA256 over `<timestamp>.<body>`), `x-timestamp` and `x-delivery-id`. It retries six times with back-off and records every attempt.
  - **Send a test**; **Replay** a delivery.
  - The delivery log can be filtered and exported.
- **Developer portal (FR-04)**:
  - getting started;
  - each endpoint with curl, JavaScript and Python code;
  - **Try it**, which calls the real public API from the browser with a sandbox client's credentials;
  - how to verify a webhook, events by scope, versions, deprecation policy and changelog.
- **Usage (FR-05)**: calls, error rate, throttled calls and deliveries given up, by client and by endpoint.

Labels are en/hi/te (area `dev`).

**Permissions**:

| Role | Grant |
|---|---|
| ITADM | Manage clients and webhooks, portal |
| DIR | View, portal; approves write clients |
| AUD, SYSADM | View, portal |

## 4. Tests

`tests/admin-api-platform.test.js` has three tests, all passing:

1. **Tokens, scopes and portal**:
   - roles refused (a role without the scope's permission; an administrator role);
   - the secret is shown once;
   - tokens by JSON and by Basic form; a wrong secret and an unknown scope are refused;
   - the scope walk over the whole catalogue;
   - no token, a forged token, an unknown version, and an internal route that is not public;
   - the deprecation headers;
   - the portal and the usage counts.
2. **Write clients and the public write path**:
   - the director's approval;
   - the internal idempotency (the key is required, and a replayed key gives the first answer) and validation (an unknown machine);
   - the audit, made as the service account;
   - bulk: 207 with each result, and only write routes accepted;
   - the project scope;
   - the Basic tier's 429 and the usage count of throttles;
   - rotation with both secrets working, then revocation.
3. **Webhooks**:
   - scope and URL checks; the secret stored encrypted;
   - the test delivery and its signature;
   - a domain event through the bus: delivered once, only for its company and type, with sensitive fields masked;
   - a failure retried after its back-off; replay;
   - the log and its export; roles; disable;
   - 100,000 deliveries listing in under 500 ms.

`e2e/admin-api.spec.js` passes on desktop and mobile:

1. A sandbox client, and a write client approved by the director in the page.
2. A webhook and its signed test.
3. The portal's code and try-it (HTTP 200).
4. Usage.

## 6. Known limitations

D-791:

- The catalogue is fixed in code.
- The sandbox is a client environment, not a separate dataset.
- SDKs are snippets, not packages.
- Developers do not self-register.
- Rate limits are counted per process.
- A failing webhook is not disabled automatically.
- The lists have status filters only.

## 7. How to verify manually

1. In a test company, set `ff.admin.p2903` (and `ff.plant.p1707` for the telematics routes).
2. As ITADM, open **Administration → API Clients & Webhooks**. Create a client acting as PM with `plant:read`, and copy the secret.
3. `curl -X POST <host>/api/public/v1/oauth/token -u "<client id>:<secret>" -d grant_type=client_credentials`. Then call `GET /api/public/v1/telematics/positions` with the token; calling `/api/public/v1/items` gives 403.
4. Under **Webhooks**, subscribe the client to `plant.*` at a request-bin URL and **Send a test**. The request carries `x-signature`.
5. Create a client with `plant:write`. It waits until a director approves it.
