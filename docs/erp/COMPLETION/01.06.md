## 1. Discovery summary
Exact decimal arithmetic and money helpers existed (`decimal.js`, `money.js`) and the golden-output harness had one fixture, but there was no registry, no versioning, no trace, no unit conversion and no shadow comparison; part 00.01 had found no business calculations at all. Decision per requirement: `docs/erp/DISCOVERY/01.06.md`. Departures from the pack: the four built-in version 1 formulas are seeded active by the system (they are the code that already ran); formulas are global, not per company; the UOM master (06.02) and workflow engine (04.01) do not exist, so units live in two core tables (D-042) and activation uses the interim approval engine (D-043); a new sample bill is the first record routed through the engine because no real module exists yet (D-040).

## 2. What was built
- **Tables** (migrations `20261030000016` and `20261030000017`, up and down): `core_formulas` (with a trigger that refuses any change to a version that is no longer a draft), `core_calc_traces`, `core_calc_shadow_results`, `core_uoms`, `core_uom_conversions`, `core_sample_bills`; flag `ff.core.p0106` (default OFF, ON in development and test).
- **Calculation language** (`src/shared/calc.js`, shared by server and browser): exact decimals, text and yes/no values, arithmetic and comparison, `if`, round, min, max, abs, floor, ceil, percent, sum. No `eval`, no floating point, no loops. Inputs are checked by type and decimal places; outputs are rounded once by the formula's policy: half up, banker's (half even, for statutory figures), down or up. A formula's syntax, unknown names and outputs are checked before it is saved.
- **Engine** (`platform/calc`): `evaluate` resolves the version in force on a date or a pinned version, records a trace for a record, and runs any SHADOW version beside it; `convert` converts units. Built-in version 1 formulas: `boq.line_amount`, `tax.gst_split`, `stock.weighted_average`, `billing.net_payable`. The application refuses to start if a stored built-in differs from the code.
- **Versions and approval**: DRAFT, SHADOW, ACTIVE, RETIRED. Activation is a request that needs passing test cases, a date of today or later and the owner chain (project controls manager for BOQ; accounts manager for tax, billing and stores; IT administrator for core; the CFO as well for financial formulas). The previous version ends the day before the new one starts.
- **Units of measure**: item-specific factors beat generic ones for the same pair; chains such as BAG to KG (item) then KG to MT (generic) are computed as exact fractions and rounded once. Nineteen reference units and eleven generic factors are seeded.
- **Pages** (behind `ff.core.p0106`): Formula Registry (list, versions, expression, inputs and outputs, test bench with "Show calculation", drafting, shadow, activation request, units and conversions); Shadow Comparison Report (parameter panel, summary tiles, table of differences, CSV export, live shadow results); Sample Bills (amounts from the engine, Show calculation on each, recalculate, submit); Approvals (a stand-in inbox: approve or reject when it is your role's turn and you did not raise the request).
- **Roles**: SYSADM and PCMGR view the registry; only SYSADM drafts, starts shadow mode and asks for activation; new role PCMGR (also approves BOQ formulas).
- Docs updated: `ARCHITECTURE.md` (section 15), `DECISIONS.md` (ADR-42 to ADR-48), `DEFECTS.md` (D-038 to D-043), `DB_CHANGES.md`, `DB_BASELINE.md`, `openapi.yaml`, `CALCULATION_REGISTRY.md` (generated); `schema/baseline.json` re-locked; six golden outputs.

## 5. Data changes
Two migrations (tables and trigger; flag seed), each tested up, down and re-up. No existing object altered or dropped. The four built-in formulas and the reference units are inserted when the application starts (idempotent).

## 6. Known limitations / deferred items
D-038 (a division keeps 12 places; 3,000 random cases matched), D-039 (formulas edited as text and JSON; no import or export; no function-reference formulas), D-040 (only four calculations registered, only the sample bill calls the engine, no lookup tables or slabs), D-041 (report has no chart, XLSX, PDF, email or Hindi), D-042 (no UOM or item master; factors shared by all companies), D-043 (interim approvals, no delegation or SLA). Formulas are shared by all companies: one company's approved version applies to every company.

## 7. How to verify manually
1. `npm install`, `npm run build`, `npm start`, open http://localhost:3000 (flag `ff.core.p0106` is ON outside production). Role SYSADM, Formulas.
2. Open `tax.gst_split`: the version table, the formula text, the approval chain. In the test bench enter 1265.43, 18, intra and Calculate: the result and Show calculation list every step. Enter 1.234 as the taxable value: a clear error.
3. Units of measure: add a conversion BAG to KG of 50 for item CEMENT_1 (Add conversion), then convert 100 BAG to MT for that item: 5.000, via the item factor then the generic one. Convert MT to KG without an item: the generic factor.
4. Role PM, Sample Bills: create a bill (12.5, 101.2345, 18%); the amounts appear; Show beside any amount opens its steps and formula version. Submit it.
5. Role SYSADM, open `boq.line_amount`, New version: change the formula to `amount = round(quantity * rate, 0)`, add a test case (12.5 x 101.2345 = 1265.00), set tomorrow as the start, save. Start shadow mode, create bills as PM, open See the comparison: live results and a Compare run show every difference.
6. Request activation. Role PCMGR on Approvals: Approve; the version is still a draft. Role CFO: Approve. Now the version shows as future (it starts tomorrow) and version 1 ends today. A bill submitted before keeps version 1 when you press Recalculate.
7. `NODE_ENV=test node --test tests/calc-language.test.js tests/calc-engine.test.js tests/calc-api.test.js` and `npm run erp:golden`; `npm run erp:regression` runs everything.
