## 2. What was built

**Performance Test Results** (`/admin/performance-tests`) is a technical console:

- **Header:** the verdict: SLOs met or missed by the latest load run and soak.
- **Chart first:** p95 by SLO kind over the runs. Each point opens its run.
- **Key figures:** the latest load run, the latest soak (hours, memory growth), the burst target, peak memory.
- **SLOs:** the parameters, with a link to ask for a change.
- **Memory chart:** the server's memory over the selected run.
- **Selected run:** its journeys against their SLOs (cards on a phone, sticky total), with export in "…".
- **Runs:** filtered by profile and result.

**FR-01 Load models** (`scripts/load_test.mjs`):

- The real server (`src/server/index.js`) runs in its own process on a seeded SQLite file:
  - 20,000 documents;
  - 2,020 employees with accounts, deployed to a geofenced site;
  - 220 DPR sites.
- The server's memory is sampled from the operating system.
- Each virtual person calls from an address of their own, as phones on mobile data do.
- Models:

| Model | Load |
|---|---|
| USERS | 1,000 people opening lists and records, one request every 5–15 s |
| PUNCH_BURST | 2,000 punches in 60 s |
| DPR_BURST | 200 DPRs (in 60 s here; 30 minutes on site) |
| MONTH_END | 50 accountants on the attendance register, trial balance, daily summary and event log, while bills are posted through the calculation engine |
| REALTIME | a latency probe every 2 s |

- Profiles: `smoke`, `load`, `stress`, `soak`, `users` and `burst`.
- `LOAD_CPU_PROF=<dir>` writes a CPU profile of the server.
- `perf/k6/models.js` holds the same models for a staging installation, and `perf/k6/summary.mjs` turns k6's summary into a report.

**FR-02 CI and SLOs:**

- On every change, CI runs `perf-smoke`, and `scripts/perf_verdict.mjs` fails the build on a missed SLO.
- `.github/workflows/perf.yml` runs the load every night and the 8-hour soak every Sunday, and records them where `ERP_PERF_URL` is set.
- A run is recorded with `POST /tst/perf/runs` and judged by the installation against parameters that change only through the 29.01 maker-checker:
  - `tst.perf.slo_list_ms`, `slo_record_ms`, `slo_save_ms`, `slo_report_ms` and `slo_realtime_ms`: 500, 300, 800, 3,000 and 2,000 ms;
  - `punch_burst_per_min`: 2,000;
  - `soak_growth_pct`: 10.
- A journey passes when its p95 is within its SLO with no error; the burst must also hold its rate. A soak passes when its memory after warm-up grows less than 10 %.

**FR-03 Profiling and fixes.** CPU profiles of the server under load gave these findings, all fixed in the platform with one additive index (BR-01; details in [CAPACITY_PLAN](../CAPACITY_PLAN.md) §2):

## 8. How to verify manually

1. Run `node scripts/load_test.mjs --profile smoke --post http://localhost:3000` against a development installation with `ff.qa.p3006` set.
2. Open **Performance Test Results**. The run shows with its journeys against their SLOs and the server's memory.
3. Run `node scripts/perf_verdict.mjs reports/load-smoke.json`.
4. Ask for a change of `tst.perf.slo_list_ms` in the Control Center. It applies to the next run once a second administrator approves it.
