## 1. Discovery summary
There was no sign-in. `AUTH_MODE=dev-headers` trusted request headers (D-001), the role map was a constant, `config.js` refused `AUTH_MODE=iam`, and there was no user table, password hash, session or MFA. So there were no existing users or legacy hashes in the repository: the legacy-hash path (BR-03, T-04) is built and proved with hashes imported in the old formats, and the first users are created by script. The user master (02.03) and organisation tables (02.02) do not exist, so users are a thin stand-in (D-059). Decision per requirement: `docs/erp/DISCOVERY/02.01.md`. Departures from the pack: SSO is configuration only (D-061); text and WhatsApp codes go through the SMS and WhatsApp connectors of the integration hub because 04.07 does not exist; biometric unlock is not built (PIN only, D-062); the sign-in routes are not behind the feature flag (ADR-66).

## 2. What was built
- **Tables** (migrations `20261030000022` and `20261030000023`, up and down): `iam_users`, `iam_credentials`, `iam_mfa_factors`, `iam_devices`, `iam_auth_policy`, `iam_sessions`, `iam_refresh_tokens`, `iam_login_events`, `iam_login_throttle`, `iam_password_resets`; flag `ff.iam.p0201` (default OFF, ON in development and test).
- **Passwords**: Argon2id from Node's own crypto, constant-time verify, decoy hash for unknown names. Hashes in `pbkdf2_sha256`, `scrypt` and salted `sha256` formats still verify and are replaced at the first successful sign-in (audited). Policy: at least 10 characters, common-password list and optional Pwned Passwords k-anonymity check, not the username, last 5 remembered, optional expiry; a change ends the person's other sessions.
- **Lockout and CAPTCHA**: failures counted per sign-in name (also for names that do not exist); a signed question after the threshold; a lock that doubles per further failure. Wrong password, unknown name, disabled account and lock all get the same message.
- **Sessions**: short-lived access token naming a session, rotating refresh token (HttpOnly SameSite=Strict cookie with a CSRF header, or in the body for native clients), reuse of a replaced token ends the session. The session row is the authority on every request, so sign-out, forced sign-out, idle and absolute timeout, concurrent-session limit and a disabled user take effect at once.
- **MFA**: TOTP (RFC 6238 vectors tested, a step cannot be used twice, seed encrypted with the vault), text and WhatsApp codes, ten single-use backup codes. Roles in the policy (default SYSADM, ITADM, CFO, DIR) cannot finish signing in without one; with none set up they are led into set-up and sign in when the first code is confirmed. A remembered device (up to 30 days) skips the step, but not for those roles unless the policy allows it.
- **Devices, PIN and alerts**: device list, forget a device; PIN unlock for field roles (five wrong PINs remove it, never for roles that need MFA); suspicious-login detection (new device, new country, impossible travel) recorded, published as an event and emailed to the person.
- **Policy and administration**: policy per company; a change is a maker-checker request (ITADM asks and SYSADM approves, or the reverse), audited, with history, export and import of settings; administrators list users, sessions and login history, force sign-outs and clear locks.
- **Pages** (behind `ff.iam.p0201`): Sign-in (English and Hindi, shown by the shell before anything else), Security & MFA, My Sessions & Devices, Authentication Policy, Login History (history, active sessions, users).
- **Roles**: everyone signed in manages their own account; ITADM and SYSADM have `iam.security.view` and `iam.security.manage`.
- **Dependency added**: `qrcode` (QR image for the authenticator app).
- Docs: `ARCHITECTURE.md` section 18, `DECISIONS.md` ADR-61 to ADR-67, `DEFECTS.md` D-059 to D-067, `DB_CHANGES.md`, `DB_BASELINE.md`, `openapi.yaml`, `.env.example` (`AUTH_SECRET`); `schema/baseline.json` re-locked.

## 7. How to verify manually
1. Start the sample sign-in server (it seeds people such as `admin-d`, `field-d` and `lock-d`, password `Excavator-Test-9-Pw`): run `npm run build`, then `AUTH_MODE=iam NODE_ENV=development PORT=3000 DATABASE_PATH=data/iam.sqlite node scripts/e2e_iam_server.mjs`, and open http://localhost:3000. The same server runs on port 3101 in the E2E tests.
2. Sign in as `admin-d`: the screen asks you to set up an authenticator (QR and key). Confirm a code, save the ten backup codes and you are in. Sign out and in again: the second step is asked.
3. Enter the wrong password for `lock-d` three times: a question appears; five failures lock the account and the right password is refused with the same message. As an administrator open Login History > Users and unlock it.
4. Sign in as `field-d` with "Remember this device", open My Sessions, set a PIN, sign out and unlock with the PIN.
5. As `admin-d`, Authentication Policy: change the idle minutes and request the change; approve it as an IT Administrator under Approvals.
6. `NODE_ENV=test node --test tests/iam-platform.test.js tests/iam-api.test.js`; `npx playwright test e2e/signin.spec.js`; `npm run erp:regression` runs everything.
