## 1. Discovery

The backup engine of 01.02 already copied and checksummed the database. This part moves it into the platform and adds schedule, encryption, the off-site copy, retention, restore tests, drills, alerts and an approved production restore. See the [discovery note](../DISCOVERY/29.06.md).

## 2. What was built

The page is `/admin/backups` (**Administration → Backup & DR**), with pill tabs:

- **Status (FR-05)**:
  - **Tiles**: last full backup; newest recovery point against the RPO; the off-site copy; the last DR drill against the RTO. A red banner shows when any check fails.
  - **Actions**: take a full backup or snapshot, run a drill, or check now.
  - The open alerts.
  - **Policy**: retention, targets, locations, and whether the backup key is set.
- **Backups (FR-01, FR-02)**: every full and snapshot, with size, rows, encryption, the off-site copy, its retention tiers and the file replication result.
- **Restore tests & drills (FR-03, FR-04)**:
  - **Restore test**: decrypts the off-site copy into an isolated folder (never the live database) and validates it: off-site checksum, file checksum, integrity, row counts and checksums of every table, and the schema.
  - **Drill**: restores the newest recovery point and measures the restore time against the RTO (240 min) and the data-loss window against the RPO (15 min).
  - Each has a PDF report.
- **Production restore (BR-01)**:
  - A request names a verified backup whose restore test passed, plus the incident reference and what happened.
  - ITADM, then DIR, approve it; only one may be open.
  - The page then shows the operator's command, `npm run db:restore -- --approved <id>`. It runs with the application stopped, checks the approval, verifies the backup, keeps a safety copy of the current database, restores, and records the execution. An approval is used once.

**Jobs**:
- a full backup daily at 02:10 IST, with file replication;
- snapshots every 15 minutes;
- retention daily;
- the checks every 15 minutes, which notify ITADM.

**Parameters**:
- retention daily 14, weekly 8, monthly 12, yearly 7 (`admin.backup.keep_*`);
- RPO, RTO and the drill interval (`admin.dr.*`).

**Configuration**: `BACKUP_OFFSITE_DIR` and `BACKUP_KEY`.

The 29.01 control center's backup tile now reads these backups. Labels are en/hi/te (area `bkp`).

**Permissions**:

| Role | Grant |
|---|---|
| ITADM, SYSADM | View, run backups and tests, request a production restore |
| DIR | View; approves a production restore after ITADM |
| CFO, AUD | View |

## 4. Tests

`tests/admin-backups.test.js` has four tests, all passing:

1. **Backup and restore test**:
   - a full backup, verified; the off-site copy is encrypted (ERPBK1 header, no SQLite text); a stored file is replicated;
   - the isolated restore test passes, and its copy is removed afterwards;
   - the PDF report;
   - a changed off-site copy fails the test;
   - roles.
2. **Drill and monitoring**:
   - with nothing backed up, four checks raise alerts;
   - the drill passes within the RPO and RTO; the checks resolve;
   - a stale recovery point fails the drill.
3. **Retention**: 40 daily fulls and 10 snapshots. The newest 14 dailies, the Sunday weeklies, the yearly and 48 hours of snapshots are kept; the rest expire and their files are deleted.
4. **Production restore**:
   - refused without a passed test;
   - one at a time; the auditor is refused;
   - ITADM then DIR;
   - the operator's step on a database file restores it, keeps a safety copy and records EXECUTED; a reused approval is refused.

`e2e/admin-backups.spec.js` passes on desktop and mobile:

1. A full backup.
2. A drill that passes, with the status healthy.
3. The drill in the tests tab.
4. A production restore approved by a second ITADM and a director, with the command shown.

## 6. Known limitations

D-794:

- The recovery point is a 15-minute snapshot, not WAL streaming.
- The off-site location is a configured directory, not a cloud second region.
- Restore tests run on the same machine.
- The production restore is executed by the operator.

## 7. How to verify manually

1. In a test company, set `ff.admin.p2906`, and set `BACKUP_OFFSITE_DIR` and `BACKUP_KEY` on the server.
2. As ITADM, open **Administration → Backup & DR**, then **Take a full backup**. The backups tab shows it verified, encrypted and copied off site.
3. Click **Run a DR drill**. It passes, with the restore time and data-loss window shown; download its report.
4. Under **Production restore**, request one for that backup with an incident. A second ITADM approves, then a director. Stop the application, then run the command shown.
