## 2. What was built

**Test Coverage & Results** (`/admin/test-coverage`, Administration) is a technical-console report. The header gives the verdict: suite green, not green, or no catalogue yet.

- **Chart first:** tests by type with their last result (pass, fail, not run). Each bar drills to the list.
- **Key figures:**
  - tests, failing and not run;
  - delivered parts with tests: **191 of 192 (99.5 %)**;
  - workflow types tested: **238 of 238**;
  - permission matrix cells: **44 roles × 45 modules**.
- **Coverage by part (FR-01):** every part in PROGRESS.csv with its tests, requirement references and results. Gaps and failures come first, and **Gaps only** shows delivered parts with no test (one: 166.6, whose tests are filed under 07.14).
- **Tests:** a list filtered by part, type, last result and text. It shows as cards on a phone with the parameters in a bottom sheet, and has a sticky total. Export (XLSX, CSV, PDF) is in the "…" menu and is audited.
- **Sandbox tab** ([Config] Sandbox Reset & Scenario Packs):
  - whether this installation is a sandbox, its database, and the calls it refused;
  - the synthetic companies, with **Generate** and a confirmed **Reset**;
  - the three packs with expected against last actual KPIs, each with **Run the pack**;
  - the runs.

**Catalogue (FR-01):**

- `scanCatalogue()` reads every `test(...)` of the repository: **2,142 tests in 526 files**. Each gets:
  - a stable ID (file plus name hash);
  - its part, from the file name, a header, the flag the file uses most, or the first completion report that names it (89 platform tests have none);
  - the requirement codes in its name (1,525 tests name at least one);
  - its type (UNIT, API, WORKFLOW, PERMISSION, E2E, VISUAL, ACCESSIBILITY, PERFORMANCE, SECURITY, INTEGRATION, DATA).
- **Sync** adds, updates and retires tests. Manual UAT cases are added with `automated = 0`.
- Runs come from JUnit output: `scripts/test_results.mjs` posts in batches of about 40 kB, joined into one run.

**Permission and workflow tests (FR-02):**

- `tests/tst-permission-matrix.test.js`: every one of the 44 roles × the key list of each of 45 modules. Holders get through, others get 403, nobody signed in gets 401.
- `tests/tst-workflow-coverage.test.js`: every one of the 238 registered document types has:
  - a default chain the engine can run (a decision step, real roles or resolvers, existing system actions);
  - a process owner that is a role;
  - a route, and a description of a missing document that does not fail.
- The test found **D-807**: 30 default chains are refused by the definition editor. The number is held and may only fall.

**Sandbox (FR-03 … FR-05, BR-01):**

- `ERP_SANDBOX=true` is refused in production and on a database whose name does not say sandbox.
- In a sandbox, these refuse every call and count it:
  - the integration hub (e-mail, SMS, WhatsApp, bank, GST, AI);
  - single sign-on and the breached-password check;
  - webhooks;
  - web push.
- The session tells the shell, which shows a **SANDBOX** banner (en/hi/te).
- **Generate** creates a company `SBX-n` with:
  - nine synthetic people, items and partners;
  - four projects, each with a site, WBS, BOQ with a cement norm, approved budget, schedule, baseline and store;
  - **twelve months of transactions**: approved DPRs through the progress engine, and stock receipts and issues through the stock API.
  - Foreign keys stay on: the integrity check finds 0 problems.
- **Reset** removes every synthetic company and all its rows, then generates a new one.
  - The delete guards of approved documents and stock ledgers are lifted for that one statement only.
  - The hash-chained audit log is never touched. A company with trail rows is renamed `SBXR-n` and made inactive.
- **Scenario runner (FR-04):** each run builds its own project and executes the thread over HTTP as the synthetic people, then reads the KPI back through the API:

| Pack | Thread through the API | Expected → actual |
|---|---|---|
| Delayed project | DPRs → progress period with actual cost (PLAN) → approved by the PM → closed period and dashboard | SPI **0.76**, planned 50 %, done 38 %, CPI 0.9048 |
| Loss-making project | the same, on time and over cost | SPI **1**, CPI **0.8**, EAC ₹12,50,000 on ₹10,00,000 |
| High wastage | DPR of 30 m³ → receipt and issue of 300 bags through the stock API → the QS's key material and reconciliation | norm 240 bags, issued 300, wastage **25 %**, over the allowed 5 % |

## 7. How to verify manually

1. Start a sandbox: `ERP_SANDBOX=true AUTH_MODE=dev-headers DATABASE_PATH=data/sandbox.sqlite npm start`. The banner shows.
2. Set `ff.qa.p3004` and, as ITADM, open **Test Coverage & Results**.
3. **Sync the catalogue**, then record a run: `node --test --test-reporter=junit "tests/*.test.js" > r.xml; node scripts/test_results.mjs r.xml`.
4. On the **Sandbox** tab:
   - **Generate a company**;
   - **Run the pack** for each scenario: each shows PASS with its expected and actual KPIs;
   - **Reset the sandbox**.
