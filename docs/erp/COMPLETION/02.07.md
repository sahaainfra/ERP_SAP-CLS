## 1. Discovery summary
Each of about 270 routes guarded itself, in its route line or its service, and nothing listed them; there were three static headers and no content security policy, no CORS handling, a CSRF header check on two routes, a sign-in limit inside the iam module only, no rotation procedure for the vault key, no threat model and no server-side export. Decision per requirement: `docs/erp/DISCOVERY/02.07.md`. Departures from the pack: the route policy was drafted from the source and then corrected against the running application (D-111); there is no socket server or Dockerfile yet, so the room guard and the container scan wait for what they protect (D-109, D-110); rate counts are per process (D-107); server-side exports exist for people's records only (D-113).

## 2. What was built
- **Route registry** (`platform/security`): `route-policy.js` declares each of the 278 routes (method, path, guard, permission, validation schema, scope, rate-limit class, audited). At start-up the application lists its own routes (`routes.js` wraps `Router.use`) and compares: in staging and production an undeclared route stops the start (BR-01); `npm run erp:route-check` (in the regression and CI) fails on an undeclared route, a stale line or an unknown permission. The snapshot is `core_route_registry` with each route's last test result.
- **Authorise stage**: a route declared with a permission is closed to a person who holds none of its permissions before the route runs; the services still check, with scope. Internal middleware `authorise(key, scope)`, `validate(schema)` and `audit()` are available to routes.
- **Self-test**: every non-public route is called with no sign-in (must be 401) and with a person who holds no permission (a permission route must be 403); results are stored and shown.
- **Headers, CORS, CSRF**: CSP (scripts from this application only, no framing, no plug-ins), HSTS on secure connections, X-Frame-Options, Referrer-Policy, Permissions-Policy, nosniff, cross-origin policies, `no-store` for API answers; a strict CORS allow-list (a foreign origin gets no CORS headers and cannot change data; preflights answered only for allowed origins); the CSRF header required on the routes where the session cookie authenticates (refresh, logout, resume).
- **Rate limits**: classes auth, otp, export, write, read and webhook, per address and per person, from the settings; 429 with Retry-After; the first refusal in a window is a security event.
- **Security settings** (`core_security_settings`): validated (a policy that allows inline scripts, or drops the framing rule, is refused) and changed only by an approved request (ITADM asks, SYSADM or DIR decides), audited with the diff, shown as change history, announced as an event.
- **Secrets**: only in the environment (staging and production refuse to start without them); the page shows set or not set, never a value; `docs/erp/SECRETS.md` has the rotation procedures and `npm run erp:rotate-vault-key` re-encrypts every stored credential under a new key (dry run first, all or nothing, each value checked).
- **Export controls**: `POST /iam/users/export` needs `iam.user.export`, refuses more rows than `core.export.max_rows`, neutralises spreadsheet formulas, needs an approval above the threshold (default 1,000 people: requester then HRMGR or DIR, tied to the exact filters, used once), and is written to the audit trail and, for people's records, the security log.
- **Rooms and background work**: the room guard checks the permission on join and again for every member on every event, dropping a member who lost access; `actAs` runs work for a person with that person's grants and only while they can sign in.
- **CI and documents**: dependency review on pull requests, a container scan job that scans as soon as a Dockerfile exists, the route check in the regression, the secure coding checklist in the pull request template, `docs/erp/THREAT_MODEL.md` and `docs/erp/SECRETS.md`.
- **Pages**: Route Registry (summary, filters, protection, last test, run the self-test, CSV) and Security Settings (rate limits, headers, CORS list, export threshold, secrets, pending request, change history, JSON export and import).
- **Roles**: ITADM configures and runs the self-test; SYSADM, AUD and ITADM view the registry and settings; SYSADM or DIR approves a settings change; HRMGR (and SYSADM, ITADM) may export people; HRMGR or DIR approves a bulk export.
- Also changed: `/iam/users/roles` and the 02.05 and 02.06 routes were corrected in the policy where the draft named the wrong permission; the refused-request security event now also covers refusals by the Authorise stage.
- Docs: `ARCHITECTURE.md` section 24, `DECISIONS.md` ADR-102 to ADR-108, `DEFECTS.md` D-107 to D-113, `DB_CHANGES.md`, `DB_BASELINE.md`, `openapi.yaml`; `schema/baseline.json` re-locked (295 objects; 291 unchanged, 4 new).
