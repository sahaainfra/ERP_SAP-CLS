# Part 30.01 — Cross-Module Integration & Real-Time Propagation

Execution step 219 · 2026-11-23 · Branch `ccr-a3b3ce3d-65llwf` · **In progress**: built and tested behind `ff.qa.p3001`. Formal acceptance waits for 29.05 and the company's G1/G2 sign-offs.

## 1. Discovery

The ERP already had everything an integration check needs to read: the event catalogue (897 types, each with its owner), the bus (71 consumers, an inbox row per delivery with its time and status), the real-time log, the notification engine, the posting log and the link columns every module stores. There was no cross-module thread test, no matrix and no latency measure. The module code `qa` belongs to site quality, so M30 is the new module `tst` (ADR-754). See the [discovery note](../DISCOVERY/30.01.md).

## 2. What was built

The page is `/admin/integration-matrix` (**Administration → Integration Matrix**), a technical-console report:

- **Chart first**: event deliveries by producing module (pass, failing, not exercised), each bar drilling to the matrix.
- **Key figures**: threads passed (15 / 15), broken hand-offs, fields typed twice, event deliveries failing, real-time latency p95 against the 2 s target, the size of the catalogue.
- **Threads** (FR-01): fifteen mandatory threads, 71 hand-offs. Each hand-off is a downstream record that must come from an upstream record of another module. The verifier reads the owners' link columns (read-only, one company; ADR-756) and reports:
  - **broken**: a record with no source, or a link to a record that does not exist;
  - **typed again** (FR-03): a field the record carries over from its source with another value (e.g. a GRN for another vendor than its order);
  - **posting failures** of the thread's documents in the posting engine.

  | Code | Thread |
  |---|---|
  | IT-01 | Tender → estimate → award → project → BOQ → budget → schedule → work authorisation |
  | IT-02 | MR → PR → RFQ → CS → PO → gate entry → GRN → vendor invoice → AP bill → payment |
  | IT-03 | WA → material request and issue → DPR → material reconciliation |
  | IT-04 | Attendance → payroll → salary transfer (and posting) |
  | IT-05 | Plant allocation → log book → fuel → cost |
  | IT-06 | IR → MB → RA bill → certification → tax invoice → receivable → receipt |
  | IT-07 | WO → sub-measurement → sub-bill → AP bill → payment |
  | IT-08 | RFI → change request → variation → revised BOQ → budget change |
  | IT-09 | Delay → claim → EOT → baseline revision |
  | IT-10 | NCR → back-charge in the subcontractor bill |
  | IT-11 | Month-end close: tasks, period, project monthly close |
  | IT-12 | PO → budget commitment → actual cost |
  | IT-13 | GRN → material test |
  | IT-14 | Hire agreement → hire bill → vendor invoice |
  | IT-15 | DPR progress line → measurement book |

- **Matrix** (FR-04): every event of the catalogue with each consumer the bus delivers it to:
  - producer, event, consumer;
  - test IDs: the thread hand-offs that travel on it, and the test files that name the event or the consumer;
  - published, handled, pending and dead deliveries;
  - latency p95 (event created → handled);
  - status. FAIL means a dead letter, or an event pending longer than `tst.integration.pending_alert_minutes`.

  Subscriptions to event names nobody declares are listed as warnings (D-799).
- **Re-keying**: every field typed twice, with the value and what the source says.
- **Latency** (FR-02): **Send a latency probe** publishes `tst.probe.sent` through the outbox. The consumer `tst.probe` puts it on the person's real-time room and in their notifications and records:
  - bus time;
  - screen time;
  - notification time;
  - PASS or FAIL against `tst.integration.latency_target_ms` (2 000).

  The probes' p95 is a key figure; the run history is a chart.
- **Runs**: **Run the checks now** queues the background job `tst.integration.check`. It stores the snapshot (`tst_integration_runs`), notifies the person and publishes `tst.integration.checked`. A nightly schedule runs it for every company with the part on and e-mails the result.
- **Document**: `npm run erp:integration-matrix` writes [INTEGRATION_MATRIX.md](../INTEGRATION_MATRIX.md). It contains the threads and their hand-offs, and the 363 edges (producer, event, consumer, test IDs, status). On the fixture: GREEN, 15/15 threads, 222 edges covered by a test, 141 without one (D-800).

## 7. How to verify manually

1. Set `ff.qa.p3001` for a test company that has data, or load the T-01 fixture (`buildThreads(db, company)` in `tests/tst-fixtures.js`).
2. As ITADM, open **Administration → Integration Matrix**. Click **Run the checks now**; the status turns Green and Threads passed shows 15 / 15.
3. Open IT-02 (**Show 12 hand-offs**): each hand-off shows its records and Pass.
4. Click **Send a latency probe**: the banner shows the time to your screen (a few ms) against 2 000 ms. A notification arrives, and the Latency tab lists the probe.
5. Open the **Matrix** tab. Filter by event `bill.sub.approved`: three consumers, with their test IDs and IT-07.3.
6. Change a GRN's vendor in the database and run again. The **Re-keying** tab lists the GRN and the fuel receipt that follows it, and the run is Red.
7. Export the matrix (… → Export XLSX); the export is in the audit trail.
8. On a project's approved baseline whose claim has an EOT award, click **Revise**, choose **Extension of time awarded** and save. The new revision's reference is the claim number.
